# Зафиксировать UTF-8 локаль в CI

## Описание
Проверка 5 в `scripts/check-docs.sh` ищет в `docs/architecture.md` номера задач, пути `tasks/` и раздел «Состояние». Изначально она использовала диапазон `grep -E '[Зз]адач[а-я]* +[0-9]{3}|tasks/|^#+ +Состояние'`. В Linux-контейнерах локаль по умолчанию `C.UTF-8`, а у этого локаля нет таблицы упорядочивания для кириллических диапазонов: `grep -E '[а-я]'` завершается с «Invalid collation character», вывод пустой, ошибка уходит в stderr. Проверка получала пустой вывод, `&& fail=1` не срабатывал, и харнес сообщал об успехе, ничего не проверив. Обнаружено на VPS 2026-10-27, воспроизведено там же.

Исходная поломка устранена 2026-10-28 в источнике: в `scripts/check-docs.sh` диапазон заменён на литералы (`[Зз]адач[^ ]*`), и коллация больше не нужна — проверка работает при любой локали. Задача фиксирует локаль в CI, чтобы класс проблем не вернулся и чтобы поведение харнеса и форматирования не зависело от образа runner.

Зависит от: —.
Среда: Linux или Windows.

## Критерии готовности
- В CI локаль, при которой `grep -E` по кириллице работает без ошибки коллации.
- Правка не меняет смысл проверок и не трогает `scripts/`.
- Харнес в CI проходит.

## Анализ
Причина не в скрипте, а в локали процесса: `LC_ALL=C.UTF-8` не определяет порядок для диапазонов в регулярных выражениях. Место правки — окружение задачи CI, а не `scripts/check-docs.sh`: по `AGENTS.md` скрипты не меняются без явной просьбы, а локаль — свойство окружения.

Две причины зафиксировать локаль, а не полагаться на аккуратность в скриптах:
1. Отказ тихий: `grep` пишет ошибку в stderr и возвращает 2, а в цепочке `grep ... | ... | grep . && fail=1` это выглядит как «нашлось нарушение, которого нет» или, наоборот, как успешная проверка. Следующий такой диапазон вернёт тот же класс поломки незаметно.
2. `dotnet format` и другие инструменты над кириллическими исходниками не должны зависеть от локали образа runner: смена образа тогда не меняет результат проверки.

Локаль `C` и `POSIX` не подходят (там нет ни кириллицы, ни UTF-8 вовсе), нужна именно `en_US.UTF-8`.

## План
1. В `.github/workflows/harness.yml`, `.github/workflows/harness-audit.yml` и `.github/workflows/build.yml` задать `env:` с `LC_ALL: en_US.UTF-8` и `LANG: en_US.UTF-8` для Linux-задач, где выполняется харнес или форматирование.
2. Не менять `scripts/check-docs.sh` и не добавлять туда проверку локали.
3. Выполнить «Проверку».
4. «Отчёт»: что уже устранено в источнике и что даёт фиксация локали. Завершить через `scripts/release-task.sh 142`, затем `bash scripts/check.sh`.

### Проверка
```
LC_ALL=C.UTF-8 grep -E '[а-я]' /dev/null; echo "rc=$?"      # ожидается rc=2 (Invalid collation character)
LC_ALL=en_US.UTF-8 grep -E '[а-я]' /dev/null; echo "rc=$?"   # ожидается rc=1 (нет совпадений, без ошибки)
LC_ALL=C.UTF-8 bash scripts/check.sh                          # ожидается «Харнес: все проверки пройдены»
bash scripts/check.sh
```

Файлы: `.github/workflows/build.yml`, `.github/workflows/harness.yml`, `.github/workflows/harness-audit.yml`

## Отчёт
Правка в окружении CI, а не в `scripts/`: причина в локали процесса (`C.UTF-8` не определяет порядок для диапазонов в регулярных выражениях), а скрипты по `AGENTS.md` без явной просьбы не меняются.

Исходная поломка (тихий пропуск проверки 5) устранена в источнике 2026-10-28 в PR #18: кириллический диапазон заменён на литералы, коллация больше не нужна. Проверено на машине: `LC_ALL=C.UTF-8 bash scripts/check.sh` → «Харнес: все проверки пройдены», rc=0, ошибки коллации нет.

Что изменено в этой задаче — фиксация локали, чтобы класс проблем не вернулся и чтобы результат не зависел от образа runner:
- `.github/workflows/harness.yml` — `env:` с `LC_ALL`/`LANG` = `en_US.UTF-8` для задачи `check`.
- `.github/workflows/harness-audit.yml` — то же для задачи `audit`.
- `.github/workflows/build.yml` — то же для Linux-задач `core` и `avalonia`.

Проверено на машине:
```
LC_ALL=C.UTF-8     grep -E '[а-я]' /dev/null  → rc=2, «grep: Invalid collation character»
LC_ALL=en_US.UTF-8 grep -E '[а-я]' /dev/null  → rc=1, совпадений нет, ошибки нет
LC_ALL=C.UTF-8     bash scripts/check.sh      → «Харнес: все проверки пройдены», rc=0
```
То есть без фиксации локали харнес сейчас работает, но любой новый диапазон в регулярном выражении вернёт тихий пропуск; с фиксацией — нет.

Все три workflow-файла разбираются как YAML. `bash scripts/check.sh` проходит.

`docs/status.md` править не потребовалось: пункт об этой проблеме уже удалён 2026-10-28 вместе с починкой в источнике.
