# Отладочный трейс: вводы пользователя и запросы к API моделей

## Описание

В режиме отладки записывать всё, что нужно, чтобы воспроизвести проблему на моках, какой бы она ни была: вводы пользователя, входы и выходы HTTP-запросов к провайдерам (fal.ai, Replicate, OpenRouter), включая изображения, заголовки, тела, коды статусов и тайминги.

Цель: по логу можно написать юнит-тест, который повторяет проблему на моке провайдера.

Зависит от: 045 (подробное логирование, уже в `main`). Использует то же включение уровня логов (`IMAGEGEN_LOG_LEVEL` или `logging.json` в папке данных). Задача расширяет 045, а не заменяет её.

Среда: Linux или Windows.

## Критерии готовности

- В режиме отладки каждый ввод пользователя записывается: текст промпта, выбранные модели, параметры генерации, прикреплённые изображения.
- Для каждого HTTP-запроса к провайдеру записываются: метод, URL, заголовки запроса, тело запроса, время отправки.
- Для каждого HTTP-ответа записываются: код статуса, заголовки ответа, тело ответа, время получения и длительность.
- Изображения во входах и выходах сохраняются отдельными файлами в папке отладки; в записи лога стоит ссылка на файл, а не base64 внутри строки.
- Заголовки и значения, содержащие ключи API (например `Authorization`), маскируются и в лог не попадают. Ключи не пишутся ни в каком виде (правило `AGENTS.md`: ключи только в шифрованном хранилище).
- Формат записи описан в `docs/specs/` и версионирован, чтобы по нему можно было разбирать лог автоматически.
- По одной записи лога можно восстановить запрос и ответ достаточно, чтобы собрать мок провайдера в тесте. Проверка: для одного сценария (генерация через один провайдер) из лога собран тест на моке, который воспроизводит запись.
- Вне режима отладки эти записи не создаются, а обычное логирование из 045 работает как раньше.
- Тесты и линтер проходят по затронутым проектам.

## Анализ

Задача создана сейчас в виде заготовки и не разобрана. Перед планированием нужно исследовать:

- Где в коде проходят все HTTP-вызовы провайдеров и как их перехватить одним обработчиком (`DelegatingHandler`), не меняя клиенты провайдеров.
- Какой формат записи выбрать: например, JSON Lines с полями `ts`, `kind`, `provider`, `request`, `response`, `files`.
- Как хранить изображения: файлы рядом с логом, с именами по хешу содержимого или по id запроса.
- Как маскировать ключи: по имени заголовка и по значению из хранилища ключей.
- Объём логов и ротация: сколько занимают тела ответов с картинками и нужна ли отдельная политика хранения (сейчас 14 дней, см. `AGENTS.md`).
- Как связать вводы пользователя и HTTP-записи в один сценарий (идентификатор генерации или прогона).
- Совпадение с `docs/architecture.md` и `docs/specs/image-client.md`, а также пересечения с 045 в конфигурации логирования.
