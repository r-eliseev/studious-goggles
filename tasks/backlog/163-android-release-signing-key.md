# Постоянный ключ подписи Android APK

## Описание
Найдено 2026-10-31 при подготовке APK для проверки 134/159/160/162. Релизный APK (`release.yml`, шаг «Publish MAUI Android (APK)», комментарий «No release keystore yet») подписывается отладочным ключом, который сборочная машина CI создаёт заново. Сертификаты у релизов разные:
- v0.1.4 — SHA-256 `ea69d1ba…1c4a`;
- v0.1.5 — SHA-256 `64e1081e…5e5a`;
- локальная сборка — третий.

Android не ставит обновление с другой подписью поверх установленного приложения: каждое обновление из релиза требует удалить приложение, а с ним БД, картинки и ключи провайдеров (`allowBackup=false`, задача 115). Возможно, связано с 161 (пропавшие сессии).

Зависит от: — (ключ и секреты GitHub создаёт владелец).
Среда: Linux или Windows; правка `.github/workflows/release.yml` разрешена этой задачей в объёме подписи APK.

## Критерии готовности
- Владелец создал постоянный upload/release keystore и добавил его в секреты репозитория (файл keystore в base64, пароль, alias); ключ не попадает в git, логи и артефакты, кроме подписанного APK.
- `release.yml` подписывает APK этим ключом (`AndroidKeyStore`, `AndroidSigningKeyStore`, `AndroidSigningKeyAlias`, пароли из секретов); без секретов workflow падает с понятным сообщением, а не подписывает отладочным ключом молча (ручной запуск `workflow_dispatch` может явно разрешить отладочный ключ для проверки сборки).
- Два последовательных запуска дают APK с одинаковым сертификатом (`apksigner verify --print-certs`), обновление ставится поверх без потери данных — проверено владельцем.
- `README.md` и `docs/knowledge/dev-environment.md`, «Релиз», описывают: последнее обновление с отладочным ключом потребует один раз удалить приложение; дальше обновления ставятся поверх.

## Анализ
- `release.yml`, задача `maui-android` (Windows): `dotnet publish … -p:AndroidPackageFormat=apk` без параметров подписи → .NET for Android подписывает `*-Signed.apk` ключом `debug.keystore`, который создаётся заново на чистой сборочной машине. Отсюда новый сертификат в каждом релизе.
- .NET for Android подписывает своим ключом через MSBuild: `AndroidKeyStore=true`, `AndroidSigningKeyStore` (путь), `AndroidSigningKeyAlias`, `AndroidSigningStorePass`, `AndroidSigningKeyPass`; пароли принимают префикс `env:` — значение берётся из переменной окружения и не попадает в командную строку.
- Секреты GitHub недоступны в выражениях `if:` напрямую; их передают в `env` шага и проверяют в скрипте.
- Переход на постоянный ключ сам потребует одного последнего удаления приложения (сертификат снова меняется). Если позже по 030 сменится `ApplicationId` (сейчас `com.companyname.imagegen.maui`, утверждён `com.eliseev.imagegen`), это будет уже другое приложение — тоже отдельная установка. Совместить оба перехода в одном релизе — решение владельца, вне этой задачи.

## План
1. Шаг «Restore signing key» перед публикацией: секреты `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` в `env`; если все заданы — декодировать keystore в `$RUNNER_TEMP` (вне рабочей копии и артефактов) и включить подпись; если не заданы: при теге — ошибка с понятным сообщением, при ручном запуске — предупреждение и отладочный ключ (проверка сборки).
2. Публикация добавляет параметры подписи только при наличии ключа; пароли — через `env:`.
3. После публикации — удалить keystore из `$RUNNER_TEMP`.
4. Документы: `docs/knowledge/dev-environment.md`, «Релиз» (секреты, однократная переустановка); `README.md` (то же для пользователей); комментарий в `release.yml` вместо «No release keystore yet».
5. Проверка: синтаксис YAML; ручной запуск workflow после добавления секретов владельцем — два запуска с одинаковым сертификатом (`apksigner verify --print-certs`), установка поверх у владельца.

Файлы: `.github/workflows/release.yml`, `docs/knowledge/dev-environment.md`, `README.md`.
