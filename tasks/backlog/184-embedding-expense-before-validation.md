# Семантический индекс: записывать расход до проверки ответа эмбеддингов

## Описание
Находка код-ревью 2026-11-02 (PR #70, задача 105). `SemanticIndexService.IndexCurrentSourcesAsync`: `ValidateResult(result, batch.Length)` бросает исключение раньше, чем создаётся и сохраняется `Expense`. Если ответ не прошёл проверку (другое имя модели, неверное число векторов, нечисловые значения), провайдер уже взял плату, а журнал расходов её не видит.

Зависит от: 185 (тот же метод; делать после её слияния).
Среда: Linux или Windows.

## Критерии готовности
- Если у ответа есть `CostUsd`, расход сохраняется в журнал до проверки ответа, даже когда проверка затем падает.
- Векторы неверного ответа не сохраняются (как сейчас).
- Успешный путь пишет расход ровно один раз (нет двойной записи).

## Анализ
Для смены размерности уже есть образец: `UpsertBatchAsync([], expense, …)` сохраняет только расход. Тест рядом: `IndexAsync_NonFiniteProviderVector_FailsWithoutPersistingIt` (`ImageGen.Core.Tests/Services/SemanticIndexServiceTests.cs`).

## План
1. Падающий тест `IndexAsync_InvalidResponse_StillRecordsPaidExpense`: провайдер возвращает ответ с `CostUsd = 0.001` и нечисловым вектором (как в `…NonFiniteProviderVector…`). Ожидать: статус `Failed`, векторов в хранилище нет, а `UpsertBatchAsync` получил расход 0.001 (в фейке репозитория посмотреть, как он хранит переданный `Expense`; если не хранит — добавить в фейк список полученных расходов).
2. Фикс: перенести создание `expense` выше `ValidateResult`. Обернуть `ValidateResult` так: при исключении сначала `UpsertBatchAsync([], expense, …)` (только если `expense` не `null`), затем пробросить исключение. Ветка смены размерности уже сохраняет расход — не дублировать. Успешный путь сохраняет расход вместе с векторами, как сейчас.

Файлы: `ImageGen/ImageGen.Core/Services/SemanticIndexService.cs`, `ImageGen/ImageGen.Core.Tests/Services/SemanticIndexServiceTests.cs`.

## Отчёт

Расход с `CostUsd` создаётся до валидации ответа. Если валидация завершается исключением, пустой batch вместе с расходом сохраняется до повторного выброса ошибки; некорректные векторы не записываются. Успешный путь по-прежнему сохраняет расход только в единственном `UpsertBatchAsync`.
