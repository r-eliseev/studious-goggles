# Заметки о релизе: что изменилось с прошлого тега

## Описание
Замечание по релизу v0.1.4 (2026-10-29): в описании релиза на GitHub стоит «Релиз v0.1» и перечислены только задачи 001–015 и 034; работа последних недель (Avalonia, хранилище, сессии и прочее, задачи из `tasks/backlog` и `tasks/DONE.md`) не видна. Все релизы v0.1.x получают одинаковый текст.

Что известно: `.github/workflows/release.yml` (шаг «Release notes») берёт папку релиза из тега без патч-номера (v0.1.4 → `tasks/v0.1`) и вызывает `scripts/release-notes.sh`; скрипт перечисляет только задачи `done` с релизом `v0.1` (в папке и в `tasks/DONE.md`). Задачи из `backlog`, сделанные между тегами, в заметки не попадают. Как определять «что вошло» (задачи, чьи файлы или коммиты изменились между предыдущим тегом и текущим, коммиты с префиксом `NNN-`, слияния PR), решить в «Анализе».

Правка `scripts/` и `.github/workflows/` — по явной просьбе владельца (эта задача и есть просьба, если план одобрен).

Зависит от: —
Среда: Linux или Windows.

## Критерии готовности
- Заметки о релизе vX.Y.Z перечисляют задачи, завершённые между предыдущим тегом и этим (номер и заголовок), независимо от папки задачи; заголовок — версия тега.
- Для первого тега (предыдущего нет) — все завершённые задачи.
- Скрипт можно запустить локально на двух тегах и получить тот же текст; способ описан в `docs/` (где описан релиз).
- `scripts/check.sh` проходит.

## Анализ
- Теги (на 2026-10-29): `v0.1.0`, `v0.1.1`, `v0.1.2`, `v0.1.3`, `v0.1.4`, все аннотированные и на одной линии истории (`v0.1.0` — предок `v0.1.4`). Между соседними тегами 0, 1, 1, 14 и 4 коммита. GitHub-релизы есть не у всех тегов: по `docs/knowledge/dev-environment.md` `v0.1.0`, `v0.1.1` и `v0.1.3` упали, первый удачный — `v0.1.2`.
- Сейчас: шаг «Release notes» в `.github/workflows/release.yml` отрезает патч (`v0.1.4` → `v0.1`) и, если есть `tasks/v0.1`, вызывает `scripts/release-notes.sh v0.1`. Скрипт берёт строки `tasks/DONE.md` с релизом `v0.1` и статусом `done` плюс файлы `tasks/v0.1/*.md` со статусом `done`. Задачи релиза `backlog` (после архивации — строки `NNN | backlog | done` в `DONE.md`) не попадают никогда. Заголовок — «Релиз v0.1», поэтому все v0.1.x получают один текст. Шаг `actions/checkout@v4` в задании `publish` — с глубиной по умолчанию (1 коммит, без тегов), то есть история и предыдущий тег в нём недоступны.
- Как задачи попадают в коммиты — не годится как источник: префиксы разнородны (`NNN-имя: …`, `Задачи 043, 044, …: done по одобрению`, `task 044: занята`, `task: новая задача backlog/…`, слияния PR без номера), один коммит может закрывать несколько задач. «Файлы задач, изменённые между тегами» тоже не годится: меняются и задачи в `todo`/`planned` (анализ, комментарии).
- Надёжный способ — разница множеств «завершённые задачи на теге». На любой ссылке `ref` множество `done(ref)` = номера из строк `tasks/DONE.md` (в версии `ref`) со статусом `done` ∪ номера файлов `tasks/**/NNN-*.md` (в версии `ref`) с `status: done` в заголовке. Архивация (`scripts/archive-tasks.sh`) удаляет файл, но пишет строку со статусом и заголовком в `DONE.md`, поэтому задача из множества не выпадает; папка задачи (релиз или `backlog`) не важна. Заголовок берётся из строки `# ` файла или из поля заголовка строки `DONE.md`.
- Проверено разовым подсчётом через `git show <тег>:…`: на каждом из пяти тегов `done` = 72 задачи (одно и то же множество), между `v0.1.0` и `v0.1.4` новых завершённых задач нет, и после `v0.1.4` по `HEAD` на 2026-10-29 тоже нет. То есть вся работа «последних недель» (Avalonia, хранилище, сессии) завершена до `v0.1.0`. По критериям заметки `v0.1.0` (первый тег) перечислили бы все 72, а `v0.1.1`–`v0.1.4` — пустой список. Это расходится с ожиданием из «Описания» (у `v0.1.0` релиза на GitHub нет) — вопрос в «Комментариях».
- Пересечения: `.github/workflows/release.yml` меняет и задача 100 (задание `maui-windows`), эта — задание `publish`. Правки в разных местах файла, порядок любой; вторая задача делает `git rebase origin/main`.

Решения по вопросам из «Комментариев» (переданы основным агентом 2026-10-29; одобрение плана подтверждает владелец):
- «Предыдущий тег» — предыдущий по версии стабильный тег вида `vЧИСЛО.ЧИСЛО.ЧИСЛО` (`git tag --sort=v:refname`), есть у него GitHub-релиз или нет. Имена строго соответствуют `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`: prerelease/build-суффиксы и ведущие нули исключены. Вторым аргументом можно задать другой существующий стабильный тег меньшей версии. Выбор не зависит от наличия GitHub-релиза и не обращается к GitHub API.
- Текст опубликованного релиза `v0.1.4` не переписывать. Новые заметки — для следующих тегов.
- В конце заметок — ссылка на сравнение коммитов (`…/compare/<пред>...<тег>`).
- Задачи `cancelled` в заметки не попадают. Тестов для скриптов в репозитории нет: «падающий тест» здесь — сценарий во временном git-репозитории (шаг 1), который сначала проваливается.

Имя тега проверяется строгим шаблоном `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` до любых git-команд, поэтому `HEAD`, SHA, ветка и строка, начинающаяся с `-`, до них не доходят. Тег разрешается только по полному имени `refs/tags/<имя>` (lightweight и annotated), сокращённое имя через ветку не разрешается. Предыдущий тег по умолчанию — строка непосредственно перед целевым в `git tag --sort=v:refname`; явный предыдущий должен быть меньше целевого в том же сортировании.
