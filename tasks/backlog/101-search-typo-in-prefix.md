# Поиск сессий: опечатка в недописанном слове

## Описание
Замечание владельца (2026-10-29, Android, скриншоты): в поиске по сессиям «watter» находит сессию с «water» в промпте, а «watte» — «Nothing found». Со стороны похоже, что поиск работает только по целым словам.

Что известно (`ImageGen.Core/Search/FuzzyMatcher.cs`, задача 079): слово запроса засчитывается, если слово текста с него начинается, содержит его или отличается от него на одну букву (расстояние Левенштейна ≤ 1, для слов от четырёх букв). Начала слов («wat») находятся. Опечатку же сравнивают только с целым словом: «watter» → «water» (расстояние 1) находится, а «watte» как недописанное «water» с опечаткой не находится (до целого слова расстояние 2, до начала «water» той же длины — тоже не 0). Пока пользователь печатает, последнее слово запроса почти всегда недописано, поэтому опечатка в нём ничего не находит.

Проверить в «Анализе» и вторую возможную причину: доходит ли до `SessionsPageModel.SearchText` текст, который клавиатура Android ещё набирает (подчёркнутый, с подсказками); если нет, поиск отстаёт на слово.

Зависит от: —
Среда: Linux или Windows (ядро; ручная проверка на Android).

## Критерии готовности
- Недописанное слово с одной опечаткой находит слово, которое с него «почти начинается»: «watte», «wate», «lighthuse» находят «water» и «lighthouse». Правило (например, расстояние до начала слова ≤ 1 для слов запроса от четырёх букв) описано в спецификации поиска.
- Порядок выдачи сохраняется: точное начало слова выше, чем совпадение с опечаткой; короткие слова (меньше четырёх букв) опечатки не прощают, чтобы не было шума.
- Тесты `FuzzyMatcher` на эти случаи и на отсутствие ложных совпадений.
- Выяснено и записано в «Отчёте», обновляется ли поиск на Android по набираемому (ещё не принятому клавиатурой) тексту; если нет — исправлено или вынесено в отдельную задачу.

## Анализ
- Текущее правило (`ImageGen.Core/Search/FuzzyMatcher.cs`, `ScoreWord`): слово текста начинается с токена → 3 очка; содержит токен → 2; токен от 4 букв и расстояние Левенштейна до **целого** слова ≤ 1 → 1. Каждый токен запроса обязан совпасть; счёт сессии в `SessionSearchService` = сумма очков × вес вида текста (Title 3, Prompt 2, Description 1), выдача по убыванию счёта.
- План задачи 079 уже предлагал «или с началом слова той же длины», но в код это не вошло (в «Отчёте» 079 об этом не сказано). Правило поиска нигде в `docs/specs/` не описано: в `docs/architecture.md` только строка про модуль `Search/`, ADR 0016 — про поиск по смыслу.
- Проверка примеров владельца по текущему коду (Левенштейн посчитан скриптом в черновике): «watter»→«water» = 1, находится; «watte»→«water» = 2, не находится — это и есть дефект; «wate» — точное начало «water», находится уже сейчас (3 очка); «lighthuse»→«lighthouse» = 1, находится уже сейчас (целое слово). Значит, из критериев не работает только опечатка в недописанном слове («watte», «lighthu» → «lighthouse»).
- Предлагаемое правило опечатки (токен `t` от 4 букв, слово `w`): совпадение с весом 1, если
  1) расстояние(t, w) ≤ 1 (как сейчас), или
  2) первые буквы `t` и `w` совпадают, и для некоторой длины начала `L` из {|t|−1, |t|, |t|+1}, `L < |w|`, расстояние(t, w[0..L)) ≤ 1.
  Других `L` проверять не нужно: при разнице длин больше 1 расстояние больше 1.
- Проверка правила на примерах: «watte» → «water» (начало «wate», 1) — да; «lighthu» → «lighthouse» («lighth»/«lightho», 1) — да; «brige» → «bridges» («bridge», 1) — да; «watte» → «watch» — нет (2); «house» → «hound» — нет (2); «watte» → «attempt» — без условия о первой букве было бы да («atte», 1), с ним — нет; «wot» (3 буквы) → «water» — нет (короткие токены опечаток не прощают); перестановки соседних букв («wtaer», «ocaen», «mountian») — нет: в Левенштейне перестановка стоит 2, так же, как сейчас для целых слов.
- Шум: для токена из 4 букв правило 2 находит любое слово с теми же первыми тремя буквами («cats» → «catalog», «rain» → «raise»). Это не больше того, что уже даёт запрос из трёх букв («cat»), и такие совпадения стоят ниже точного начала (1 против 3). Условие о первой букве отсекает совпадения со «сдвигом» на одну букву («watte» → «attempt»), которые для начала слова случаются чаще, чем для целого слова.
- Порядок выдачи: опечатка остаётся 1 очком, точное начало 3, подстрока 2 — критерий «точное начало выше» выполняется без изменения весов.
- Вторая возможная причина (набираемый текст клавиатуры Android): MAUI `Controls/SessionsListView.xaml` — `SearchBar` с `Text="{Binding SearchText, Mode=TwoWay}"`; `SessionsPageModel.OnSearchTextChanged` на каждое изменение отменяет прошлый поиск и запускает новый через 250 мс (`SearchDebounce`). Передаёт ли Android-реализация `SearchBar` в `Text` ещё не принятый (подчёркнутый) текст, по коду проекта не видно — неизвестно; проверяется только на устройстве или эмуляторе. Симптом владельца («watte» → «Nothing found») полностью объясняется правилом выше и от этого не зависит. Avalonia: `TextBox` с той же двусторонней привязкой.
- Пересечения: 089 (`SessionsPageModel`) — эта задача его не меняет (если понадобится правка набираемого текста, она уходит в отдельную задачу). С другими задачами 088–100 файлов нет.
