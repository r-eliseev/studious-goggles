### Partial 20-repeat diagnosis (task 274)

The cancelled [run 43296911876](https://github.com/r-eliseev/studious-goggles/actions/runs/43296911876) uploaded artifacts for 14 of 20 Avalonia repetitions. Runs 09 and 11 were marked failed because the newly collected host crash reports were `UsageTrackingAgent` reports, not reports for the Avalonia app. In run 14, `summary.json` says `aliveAfter30s=false`, `crashReports=0`, `exitedAtSeconds=5`; however, `process-timeline.txt` shows no process through the 45-second sample and a live process at 50 seconds, while the app log records startup at `2026-11-12 21:48:43.500`. The simulator log records the process receiving SIGTERM during cleanup at `21:49:46.771`; there is no app crash report. This points to delayed process startup and overly broad host crash-report counting as explanations for the smoke failure, but does not establish why startup was delayed. The 20-run result is incomplete and must not be treated as the final failure rate.

The amended smoke artifact separates `crash-reports/app/` from `crash-reports/other/`. `summary.json` reports `crashReports` for the app executable only, `otherCrashReports` for unrelated simulator/host processes, `firstSeenAtSeconds` for the first launchctl sample containing the app, and `exitedAtSeconds` only when a previously seen app disappears. `null` for `firstSeenAtSeconds` means the app was never seen during the 60-second sampling window; this is a launch delay/timeout, not evidence of an exit. `process-timeline.txt` records actual monotonic elapsed seconds, UTC timestamps, running state, the launchctl line and probe status. Repeated runs print progress and are stored under `reports/ios-smoke/<app>/run-NN/`.

Task 274's first complete 20-repeat dispatch, [run 43825048969](https://github.com/r-eliseev/studious-goggles/actions/runs/43825048969), showed one MAUI smoke failure and three Avalonia smoke failures. The first run used loop counters as elapsed seconds, and slow simulator commands made those labels inaccurate: the app log in MAUI run 05 begins about a minute after launch, and the app logs in Avalonia runs 09 and 13 begin after 30 seconds. Those counts are preliminary and must not be treated as the final measured failure rate. Avalonia run 18 never produced an app log or process; simulator logs show installation/placeholder activity around the smoke window. The only captured SIGTERM for the delayed runs occurs during smoke cleanup, so the evidence points to delayed or missing simulator launches rather than an app that exits after starting.

The first dispatch after the monotonic-timeline change, [run 44039721757](https://github.com/r-eliseev/studious-goggles/actions/runs/44039721757), did not reach the smoke because both iOS builds failed during .NET workload installation: the .NET 11.0.100 Emscripten manifest conflicts with the .NET 10.0.110 manifest. Builds using the diagnostic Xcode 26.4.1 / .NET 10.0.203 option passed in [run 44040174321](https://github.com/r-eliseev/studious-goggles/actions/runs/44040174321). That complete 20-repeat run reported 11/20 MAUI and 9/20 Avalonia smoke failures, but these are not confirmed app-exit rates: most failed samples were `launchctl list` timeouts, and no app crash reports were found. In MAUI run 09, for example, the app log shows startup at 08:32:01Z and the launch log gives PID 42190, while the first successful process query came at 08:32:37Z. Avalonia run 05 likewise logged startup at 08:08:10Z, while its launchctl probes timed out. Some other runs had no process or app log within the 60-second window; those remain actual launch failures or unresolved launch delays. The evidence points to simulator launch/query contention on the hosted runner, with the current launchctl observer unable to distinguish slow launch from a query timeout. A scheduled `main` run [44067539154](https://github.com/r-eliseev/studious-goggles/actions/runs/44067539154) later passed both iOS builds and both one-run smoke jobs; this confirms the workload conflict did not reproduce there, but does not replace the 20-repeat diagnostic.

Task 285 replaces the proposed follow-up with PID-based liveness. The smoke reads the bundle-specific `<bundle id>: <pid>` line from `launch.log` as it is written and checks that simulator process on the macOS host with `ps -p <pid>` at each sample. `launchctl list` remains diagnostic evidence in `process-timeline.txt`; its success or timeout no longer decides whether the app is alive. `summary.json` includes the observed `pid` (or `null`) and `livenessSource: "pid"`. If no PID is printed by the 30-second sample, `aliveAfter30s` is false.

The two corrected 20-repeat `workflow_dispatch` runs are [44194058365](https://github.com/r-eliseev/studious-goggles/actions/runs/44194058365) and [44475603240](https://github.com/r-eliseev/studious-goggles/actions/runs/44475603240), both using the Xcode 26.4.1 diagnostic toolchain. Both apps completed all 20 repetitions in both runs. Run 44194058365 recorded 1/20 MAUI and 4/20 Avalonia late or missing launches; run 44475603240 recorded 3/20 MAUI and 0/20 Avalonia. Across these 200 launches, no failure showed a previously observed PID exit and the failed summaries had zero app crash reports. In the second run, MAUI run 11 never reported a PID in the observation window; runs 14 and 17 first reported their PIDs at 41 seconds, after the 30-second acceptance sample. The process timelines and copied app logs for both runs are retained locally under `tmp/task-285/dispatch-<run>-{maui,avalonia}/`. These results establish that the liveness observer now measures the launched process independently of `launchctl`, while slow or missing simulator launches remain intermittent, especially for MAUI. They do not establish an app-side process exit; task 285 should be reviewed with a proposed investigation of simulator/app startup timing rather than an app code change.

## Avalonia iOS in the simulator: what prevented the launch (2026-11-07)

- **`-p:TrimMode=copy` breaks the `AppDelegate` mapping.** The runtime creates the generic `Avalonia.iOS.AvaloniaAppDelegate\`1`: with the default registrar this is a `MemberAccessException`, with the static one "because the type is generic". At the same time `_OBJC_CLASS_$_AppDelegate` is present in the binary (`llvm-nm`). Without `TrimMode=copy` everything works. The linker warnings for which the flag was added must not be errors: `-p:ILLinkTreatWarningsAsErrors=false`, because `Directory.Build.props` enables `TreatWarningsAsErrors`.
- **`AvaloniaXamlLoader.Load(this)` in the iOS head's `MainView` left `PageHost` empty.** `InitializeComponent()` helps.
- **Links to resources from the desktop project.** `Link` must include `Fonts/`: `Assets/Fonts/%(RecursiveDir)%(Filename)%(Extension)`. `%(RecursiveDir)` is only the part of the path after `**`.
- **The cause of a crash is shown by the `launch.log` of the smoke artifact.** On a `SIGABRT` from an unhandled managed exception there is no crash report (`crashReports=0`).
- **Checking the process at 15 s is unreliable.** MAUI was sometimes still on the splash screen at 15 s, so the check at 30 s decides.
- **`launchctl list | grep -q` under `pipefail` fails falsely.** `grep -q` exits on the first match, `simctl spawn` gets `SIGPIPE` ("signal 13: Broken pipe"), and the check considers a live app dead (run 42409893841). The output is saved to a variable first. Verified by run [42412288939](https://github.com/r-eliseev/studious-goggles/actions/runs/42412288939): both iOS smokes are green.
