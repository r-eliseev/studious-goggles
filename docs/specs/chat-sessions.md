# Specification: sessions and chat with an assistant

Status: accepted by the owner 2026-10-27 (answers to questions in the session, see `docs/history.md`)
Extends `docs/specs/image-client.md`: it changes the main working scenario. The catalog, parameters, spending, errors and moderation from the main specification stay in force.

## Idea
The user works as in ChatGPT: writes in the chat what they want to draw, the system draws and shows the result. The user says what to change, the system changes the prompt and sends it to generation again. The assistant may ask clarifying questions. The list of models for generation is a session setting and can be changed at any time. For example, first practice on the cheapest model, then run the same prompt on all the needed models in one run, several times with different seeds.

## Terms
- **Session**: one chat. Stores the message history, the settings and all runs. The analog of a "conversation" in ChatGPT.
- **Message**: a line of the user or the assistant in the session.
- **Assistant**: an LLM through OpenRouter chat completions. It answers with text (an answer or a clarifying question) or calls `generate_images` / the `generate_video` available in the session with a ready prompt.
- **Run**: one generation launch for one prompt. It creates a generation for every "model × seed" pair. Replaces the term "run group" of the main specification.
- **Generation**: one picture from one model with one seed. Stores the exact prompt, model and seed, so it can be repeated or minimally changed.
- **Session settings**: the list of models for generation, the number of runs per model, the assistant model.

## Behavior
### S1. Sessions
- S1.1 A session list, as in ChatGPT: newest on top, create a new one, open, delete with confirmation.
- S1.4 Settings offers deleting the whole history with confirmation. Sessions, related records and media files are deleted; after the operation an open chat returns to the list of empty sessions. Provider keys, settings and the spending ledger are kept.
- S1.2 Session title: the first 40 characters of the user's first message. The user can rename the session (up to 40 characters, an empty title is not accepted); renaming does not move the session up the list. A list row shows the time of the last change and the number of runs ("… · 3 runs").
- S1.3 A new session gets the default settings: one model `black-forest-labs/flux.2-klein-4b`, one run per model and the assistant model chosen in Settings (originally `anthropic/claude-haiku-5.5` at OpenRouter). The assistant model setting applies only to new sessions. The assistant model is chosen among the tool-capable models of all configured chat providers; the catalogs of OpenAI-compatible and Anthropic-compatible providers are set through `chatModels` in `providers.json` (ADR 0024). The saved model is visible in the chat.
- S1.4 Session search has separate "Words" and "Meaning" modes; the results of the modes are not mixed. "Words" searches titles, prompts and picture descriptions (weights 3, 2 and 1). The query is split into words, every query word must be found. A word counts if a text word starts with it (3 points), contains it (2) or — for query words of four letters or more — differs from a text word, or from the beginning of a text word with the same first letter, by one letter (1 point). Swapping adjacent letters counts as two errors and is not forgiven. Results go by descending score, one row per session. "Meaning" requires a separate switch in Settings and a finished indexing. The user chooses an embedding model from OpenRouter's embedding catalog; the default is `baai/bge-m3`. Before enabling or changing the model, the UI shows a source/token/cost estimate when the catalog provides a price. Images and provider URLs are not included in the embedding request. The index is stored locally in SQLite; after a text changes it is updated, after a session is deleted its vectors are deleted. Changing the model stops indexing, clears old vectors, saves the selection and starts indexing again when Meaning is enabled; while indexing, search uses only vectors for the selected model. A retired or unavailable model makes Meaning unavailable while Words keeps working locally. Without a key, network or a ready index Meaning is unavailable, while Words keeps working locally. In Meaning, queries shorter than 3 characters are not sent; the search waits 400 ms after input and shows up to 20 sessions by cosine similarity. Turning Meaning off deletes the local index.
- If more than 10 000 texts are found, Meaning indexes the 10 000 most recently changed ones and shows a warning; the rest stay available in Words. For Meaning the query is limited to 8 192 characters.

### S2. Chat and assistant
- S2.1 The user writes a message; the assistant receives the system prompt, the current session prompt (the prompt of the last run), a summary of the old part of the history if there is one, and the session messages selected by the model's context budget; the user's current message is passed verbatim.
- S2.2 The assistant decides itself: answer or ask back (ordinary text), call `generate_images` for a picture, or, if video models are selected in the session and the user explicitly asks for a video/clip/animation, call `generate_video` with a full prompt in English. The video tool takes an optional id of a successful picture of this session as the first frame. The generation starts immediately, without confirmation (the owner's decision); if the answer contains both tools, the first one in order is executed and a warning is logged.
- S2.3 The prompt sent to generation is always visible in the chat in the run block and on every card. There is no hidden substitution (F9.4 of the main specification). The prompt is shown once — in the run block; the assistant's text, if it came with the call, is a separate assistant message, and if there was no text, there is no message.
- S2.4 The assistant can look at the pictures of the last run if the assistant model accepts pictures as input (optional in the skeleton, task `tasks/backlog/017-assistant-vision.md`).
- S2.5 An assistant error (no connection, a free model limit, an invalid key) is shown in the chat as a separate message with the reason; the user's message is not lost. The "Try again" button exists only on the last message if it is an assistant error, and does not work while an answer is in progress: it resends the user's last message (with its pictures) to the assistant without adding a new user message; the error stays in the history and does not go into the request.
- S2.6 Context: the history budget is counted from the model's context with a reserve for the answer, the constant prompt, pictures and the summary; the latest messages are sent verbatim, and errors are excluded. The token estimate is corrected by `usage.prompt_tokens` in memory per model. If the history exceeds 80% of the budget and there are at least 10 messages older than the latest 20, the assistant folds them into a background summary of up to 300 words in the conversation's language. The request carries the system prompt, the current session prompt, the previous summary and the messages that fit. A failure to create a summary is only logged; the previous summary and the budget selection of the history are used. In the feed, after the covered message, there is a thin divider and "Show summary" with the text, model and price. If the request does not fit, first the pictures of the last run are excluded, then extra attachments; if needed, old messages are shortened for the request without changing the database. ADR 0015; implemented in tasks 082–084 and 110; code `ImageGen.Core/Context/*`, `AssistantService`, `ConversationSummaryService`, `ConversationSummaryRepository` and the Chat templates of both heads.
- S2.7 When a session opens and when rows are added, the feed scrolls to the last one. While the user follows the end, a card update and a change of the feed size (for example, with the keyboard) also keep the bottom edge of the last row visible. Scrolling up pauses following until the user returns to the end.

### S3. Runs and generations
- S3.1 A run takes the models and the number of runs N from the session settings at the moment of launch. Changing the settings does not touch runs already started.
- S3.2 Seeds: N random seeds from 0 to 2147483647 are chosen for a run, the same for all models of the run (a fair comparison). Generations in a run: models × N.
- S3.3 If a model does not accept a seed (per the catalog), the seed is not sent, and the generation is marked "seed not supported": it cannot be repeated exactly.
- S3.4 Generations run in parallel and independently; a failure of one does not affect the others. All image providers use the shared submit → persist handle → poll → terminal lifecycle. At most four jobs per provider id are tracked locally at the same time, and different providers do not block each other. A provider slot is held until the terminal status, including restored watchers. When a session is deleted the request is cancelled; a local synchronous transport is tracked until the terminal status. If a remote cancel failed, the limit describes only the locally tracked work.
- S3.5 Generation states: queued, running, done, failed, cancelled, filtered (the common model of the main specification).
- S3.5.1 Cancellation of an active generation can be requested separately or for the whole run. `Cancelled` and `NotFound` end local tracking and save "cancelled" if a terminal result is not saved yet. `AlreadyCompleted` means the provider finished before the cancellation: local tracking continues, the result and a possible price are saved the ordinary way, and the cancellation request returns "not active". `CancellationRequested` keeps the job active, continues tracking and shows that the provider may still finish it and charge. A request error is shown as a failed cancellation; repeated taps do not send a second remote request.
- S3.5.2 If a result was recorded before the cancellation, it stays unchanged. If the cancellation ended the local job before the result came, the late picture is not saved.
- S3.5.3 The time of the `CancellationRequested` confirmation is stored with the generation, including its later successful result and recovery after a restart.
- S3.6 A picture is saved to a file and the DB immediately when received, before it is shown.
- S3.7 A generation stores: the exact prompt, the model, the seed and the "seed applied" flag, the status, the file path, the file type, the actual price (`usage.cost`), the error, the creation and finish time.
- S3.9 The summary above the run's cards shows the number of models, runs per model, finished generations and the sum of known prices; it is updated on every change of a card's status or price.
- S3.10 A successful card with a file shows the actual width and height of the raster and the reduced aspect ratio (for example, `1200×800 px · 3:2`); the dimensions are read asynchronously from the saved file, do not affect the status and are available to the screen reader. If the file is missing or unreadable, the line is hidden.
- S3.8 Generations that did not finish before the app was closed are marked with the error "Interrupted" on the next start, except queued provider jobs with a restorable handle. A fal generation with a saved handle resumes without a repeated submit: the job is polled again until the end. In-memory handles of synchronous transports do not survive a restart, so such generations are marked "Interrupted" without a repeated paid request. If the job's provider is no longer in the configuration, the generation ends with the error "ModelUnavailable" instead of hanging. The number of rows finished during recovery includes both those finished because of a missing provider and those marked "Interrupted".

### S4. Generation actions
- S4.1 "Repeat": a new run of one generation: the same prompt, the same model, the same seed.
- S4.2 "New seed": the same prompt and model, a new random seed.
- S4.3 "Edit": the exact prompt opens for manual editing (without the assistant); after confirmation a run of one generation starts: the same model, the same seed, the new prompt.
- S4.4 Runs started by actions are shown in the chat the same way as the assistant's runs.
- S4.5 "Other model…": on a filtered card and on an error — the model picker. On top, "Used in this session" — image models already used in this session (except the model of this card), by last use; below, a collapsed "All models" with the whole catalog and search (the search filters only "All models"). The choice starts a run of one generation: the same prompt, the same seed, the chosen model; if the model does not accept a seed, the seed is not sent (as in S3.3). The run is marked with the origin `RunOrigin.OtherModel`.
- If the source generation contains reference images, `Other model…` starts only when the chosen model supports all these images per `input_references`; on incompatibility the UI shows an error and stays in the model picker. Images are never dropped silently.
- S4.6 "Copy prompt": on all finished cards — the exact prompt of the generation is put on the clipboard.
- S4.7 "Details": only on an error — a window with the original error text (`Generation.ErrorMessage`); the card keeps a short reason.
- S4.8 "Save image": on a done card. Desktop — the system "Save as" dialog (default name `imagegen-<first 8 characters of id>.<extension>`); Android 10+ — to the gallery (`Pictures/ImageGen`, no permission); Android 9 and lower — to the same folder with the write permission; iOS — to Photos (with an "add only" access request). After saving the card shows "Saved"; a denied access shows a message.

### S5. Session settings
- S5.1 The session models screen: the list of OpenRouter image models with search and checkboxes, the number of runs per model from 1 to 10.
- S5.2 The list can be changed at any time; the new values apply to the next run.
- S5.3 The session models screen on a page and in the side panel has the tabs "Image models" (the default: the number of runs, the counter of selected models and the list with checkboxes) and "Assistant model" (a single-choice list); each tab has its own scrolling. Search and "Refresh" are above the tabs, the search filters both lists. The shared "Save" and "Cancel" are pinned below the tabs outside the scrolling and stay visible with a long list.
- S5.5 The models on both tabs are grouped by vendor. The vendor is derived from the model id prefix before `/` after removing leading `~`; for fal the prefix is `fal-ai`, ids without `/` and other unknown ones go to "Other". The vendor name is the most frequent label before `: ` among models with this prefix; on a tie the first one alphabetically, case-insensitive, and if there is no label — the prefix itself. Groups with the same label are merged case-insensitively; models of different providers may get into one group. Groups are ordered by name, "Other" is last; models inside — by name and then by provider id. The header shows the name and the number of matches; for pictures also the number of selected models. On opening, the group with the selected model is expanded. With a non-empty search only the matching groups are shown and expanded; expansion changes during a search are temporary, after clearing the saved state returns. "Refresh" does not reset the state. Collapsed groups do not create model rows until expanded.
- S5.6 An image model row shows the price only for `output_image`. The source of OpenRouter prices is `images/models/{id}/endpoints`; on `Refresh` the catalog and prices are requested again, the cache is used on reopening. The first available unit is shown in the order image, megapixel, token, request; token is converted to a price per million output tokens. Several prices of one unit are shown as a range. Examples: "$0.014 / MP", "$0.008–0.036 / image", "$40.00 / 1M output tokens". If there is no output price, "price unknown" is shown; for fal the price is currently shown as unknown.
- S5.7 Rows of image models and assistant models show the provider's display name together with its id; identical model names of different providers must be distinguishable. `ModelRef` and the saved choice still use the provider id + model id pair.

### S6. Appearance (the owner's decision of 2026-10-28, ADR 0014)
- S6.1 The "Style" setting: Quiet (A), Gallery (B), Notebook (C); Quiet by default (an assumption, ADR 0014). The styles differ in colors, fonts, radii and five markup variants (`docs/design/tokens.json`); the layout, the set of elements and the texts are the same.
- S6.2 The "Theme" setting: as in the system (the default), light, dark.
- S6.3 Both settings are on the settings screen, apply to the whole app, apply immediately and are kept between starts.
- S6.4 The settings screen is called "Settings" (Routes.Settings). The entry is the gear icon at the bottom of the session list. For each configured provider the display name, the key state (only the last four characters or Not connected), Change and Remove are shown. Here the assistant model for new sessions is chosen from the available chat models; the value is stored in `defaults.json`, and a corrupted file is replaced with the built-in value `anthropic/claude-haiku-5.5` at OpenRouter. First run requires the key of the provider of the chosen assistant model; on the key screen you can choose another chat provider and then a model from its catalog. Deleting a key requires confirmation, deletes only the secret of the chosen provider and keeps Settings open; deleting the key of the assistant model leads to a repeated request the next time Sessions opens. "Open folder" is shown only on the desktop (IFolderLauncher.IsSupported).

## Walking skeleton (release v0.1)
Goal: all systems work end to end on one provider, without polishing.
- Included: only OpenRouter; only MAUI, launched and checked on Windows, Android is only built in CI; entering the key on first launch (the key in SecureStorage); the session list; the chat with the assistant; the session models screen; N runs per model with shared seeds; a parallel run; statuses; the `usage.cost` price on the card; saving sessions, messages, runs, generations and the catalog cache in SQLite and pictures in files; the S4 actions; the "Interrupted" mark at startup; the UI in English through `.resx` (Russian is added later).
- Not included: fal and Together AI, Web and Docker, the spending screen and the price estimate before the run, comparison, the gallery as a separate section (generations just lie in the DB), generation parameters (aspect ratio, resolution), references and Img2Img, Img2Text, uploading your own pictures to the chat, themes, the settings screen, changing the assistant model from the UI.

## Keyboard (task 073)
The main modifier is Cmd on macOS, Ctrl on Windows and Linux.

| Shortcut | Action | Where |
|---|---|---|
| Cmd/Ctrl+N | new session | all screens (window, File menu) |
| Cmd/Ctrl+, | settings | all screens (window, File menu) |
| Cmd/Ctrl+F | session search (focus in the search field) | all screens (Find menu) |
| R | repeat the generation | the focused card |
| Shift+R | new seed | the focused card |
| E | edit the prompt | the focused card |
| Cmd/Ctrl+S | save the picture | the focused card |
| Cmd/Ctrl+C | copy the prompt | the focused card |

Letter shortcuts work only in a card, so text in the input field is not affected. In MAUI the letter shortcuts have no accelerators (the "Card" menu items). The macOS menu and the MAUI accelerators on Windows and Mac are not verified (`docs/knowledge/maui.md`).
