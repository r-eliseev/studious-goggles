# 0005. OpenRouter как задание в фоне и общий опрос статуса

Статус: принято
Допустимые статусы: предложено, принято, заменено на NNNN, отклонено
Дата: 2026-10-28

Уточняет ADR 0003 (раздел «Решение», handle OpenRouter и `CancelAsync`).

## Контекст
ADR 0003 подгонял синхронный OpenRouter (`POST /api/v1/images` держит соединение до готовой картинки) под submit/watch так: handle «содержит уже готовый ответ». Тогда `SubmitAsync` у OpenRouter ждёт всю генерацию, а у fal и Replicate возвращается сразу. Оркестратор вынужден различать провайдеров, задание OpenRouter нельзя отменить, а состояния «в очереди» и «идёт» у него условные. Владелец (2026-10-28): генерация OpenRouter запускается в отдельной задаче, чтобы не блокировать UI и полностью повторять поведение остальных провайдеров, а статус получается полноценным опросом.

## Решение
1. **Задание OpenRouter в фоне.** `SubmitAsync` у OpenRouter не ждёт ответа. Он регистрирует задание в памяти процесса (`OpenRouterJobRunner`, singleton), запускает HTTP-запрос в отдельной задаче (`Task.Run`) со своим `CancellationTokenSource` и сразу возвращает handle: id провайдера и локальный id задания. Байтов в handle нет.
2. **Состояния задания в памяти:** «в очереди» (ждёт слот; локальная позиция известна) → «идёт» (HTTP-запрос отправлен) → «готово» (байты, тип, цена) / «ошибка» (`ErrorKind`, текст) / «отфильтровано» (отказ модерации) / «отменено». Слоты ограничивает семафор провайдера (как сейчас `MaxParallelGenerations = 4`).
3. **Общий опрос для всех провайдеров.** Каждый провайдер даёт одну операцию чтения состояния: `PollAsync(handle) → JobUpdate`. У fal и Replicate это HTTP-запрос статуса, у OpenRouter — чтение из `OpenRouterJobRunner`. Цикл опроса один на всех (`ProviderJobPoller`): нарастающий интервал, событие при каждой смене состояния, конец на конечном состоянии. `WatchAsync` из ADR 0003 строится из `PollAsync` этим циклом. Интервалы — у провайдера в конфиге (для OpenRouter короткие: опрос локальный).
4. **Результат.** «Готово» у OpenRouter отдаёт байты из памяти; оркестратор сохраняет файл и запись до события (как у всех). После выдачи конечного состояния задание удаляется из памяти; неполученные конечные задания удаляются по сроку.
5. **Отмена.** `CancelAsync` у OpenRouter отменяет HTTP-запрос через `CancellationTokenSource`: задание переходит в «отменено». Списывает ли OpenRouter деньги за прерванный запрос — неизвестно; на карточке цена такого задания «неизвестно».
6. **Перезапуск.** Handle сохраняется в БД сразу после `SubmitAsync`, как у всех. Задание в памяти не переживает перезапуск: `PollAsync` с неизвестным локальным id возвращает «ошибка, `ErrorKind.Interrupted`». Отдельной ветки для OpenRouter в восстановлении нет.

## Альтернативы
- **Handle с готовым ответом (исходный текст ADR 0003).** Проще, но оркестратор различает провайдеров, нет отмены и честных состояний.
- **Только событие завершения, без опроса.** Меньше работы для OpenRouter, но два механизма в оркестраторе (событие для одних, опрос для других). Владелец выбрал одинаковый опрос.
- **Персистентная очередь OpenRouter в БД.** Восстановление после перезапуска всё равно невозможно: синхронный HTTP-запрос не продолжить.

## Последствия
Проще: `GenerationService` одинаково работает со всеми провайдерами (submit → сохранить handle → опрос → сохранить результат → событие), UI никогда не ждёт провайдера, у OpenRouter появляются отмена и позиция в локальной очереди. Сложнее: у OpenRouter своё хранилище заданий в памяти и уборка завершённых; байты картинки живут в памяти до опроса. Реализуется задачей 025 вместе с контрактом ADR 0003.
