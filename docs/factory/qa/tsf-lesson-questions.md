## A. Что такое liquid software, liquid factory и как фабрика подстраивается (`liquid-software`, `liquid-factory`, `adaptation`)

- **`liquid-software`.** Устоявшегося определения нет [ext]. Есть три разных смысла: (1) академический, Liquid Software Manifesto (Taivalsaari, 2014): приложения и данные свободно переходят между устройствами; (2) «interfaces negotiated at runtime between agents» (arXiv 2601.21993, 2026): интерфейсы, которые агенты согласуют на лету; (3) блоговый, эпохи агентов: Flavio Copes, "Liquid Software: When Software Can Change Its Shape" и Thingelstad, "software is liquid": софт, который сознательно сделан понятным, «своим» и переформируемым; «liquid» значит «адаптируемый», а не «нестабильный»; автоматически это не происходит, агенты ошибаются. Видео использует третий смысл [`tsf-lesson`, `liquid-software`].
- **`liquid-factory`.** Внешнего определения «liquid software factory» нет [ext]. По `tsf-lesson` фабрика «жидкая», потому что [mine]: она поставляется пустой шаблоном (`empty-factory`); специализируется планом-промптом (`configure-step`); агент может менять её настройки и интерфейс так же, как человек (`plan-from-files`); всё в ней видно и измеримо (`tool-summaries`, `subagent-budgets`, `versioned-stage-templates`). Рабочее определение: *конфигурация фабрики это данные, которые агент может переписать по твоей просьбе*.
- **`adaptation`.** Источник показывает адаптацию только **по команде человека**: configure-план на ~150 строк и разовые правки через паритет доступа [`tsf-lesson`]. Автоматической адаптации «по ходу разработки» в нём нет, хотя заявлено «it keeps changing shape as you learn». Автоматический механизм есть в `warp-talk`: skill loop, наблюдатель видит правки людей и улучшает навык [`warp-talk`, `skill-loop`]. [mine] Адаптивная фабрика = жидкость (менять дёшево) + петля (есть сигнал, что менять). Источник 01 даёт первое, 02 даёт второе.

## B. Мета-оптимизация и «в петле / рядом / вне» (`meta-optimization-how`, `loop-modes`)

- **`loop-modes`.** Термины из статьи IEEE 2016 про контурное управление, единого стандарта для агентов нет [ext]. Ядро везде одинаково: *in* = человек одобряет или направляет действия; *on* = человек наблюдает и может вмешаться; *out* = агент действует без человека. «Near the loop» из `tsf-lesson` близок к *on*, но с важным оттенком [`tsf-lesson`]: агент **сам** останавливается только на точке решения и приносит результат, то есть эскалация по событиям, а не непрерывный надзор.
  Предостережения [ext]: слово «loop» двусмысленно, пока не сказано, какая именно петля; режим *on* может выродиться в *out* (внимание человека гаснет); *in* не масштабируется на много агентов (IDC); есть более тонкая схема LoopRails, 7 уровней L0-L6 **на действие**, а не на систему.
  [mine] Для нас вывод: задавать режим для каждого типа действия (одобрить спеку, слить, выпустить), а не для фабрики в целом. [исправлено владельцем 2026-11-17] Задачу проходит агент-планировщик (пишет план и ревьюит результат), а не человек; одобрение планов дано заранее постоянной инструкцией (`docs/status.md`, ADR 0033). Значит по задачам фабрика уже ближе к *near*, чем я первоначально написал; человек остаётся на постоянных инструкциях, целях продукта и эскалациях.
- **`meta-optimization-how`.** Метода в `tsf-lesson` нет, только тезис [`tsf-lesson`, `meta-optimization`]. [mine] Из 01 и 02 складывается такой метод: измерить (доля человеческого времени и токенов на единицу выпуска, `outbox-stays-open`) → найти, где человек ждёт или переделывает → заменить ручной шаг автоматикой с воротами или переместить человека на точку решения → повторить. Кандидаты метрик для нас: минуты владельца на смерженную задачу, число возвратов, время ожидания одобрения.

## C. Как работает agentic engineering (`agentic-engineering`)

Независимого определения я не нашёл: поиск выдал в основном курсы [ext]. По источникам [`tsf-lesson`, `warp-talk`]: инженерия смещается с писания кода на проектирование, ограничение и измерение систем агентов; человек остаётся там, где нужны вкус и суждение (`human-taste`). Общее ядро двух источников: **строишь систему, которая строит продукт**. Всё остальное (практики, роли, верификация) требует независимых источников.

Ближайшее: видео IndyDevDan "My Super Simple Software Factory (For Agentic Engineers)" (сторонний пересказ: ADW, цепочки специализированных агентов с обычным Python между фазами) и его курс «Tactical Agentic Coding» (по сторонней карточке: 14 модулей, 6.5 ч, AFK-агенты, 12 leverage points, оркестрация; не проверено). **Что автор урока 2 это IndyDevDan, пока гипотеза**, основанная на близости терминов; страницу автора (agenticengineer.com) проверить не удалось, хост вне разрешённой сети.
- **`tsf-skill`.** Конкретный TSF-скилл (`/tsf init`, `configure`) не найден [ext]. Публичные аналоги того же паттерна (один скилл, который ставит фабрику в репозиторий): riquenandez/ts-factory (порт Super Simple Software Factory на Bun/TypeScript, один Claude Code skill плюс установочный скрипт), dwightfowler-tema/factory-setup (скилл с режимами init/repair/upgrade), PaddyMc/software-factory (`factory init`), juan-campuzano/minifactory (`init` и plugin-шаги), geut/factory-skills (бюджетная фабрика). Подробный разбор каждого (ссылка, описание, компоненты, как работает): `docs/factory/research/factory-kits-readme-level.md`. Уточнение: `ts-factory` это порт SSSF (disler/super-simple-software-factory, подпись на странице IndyDevDan), а `factory-setup` по README происходит из репозитория ZazenCodes, который найти не удалось.

## Что из этого следует для концепции [mine]

1. «Жидкость» это свойство конфигурации (данные, которые агент может менять), а не волшебство; без петли обратной связи она меняется только по команде человека.
2. Режим участия человека задавать **по действиям**, и именно здесь «near the loop» становится измеримым.
3. Метрики (человеческое время, токены, возвраты) это первый шаг мета-оптимизации, без них она остаётся лозунгом.
4. Скилл `init`/`configure` как отделимая «пустая фабрика» это наш пробел, и аналоги из `tsf-skill` можно изучить как прототипы.
