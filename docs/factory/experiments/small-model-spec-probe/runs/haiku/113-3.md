**ASSUMPTIONS**

1. Plan step 2 assumes the `generation` table's primary key is the generation id, so the "more than one row" branch is unreachable. The spec states this but does not show it, and a non-unique key would make the `count != 1` guard behave differently.
2. The plan assumes task 111 is merged and that the `CapturingLogger` extensions from 110 either exist in main or can be added without breaking current tests. The spec hedges with "если они уже в main", so the starting state is unknown.
3. The sentinel-based log check assumes that real provider and SQLite exception messages, which can include URLs or request details, never reach operational logs. The spec only tests a synthetic sentinel, not real exception formats.

**QUESTIONS**

1. The spec requires that no event is published when the update fails, but it does not say what the UI should see for a real failure. Is a silent stall in the last persisted status acceptable, or should a failure event or status exist? This is the central gap between "no false terminal event" and the goal of UI/DB consistency.
2. Zero affected rows is always marked non-transient, but a generation deleted concurrently, for example by a user action, is a plausible zero-row case. Should that be treated as a distinct, expected outcome rather than a storage failure?
3. The spec does not say what happens to the persisted row when the Running transition fails. The row seems to stay in Pending/Queued, and it is unclear who reconciles it on restart or whether 122 covers it.
4. The spec says own-token cancellation (108) is not an Error, but it does not define how to tell own cancellation from an `OperationCanceledException` thrown by an HTTP timeout, which is a `TaskCanceledException` subclass. Which token is "own" when the host shutdown token is linked?

**RISKS**

1. In the `Launch` catch, if the logger throws (for example, the Debug sink fails), the exception escapes, the Task faults, and the slot may not be released. Slot removal needs to be in a `finally` that does not depend on logging succeeding.
2. Making `WhenIdleAsync` complete without fault can hide real failures from any test or caller that only awaits it. The Error log then becomes the only signal, so tests must assert on it explicitly.
3. The boundary test change for 106 stops a second terminal persistence after a file-save failure. This leaves the DB and file out of step until 122 lands, and a re-run could produce duplicate outputs.
4. Other `IRunRepository` substitutes in tests can still return success without writing a row. The spec does not require auditing them, so the new strict contract is not enforced by those tests.
