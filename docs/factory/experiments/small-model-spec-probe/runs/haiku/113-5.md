**ASSUMPTIONS**

1. The plan assumes the 111 work already left `CapturingLogger` with structured state and an `Entries` list that can be extended without breaking existing tests. The spec does not describe that API, so the test step depends on an unverified baseline.
2. The plan assumes the project's logging policy exists, that it defines what "Debug" means for exception detail, and that generation, session, and provider ids are safe to log at Error level. The spec refers to this policy but does not state it.

**QUESTIONS**

3. The criteria require an exception when affected rows is greater than 1, but step 2 says that case cannot be tested. Is code review the only acceptance check for that branch?
4. When `Launch` observes an unexpected failure, the spec forbids a second Failed write. What state does the DB row keep, and who reconciles a generation left as Running with no entry in `_running`: task 122, task 125, or a startup check?
5. The spec says no event is published on failure. Should the UI learn about the failure at all, or should it stay in the running state until restart?
6. A zero-row UPDATE can also happen when a generation is deleted or cancelled by the user (108). Should that still be a `StorageWriteException` and an operational Error, or should it be a benign no-op?
7. The criteria mention failure of the intermediate Running status, but step 5 describes only the terminal path. Does the Running transition also go through `SaveAndNotifyAsync`, and does it publish an event and log once?
8. Real SQLite failures such as busy or locked database, or I/O errors, are not classified in the spec. Are they wrapped into `StorageWriteException`, and with which `IsTransient` value? Task 125 depends on that answer.

**RISKS**

9. Own cancellation is identified by "expected own-token OperationCanceledException", but HTTP timeouts surface as `TaskCanceledException`, which is also an `OperationCanceledException`. If the check does not look at the token, provider timeouts will be silently dropped instead of reported as Error.
10. The plan does not guard the logging calls inside the `Launch` catch. If the logger throws, the `finally` still runs, but the Task faults, which violates "Task завершается без fault" and "WhenIdleAsync завершается без fault".
