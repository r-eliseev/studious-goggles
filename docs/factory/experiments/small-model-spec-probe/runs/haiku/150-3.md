**ASSUMPTIONS**

1. The decoder receives the raw `b64_json` string with no data-URL prefix, and `ProviderResponseLimits.Image` is the decoded byte count. The spec never states either.
2. The whitespace set is exactly what `Convert.FromBase64String` skips on the target runtime (space, tab, CR, LF). The spec asserts this without a source, and the guard must count the same set.
3. The 72 MiB JSON reader rejects oversized responses before `DecodeImage` runs, through an error path other than `Unknown`.

**QUESTIONS**

4. The criteria require a decoded 50 MiB image to be accepted with whitespace, but the 72 MiB JSON limit stays unchanged. With `\r\n` escaped in JSON and `+` escaped by the serializer, a valid 50 MiB image can exceed 72 MiB. Which criterion wins?
5. The criteria say oversize yields `Unknown`, but plan step 4 keeps `FormatException` on the direct client and maps to `Unknown` only in the queued adapter. What does the direct client return or throw for an oversized decoded image?
6. "Зависит от: —" conflicts with step 6, which gates `done` on tasks 150 and 152 ("provider matrix"). Tasks 143 and 127 are referenced without description. Which of these actually block this fix?
7. Is there a real provider response that contains CR/LF or escaped `\n` inside `b64_json`? The bug report should name the provider and include a sanitized sample, since the whole fix rests on this claim.

**RISKS**

8. Whitespace parity: the plan tests space, CR, LF and NBSP but not form feed, vertical tab or U+FEFF. If the guard and the runtime disagree on any character, oversized input can pass the guard or valid input can be rejected.
9. Test realism: the large tests use zero bytes to avoid `+` escaping, but System.Text.Json escapes `+` by default. Real random images will be larger on the wire, so the production boundary can pass in tests and fail on real provider output.
10. Boundary gap: the production wrapped test uses 49 MiB, not 50 MiB with whitespace, so the exact-limit criterion is never exercised at production size. Multiple ~70M-character strings plus JSON and decoded copies across two clients may also consume hundreds of MB and slow CI.
