ASSUMPTIONS:

1. Token and word splitting follow the existing `FuzzyMatcher` tokenization (Unicode letters/digits, lowercase comparison), and `Distance` is plain Levenshtein with no case folding beyond what already exists. The spec does not say so.
2. Words in `SearchText` are matched only after the same tokenization as the query, so "water," with punctuation and "Water" in a different case are treated the same as "water" in the proposed prefix rule. The spec says nothing about case or punctuation for prefix comparison.
3. The Avalonia test `Search_FindsSessionByPromptWithTypo_ShowsSnippet` is assumed to remain valid after the change, since the spec says to run it unchanged but does not say what it asserts.
4. `SessionsPageModel` and the MAUI `SearchBar` binding are assumed to behave the same on Android and Windows; the spec only validates Android manually and says no MAUI code changes.

QUESTIONS:

1. The spec says the prefix-typo rule should apply only to query tokens of four or more letters, but the Analysis also says a three-letter token like "wot" must not match. Should a three-letter token ever get the prefix-typo rule, or is the threshold strictly four?
2. The Analysis says "первые буквы совпадают" is required, but the Criteria only say "почти начинается". Is the first-letter requirement a product decision (already recorded as accepted by the owner) that should also appear in the Criteria, so that the acceptance text matches the implementation?
3. Does "Порядок выдачи сохраняется" mean the only ordering guarantee is "exact prefix scores 3 > typo 1", or should ties between a typo match and a substring match (score 2 vs 1) also be specified?
4. The Criteria say the rule is "described in the search specification", but the Analysis says no such spec exists; the plan then adds S1.4 to `chat-sessions.md`. Is that file the intended single source, and is the Criteria text meant to be satisfied by that new section?
5. The Android IME question is listed as a Criteria item, but the Plan says the owner checks it manually and the MAUI code is not changed. What is the acceptance outcome if the check shows the IME does not forward uncommitted text: is task 101 done, blocked, or split?

RISKS:

1. The new rule keys on `word[0]` and `token[0]`, which are UTF-16 code units; for characters outside the BMP or for combining marks, "first letter" and the prefix slice `word[..length]` may split a grapheme or surrogate pair, so the Distance result may be misleading. The spec does not mention this.
2. `IsTypo` is evaluated for every word of every session on every keystroke after a 250 ms debounce; the spec does not state performance limits for large session histories, and the extra prefix checks add up to three Levenshtein calls per word pair.
3. The `length > 0 && length < word.Length` guard means a word equal in length to the token can never match through the prefix branch, but the Distance branch already covers it; the spec's rule should be checked against a case where `token` is longer than `word` (for example "lighthu" against "light"), which the plan does not test.
4. Plan step 2 is ordered before the Avalonia regression test in step 4, but step 3 says "должен пройти сразу", so a failure there is reported as a return to step 2 without a separate failing test to show what changed; the TDD order is only partly enforced.
5. The ASCII-only examples in the plan (`watte`, `water`) do not exercise the Cyrillic path of the new condition; `Match_CyrillicTypoInPrefix_Scores1` is listed as a regression test but is not in the step 1 failing set, so its behaviour under the new rule is unverified.
6. If the IME sends the uncommitted text in a shape that differs from the committed text (for example a composing span included or excluded), the owner's manual check in task 140 may pass or fail for reasons unrelated to fuzzy matching, and the spec does not define how to tell these apart.
