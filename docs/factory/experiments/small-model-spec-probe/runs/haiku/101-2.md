ASSUMPTIONS

1. Spec says "слово текста начинается с токена → 3 очка" is the only prefix case, but the plan's new rule compares `token` to `word[..length]` with a Levenshtein cutoff; I assume `Distance` is a plain Levenshtein on Unicode code points (not grapheme clusters), since the spec says Cyrillic and digits must keep working.
2. I assume the 4-letter threshold (`MinTypoLength`) applies to the query token only, not to the candidate word, so a 4-letter query token can match a 3-letter-prefix-derived length in the candidate.
3. I assume the spec's scoring weights (Title 3, Prompt 2, Description 1) and the "each query token must match" rule apply to the whole session, so a token matched only by a typo still counts as satisfied for AND logic.
4. I assume "Порядок выдачи" tie-breaking is unspecified; ties in score between two sessions are presumably ordered by something stable, but the spec does not say what.

QUESTIONS

1. The criteria say "короткие слова (меньше четырёх букв) опечатки не прощают", but the plan's `MinTypoLength` check and the example `wot` → `water` both assume the query token length, while the criteria speak of "слова" in general. Which length is meant: the query token or the text word?
2. The plan changes behaviour only for typos inside a prefix, but the criteria state "для целых слов правило не меняется" only in the decisions section. Should the criteria and the decisions be reconciled into one explicit rule for whole-word typos?
3. The Analysis states Android IME behaviour is unknown and the symptom is "полностью объясняется правилом выше". Is this verified on a device, or only inferred from the code? The criteria still require a recorded answer.
4. The spec says the typo rule applies "для слов запроса от четырёх букв", but the plan's first branch (`Distance(token, word) <= 1`) is also gated by `MinTypoLength`. Is the whole-word typo rule supposed to be unchanged for 3-letter tokens, or should it be gated only for the new prefix branch?
5. The plan's test `Match_TypoInPrefixOtherFirstLetter_NoMatch` expects "attempt" to be rejected, but the Analysis says the first-letter condition is a decision of the owner. Is the owner's decision final, or is there an open alternative (for example, allowing first-letter mismatch only for lengths ≥ 6)?
6. The task says "Файлы" include `tasks/backlog/140-*.md` and `016-skeleton-manual-check.md`, but the release step is `scripts/release-task.sh 101`. Is 101 the correct number for this task, given the dependency list is empty and the overlap section refers to 088–100?

RISKS

1. The `IsTypo` pseudocode checks `token[0] != word[0]` before the prefix loop, but for a 4-letter token whose first letter is a Cyrillic capital and the word is lowercase, `Distance` returns 1 while first-letter check fails; case handling is not specified in the spec, so the match set depends on whether `Match` lowercases input first.
2. The prefix loop uses `word[..length]` with `length` up to `token.Length + 1`; if a word is exactly `token.Length` long, `length < word.Length` excludes it, which means a typo in the last letter of a word of the same length is not matched by the prefix branch but is matched by the whole-word branch. The spec does not say this asymmetry is intended.
3. Surrogate pairs and combining marks: `word[..length]` slices by UTF-16 code units, so an emoji or a decomposed Cyrillic letter in a prompt can produce a broken substring and a false negative or positive; the spec's Unicode requirement does not mention this.
4. The debounce (250 ms, `SearchDebounce`) is cancelled on each keystroke; if Android delivers the IME composing text only after commit, the typed-but-uncommitted case in criterion 4 may be impossible to verify in code, so the manual check in task 140 is the only evidence.
5. The plan says "Тесты шага 1 проходят" after step 2, but the test `Match_TypoInPrefixEveryToken_Matches` expects score 4 for `["red", "watte"]` on "red water"; this assumes "red" scores 3 and "watte" scores 1, which holds only if no other word in the text also matches, so the expectation is fragile if the text grows.
6. The release script and the final `bash scripts/check.sh` are run after the report is written; if check fails, the task is already released and the status is inconsistent with the "не оставляет готовую задачу в in-progress" rule.
7. Concurrency: `OnSearchTextChanged` cancels the previous search, but `SessionSearchService` may still be running on a background thread when a new query arrives; the spec does not say whether stale results can overwrite newer ones.
