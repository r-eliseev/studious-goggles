ASSUMPTIONS
1. The spec's dependencies 025, 055, 057, 063, 064, 067 are already merged and their current state matches what the spec describes (e.g. `DetailsText`, `RunPromptFormat`, `IsError` exist as stated).
2. The design resource keys and values in `docs/design/implementation.md` (e.g. `IgCardShowOverlay`, `IgUserMessageAlignment`, `IgRunBorderThickness`) are already defined in the Avalonia and MAUI theme dictionaries that 061/062 produce, and the spec's own references to them are correct.
3. `Generation` exposes timestamps (`CreatedAt`, `CompletedAt`) and a cost value, since the spec says "проверить" rather than confirming the fields exist.
4. "Нестандартные" statuses such as `Cancelled` and `Filtered` are produced by the existing domain model; the spec does not say where `GenerationStatusKind` values are derived from.
5. Responsive breakpoints (840 px for Avalonia, `OnIdiom` for MAUI) apply to the whole chat view, and "на телефонах" means the MAUI phone idiom only.

QUESTIONS
1. The spec says `NoticeText` (per-card parameter notices) is "решение владельца в 074", but 074 is "Try again", a different feature. Which task actually owns the decision that notices sit on each card rather than under the prompt?
2. Criterion says "стили различаются только ресурсами", yet step 2 hardcodes `HorizontalAlignment={DynamicResource IgUserMessageAlignment}` and `IsVisible` bindings for roles. Is the layout decision (right-aligned bubble) meant to be expressed through resources, and does `DynamicResource` accept a `HorizontalAlignment` value in Avalonia without a converter?
3. Step 2 adds `IgCardShowShortMeta` to `implementation.md` and the theme dictionaries of 061 and 062, although the criteria list only `IgCardShowFullMeta` and `IgCardShowOverlay`. Is an extra key expected, and who approves changing the design reference owned by 061/062?
4. The "Update_SeedNotApplied_ShowsSeedNotSupported" test name and the "seed not supported" notice are not described anywhere in the spec text. What exact string or behaviour is expected?
5. The spec says `docs/specs/chat-sessions.md` should not change, but the note about 057 says the prompt must appear once. Is there a spec-level statement of which element owns that prompt display after 057?
6. Criterion "Тесты из «Плана» проходят" does not say whether `ChatFlowTests` must stay green unchanged, or whether changes to `DetailsText` (kept per the analysis) affect them.
7. The spec does not state how the "Filtered" card text is localised; the quoted English string is given, but the rest of the UI language should be confirmed.

RISKS
1. Step 1 adds `IsQueued`, `IsFiltered`, `IsCancelled` alongside `StatusKind`, which duplicates state; the plan does not say which is the source of truth, so the two can diverge on transitions (e.g. Running→Cancelled).
2. The `HeaderText` update path is left open ("подписка на `PropertyChanged` генераций или пересчёт"); if generations change without raising `PropertyChanged`, the run header ("2 of 6 done") goes stale, and two options have different concurrency behaviour.
3. `CostText` and `TimeText` depend on `CompletedAt - CreatedAt`; for failed, filtered or cancelled generations `CompletedAt` may be null, so a time is computed incorrectly or throws. Failure paths are not specified.
4. Avalonia `:pointerover` overlay visibility is not reachable on touch devices and is not reproducible in headless tests, so the `IgCardShowOverlay` criterion cannot be verified by `GalleryStyle_*` tests as the plan states.
5. The MAUI phone grid uses `OnIdiom`, which is evaluated once at page load; rotation or window resize on Windows/tablet will not reflow the grid.
6. Step 2 says the "идёт" card uses `ProgressBar IsIndeterminate` but no constraint on how often `Running` transitions fire; without throttling, frequent status updates can thrash the ItemsRepeater/CollectionView virtualization.
7. The plan says "если шаг не получается — поставь `blocked` и остановись", but the Linux environment cannot build MAUI for Windows, and the Windows target relies on CI; a failure in MAUI XAML compilation will surface late, after Avalonia work is already merged.
8. Changing `IsVisible` bindings to `DynamicResource` values (`IgCardShowFullMeta`, `IgCardShowShortMeta`) means the visibility is set once at runtime from resource lookup; if the theme is swapped at runtime, the controls will not update unless the bindings are re-evaluated.
9. The spec touches shared files with 025, 055, 057 (`GenerationItemViewModel`, `ChatView.*`); merge conflicts are likely, and the plan does not sequence work against those branches.
10. Dropping `DetailsText` from the card layout while keeping it as the accessible name means screen readers announce the full text, which can contradict the new per-field layout; the accessibility test may pass while the reading order is wrong.
