ASSUMPTIONS

1. The spec assumes the reader has `FuzzyMatcher.cs`, `ScoreWord`, `Distance` and `SessionSearchService` at hand. The spec gives no content of them beyond the summary in «Анализ», so the implementer must trust that summary rather than verify it.
2. Assumes `Distance` is a plain Levenshtein on UTF-16 code units, so a surrogate pair or combining character counts as more than one letter. The spec never says how Unicode is normalized.
3. Assumes "first letter" means `token[0] == word[0]` with case-sensitive comparison only if the matcher already lowercases both sides. The spec does not say whether matching is case-insensitive.
4. Assumes the prefix rule with `L` in {|t|−1, |t|, |t|+1} is the intended behaviour, but the criteria only give examples. Whether the rule should allow a typo that is not in the first three letters, or handle a missing first letter, is not stated.

QUESTIONS

1. The criteria say "короткие слова (меньше четырёх букв) опечатки не прощают", but the plan says "токен от 4 букв" for the prefix rule and the Analysis says "слова запроса от четырёх букв". Does the 4-letter threshold apply to the query token only, or also to the matched text word? The text word length is not constrained anywhere.
2. The Analysis says the first-letter condition "отсекает совпадения со сдвигом", and the plan adopts it as a decision. Is the owner's expectation that a typo in the first letter (e.g. "qater" → "water") should still match? The spec does not say, and the criteria do not cover it.
3. The plan says the rule for whole words is unchanged, but the new prefix rule can match a text word that is itself longer than the token. Should a prefix match score the same as an exact prefix of the same length, or lower? The spec only fixes the 3/2/1 values without explaining the ordering between a typo-prefix and a substring match.
4. The criteria require "правило описано в спецификации поиска", but `docs/specs/` has no search spec (the Analysis says so). Plan step 5 adds it under `chat-sessions.md` S1.3/S1.4. Does the owner accept that location, given that `docs/architecture.md` is said to hold only one line about `Search/`?
5. The Analysis says the IME question "не зависит" from the symptom, yet the criteria require it to be "выяснено и записано". Who decides the outcome if the Android check is not run, since the plan says the owner checks it by hand and the task still has to reach `release-task.sh`?
6. The plan says "Недоступная ручная проверка ... не оставляет готовую задачу в in-progress", but also says `blocked` is for "недоступной обязательной среды". Is a missing Android device a blocker or an accepted deferral to task 140?
7. The plan refers to `scripts/release-task.sh 101` and `scripts/check.sh`, and to tasks 016, 046, 140 and 089, but none of these files are provided. Their existence and contents are assumed.

RISKS

1. Step 2 changes `ScoreWord`, so every query token now also goes through `IsTypo` for whole words. Because `Distance(token, word)` is checked first, the existing whole-word behaviour is kept, but the new branch can add matches for words the existing tests expect to be absent, so the full `FuzzyMatcherTests` suite must be re-run, not only the new cases.
2. The prefix rule with `L = |t|+1` requires `L < |w|`. For a text word equal in length to the token plus one, the check is skipped, so a case like "watte" → "water" (length 5, prefix "wate") is found only through `L = |t|−1`. This edge is correct but easy to break when the `length < word.Length` guard is written wrongly.
3. Scoring: the typo branch gives 1 and the substring branch gives 2. For a token such as "lighth" that is a substring of "lighthouse" and also a prefix-typo match, the matcher returns the highest score per word, so the outcome depends on the order of checks in `ScoreWord`. The spec does not say which branch wins.
4. The Analysis claims "wate" already matches "water" at score 3, which is true only if the exact-prefix branch is checked before the typo branch. If the code uses a `Max` over all branches it is fine; if it returns early, the claim is unverified.
5. Performance: the prefix rule runs `Distance` three times per text word for every query token on every keystroke, with a 250 ms debounce. The spec does not mention the number of sessions or the cost on Android devices.
6. Cyrillic and Unicode: the spec says "не менять Unicode-токенизацию", but `token[0] != word[0]` on a surrogate pair or a letter with a combining accent compares half a code point, and can give a false negative for emoji or decomposed Cyrillic letters "й".
7. IME: the reported symptom ("watte" → "Nothing found") may also come from `SearchText` not updating during composition, as the spec itself notes. If the IME does not commit text, the 250 ms debounce will not fire at all for the composing text, so fixing `FuzzyMatcher` alone will not resolve the owner's report, and the Core tests will pass while the device still fails.
8. Documentation step 5 says the rule "перестановка соседних букв считается двумя ошибками" but the Analysis says it is 2 under Levenshtein only if the matcher does not use Damerau distance. If `Distance` is Damerau, "wtaer" would match and `Match_SwappedLetters_NoMatch` would fail, so the test asserts a property that depends on an unverified implementation detail.
9. Step 6 says `scripts/release-task.sh 101` runs before `bash scripts/check.sh`, so the task may be marked released before the check passes. If the check fails, the released state and the code disagree, and the plan gives no rollback.
10. Step 4 requires the existing Avalonia test to pass "без изменений", but that test depends on the snippet and the typo case. A change in `FirstIndex` or in the set of matched words may alter the snippet shown, and the spec does not say whether snippet output is also covered by the criteria.
