**ASSUMPTIONS**

1. Task 111 is merged and provides `_running`, slot release, `WhenIdleAsync`, and the cancellation semantics of 108. The spec relies on these without stating their contracts.
2. `GenerationUpdated` subscribers are invoked synchronously from `SaveAndNotifyAsync`, so "event only after confirmed update" and the subscriber-isolation catch in step 5 behave as described. The spec does not say how events are dispatched.

**QUESTIONS**

3. If the Running status write fails, step 6 forbids a second Failed write from the supervisor. What status does the generation keep in the DB, and what does the UI show? The spec does not say.
4. The criteria say `SaveAndNotifyAsync` "does not suppress failure", but step 5 logs and drops subscriber exceptions. Is a subscriber exception a generation failure or not?
5. Step 2 fixes `IsTransient=false` for zero affected rows. Does a zero-row result from a concurrent delete or a busy database need a different signal for task 125?

**RISKS**

6. If the supervisor swallows the exception and `_running` is cleared, the DB row may remain Running with no event and no retry. `WhenIdleAsync` completes without fault, so the inconsistency the task is meant to fix stays hidden.
7. Step 5 writes full exception detail to Debug. Inner exceptions such as `HttpRequestException` can carry URLs or request data, and the leak check in the Test section covers only the Error level, so Debug output may leak secrets.
8. If cancellation arrives during or just after a confirmed UPDATE, the spec does not say whether the event fires or whether the own-cancellation path skips the Error. The result could be a silently missing event or a mislabelled Error.
9. SQLite busy or locked conditions surface as `SqliteException`, which step 1 does not wrap. On Linux and Windows these reach the supervisor unclassified, bypassing the `StorageWriteException.IsTransient` contract that task 125 depends on.
