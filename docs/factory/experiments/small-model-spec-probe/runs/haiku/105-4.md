ASSUMPTIONS
1. The 2026-10-31 clarification (full history indexed at once, separate "Meaning" mode, no result mixing) overrides the earlier "Analysis" section and the plan's "per-session best match" ranking, which is inconsistent with it; I assume the 10-31 decisions are authoritative.
2. The OpenRouter `/embeddings` endpoint accepts a `string[]` input and returns `index`-tagged items for `baai/bge-m3`, with the 1024 dimension verified at first call as the spec requires; I assume no per-request input count or token limit beyond the 64-item batch.
3. `SessionChangeNotifier` emits events for title, prompt, and description changes, and for session deletion, so the 2-second recompute and removal paths have a trigger.
4. `search.json` in the data folder is the single place for the enable flag, and it is not synced or shared across the Linux, Windows and MAUI shells with different data folders.
5. Expense log entries from 021 stage A exist in main with an `ExpenseKind.Embedding` value and an operation-id field, as the plan requires.

QUESTIONS
1. The Analysis section says re-indexing strategy must be decided before `planned`, while the 10-31 clarification says all history is indexed at once on enable. Is the one-pass enable the chosen strategy, and does it satisfy the "re-indexing decided" criterion?
2. The `usage.cost` unit is unconfirmed, yet the plan records `CostUsd?` and writes cost to the expense journal. What is the fallback when cost is unknown: null entry, or zero, and how is "actual vs unknown" shown in the UI?
3. The spec requires "no hidden repeated paid requests" but retries 429/5xx up to 2 times on each batch. Does each retry count as a separate paid charge in the journal, and is there a user-visible cap on total retries per pass?
4. The 10,000-text limit ("first 10,000 most recent") conflicts with "full history at once". Which 10,000 are kept, how is "most recent" defined for prompts (run date vs. edit date), and what does the user see when the limit is hit?
5. Ranking: the spec states "best match per session" for semantic results, but it does not define how this is presented next to the separate word-search list, nor whether a session can appear with a low cosine score. Is there a minimum score, and the criteria forbid an invented threshold, so what is the cut-off?
6. The "Meaning" toggle is disabled when there is no OpenRouter key, but the criteria say the offline/no-key state must be shown explicitly. Where is the distinct message text and state for "no network" versus "no key" versus "provider failure"?
7. The enable flow writes the flag to `search.json` and "deletes vectors" on disable. Is disable also expected to be reversible without re-paying, and what happens to vectors when the user changes the embedding model in a later version?

RISKS
1. Deleting a session cascades to `text_embeddings`, but the stale-response criterion needs writes to be rejected if the session was removed mid-request; the plan does not state where that check happens (repository transaction vs. service), so a late batch can reinsert vectors for a deleted session.
2. The `content_hash` covers normalized text only, so a prompt edit that creates a new run gets a new `prompt:<runId>` key, leaving the old key orphaned; orphan removal is only mentioned for "removed sources," so orphaned vectors may persist and count against the 10,000 limit.
3. Batch-level transactions with a 2-second debounce on `SessionChangeNotifier` can race with a full pass: the pass may compute pending sources while a debounced recompute also embeds the same text, producing duplicate paid calls.
4. Loading all vectors into memory on first search is roughly 40 MB at 10,000 × 1024 float32, plus the LRU and copies during cosine computation; on a mobile MAUI shell this may exceed comfortable memory and the plan defers measurement to the report, after release.
5. Float32 little-endian BLOB round-trip depends on the dimension recorded at write time; if the model returns a different dimension for a later call (or a different model version), existing rows are mixed in the same cosine computation, and the plan has no check that `model` and `dimensions` match before ranking.
6. The `ProviderException(Unknown)` path for NaN/mismatched vectors and the batch `Failed` state do not say whether a failed batch leaves earlier batches usable, so the user can see a partial index labelled "Ready" or be stuck in "Failed" with no resume action.
7. Cancellation: `StopAsync` is described as keeping saved batches, but an in-flight paid request whose response arrives after stop may still be charged and logged; the plan does not say whether that response is discarded or saved.
8. Cross-shell behaviour: the same `search.json` and SQLite file may be opened by Avalonia on Windows and MAUI on Android with different paths; concurrent indexing from two shells is not addressed, and SQLite write locking during a long pass could block the UI shell.
