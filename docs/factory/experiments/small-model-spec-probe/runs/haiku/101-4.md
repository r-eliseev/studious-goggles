ASSUMPTIONS

1. The spec's description of `ScoreWord` (prefix 3, contains 2, typo 1 only for whole words of ≥4 letters) matches the actual `FuzzyMatcher.cs`, which the spec states but I cannot verify from the text alone.
2. Tokenization is Unicode-aware and splits on whitespace/punctuation the same way for Cyrillic and digits, as the regression tests assume.
3. "Distance" is plain Levenshtein with unit-cost substitution, insertion and deletion; transpositions cost 2, as the spec states.
4. Searching runs on every keystroke with a 250 ms debounce, so a partial word is always the final token when the user pauses, which is why the typo in the last token matters.
5. `SessionSearchServiceTests` helper `Create(params SearchText[])` and the `SearchTextKind` enum exist as named in the plan.

QUESTIONS

1. Does `ScoreWord` already contain the "prefix typo" branch the plan mentions as "or with a prefix of the same length" from task 079, or was it dropped? The Analysis says it was not implemented, but the plan's step 2 replaces a condition whose exact text should be checked against the file.
2. Is the first-letter rule meant to apply to the prefix-typo branch only, or should whole-word typos also require matching first letters? The spec says "for whole words the rule does not change", but the decision is recorded only in the "Решения" paragraph and not in the acceptance criteria.
3. The acceptance criteria say "короткие слова (меньше четырёх букв) опечатки не прощают", but the test list covers only `wot`. Should the 4-letter boundary (`wate`, exactly four) be tested explicitly for the prefix branch?
4. What is the intended behaviour when a query token has a typo and matches only through the prefix branch, but the text has an exact whole-word match for a different token? Does `FirstIndex` or snippet selection change?
5. Is the 250 ms debounce value part of the acceptance criteria, or only an implementation detail? The manual Android check depends on it ("через четверть секунды").
6. The "Ручная проверка" section asks to register Android IME findings in task 140, while the plan also says to write the scenario there. Which file is the owner of the manual scenario, and does 140 exist in `tasks/backlog/`?
7. The plan says `scripts/release-task.sh 101` runs before `scripts/check.sh`, but the spec does not say what "release" means for this task or whether it is required before the manual Android check. Please confirm the order.

RISKS

1. Step 2 replaces the typo condition in `ScoreWord` with `IsTypo`, but the new prefix branch also fires for whole-word tokens of exactly four letters that already match via `Distance <= 1`. The early return on `Distance(token, word) <= 1` keeps existing scores, but any token whose first letter matches and which is a prefix of a longer word will now score 1 where it previously scored nothing, which the "Шум" paragraph accepts only implicitly for the first three letters.
2. The prefix check uses `word[..length]` with `length` derived from `token.Length`. If `word` is shorter than `token.Length - 1` the loop must still guard `length < word.Length`; the pseudocode does, but a naïve implementation dereferencing `word[0]` on an empty word would throw, so the empty-word case needs a test.
3. Surrogate pairs and combining characters (emoji in prompts, Cyrillic with combining marks) can make `token[0] != word[0]` and `Distance` operate on UTF-16 code units rather than text elements, so a typo near an emoji could match or miss unexpectedly.
4. Scoring is additive across tokens and text kinds, so a session where a prefix typo matches a title (weight 3) can outrank a session with an exact prompt match. The spec does not say whether this is acceptable, and the "exact prefix ranks higher" criterion is only checked for one two-session case.
5. The Android IME behaviour (committed vs. composing text in `SearchBar.Text`) is unknown from the code. If the platform does not update `Text` during composition, the fix for `watte` cannot be verified on the device until the separate task exists, so the acceptance criterion cannot be closed in this task.
6. `scripts/release-task.sh 101` and the instruction that an unavailable manual check must not leave the task `in-progress` could conflict: if the Android check is blocked, the release step may run before the manual result is recorded, leaving the task in an inconsistent state.
