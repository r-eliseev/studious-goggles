ASSUMPTIONS:
1. The "design system" resources (`IgCardBackgroundBrush`, `IgRunPadding`, `IgUserMessageAlignment`, `IgPrompt*`, `IgCardShowOverlay`, etc.) already exist in `implementation.md` and in the Avalonia/MAUI theme dictionaries, with the exact keys and types the plan uses; the plan only consumes them and never defines them.
2. "Задача 069" (menus and hover actions), "074" (Try again, per-card notice ownership), "016", "046", "061", "062", and the ADR 0014 decisions referenced in the spec are all resolved elsewhere and their outcomes are known to the implementer.
3. `Generation` already carries timestamps (`CreatedAt`, `CompletedAt`) and a seed/cost field, so `TimeText` and `CostText` can be computed without model changes.
4. The `Filtered` status and the "Filtered by the provider…" text are produced by the existing domain model; the spec does not say how a generation becomes `Filtered` versus `Failed`.
5. Image aspect ratio 3:2 is enforced by the card layout and the placeholder, not by the image data returned from the provider.

QUESTIONS:
1. Section 2.4 of `implementation.md` is cited as the source of style differences, but the spec never lists which keys differ between Gallery and Notebook; should the implementer assume the dictionary keys in 2.4 are complete and final?
2. The plan adds `IgCardShowShortMeta` as a new key to dictionaries 061 and 062 and to `implementation.md`, while the acceptance criteria only mention `IgCardShowFullMeta` and `IgCardShowOverlay`; is the new key approved, and what is its exact value in each theme?
3. The `Update_SeedNotApplied_ShowsSeedNotSupported` test name and the "seed not supported" wording have no string in the spec; what is the exact user-facing text and which resource key holds it?
4. The "Queued" card and "Cancelled" card are listed in the status set, but the acceptance criteria only give text for Filtered and Error; what text and icon should Cancelled show?
5. The spec says notices are "на каждой карточке, решение владельца в 074", but 074 is "Try again" in the Анализ section; is the per-card notice decision actually in 074, and is it final?
6. The spec says the `IgCardShowFullMeta` / `IgCardShowOverlay` pair is Gallery-specific, but the plan's MAUI step only states "полоса Gallery видна всегда" on phones; what happens on Notebook and on desktop widths below 840?

RISKS:
1. Step 1 adds `IsQueued`, `IsFiltered`, `IsCancelled` alongside `StatusKind`; two sources of truth for the same status can diverge unless the booleans are derived from `StatusKind` in one place.
2. `RunItemViewModel.HeaderText` is said to update via `PropertyChanged` of generations or recalculation in `ChatPageModel`; the spec does not say which, and a missed notification leaves the header count stale while generations finish concurrently.
3. `TimeText` depends on `CompletedAt - CreatedAt`, which is null for running, queued, and cancelled generations; the plan does not say whether those show an empty value, a dash, or a crash-prone subtraction.
4. The plan says to hide the seed and time in the overlay "by hover" on desktop; pointer hover is not available on touch in Avalonia and the spec does not provide a fallback, so keyboard and touch users may never see seed or time.
5. The `:pointerover` pseudo-class in step 2 is Avalonia-specific; the spec does not account for the MAUI side, where the same overlay has no hover, and the plan says only "полоса Gallery видна всегда" on phones without saying what desktop MAUI does.
6. `ProgressBar IsIndeterminate` under the image is the only "running" indication; the plan does not say how the placeholder behaves when a generation switches from Running to Done or Failed while the card is on screen.
7. The `WrapPanel` / `UniformGrid` 3-column layout with a switch to 2 columns below 840 px is a width breakpoint with no specified mechanism in Avalonia; the plan does not say whether it uses a `Grid` with `ColumnDefinitions` binding, a converter, or a media query equivalent.
8. Step 2 says "в разметке нет проверок стиля" as a success criterion, yet the plan uses `IsVisible={DynamicResource IgUserMessageRoleVisible}`, which is a value binding rather than a style check; the criterion is ambiguous enough that a reviewer may reject correct code.
9. The Avalonia test `GalleryStyle_UserMessageAlignedRight` depends on which resource dictionary is loaded in headless tests; if the test does not switch the theme, it will pass or fail on the default style and not on the Gallery style.
10. Step 3 requires MAUI XAML to use `OnIdiom` for a 2-column grid, but the Android build is the only one checked; the Windows MAUI target is built only in CI, so a platform-specific XAML failure would surface late.
