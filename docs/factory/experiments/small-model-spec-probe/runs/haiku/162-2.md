ASSUMPTIONS
1. The "ghost" `Button` inside the `SwipeView` is the only element that receives the tap, and the fix in step 1 (replacing it with a `TapGestureRecognizer` on the `Grid`) will not itself get swallowed by the swipe gesture recognizer on Android.
2. `SessionsListView.xaml` contains the Today and Earlier templates with the structure described in Analysis (`SwipeView` → `Grid` with `ContextFlyout` → `Button`), and these are the only places where a session row is rendered on MAUI.
3. `SwipeBehaviorOnInvoked`, `Threshold` and `SemanticProperties` are available in the MAUI version used by the project (net10.0), and `Threshold` is a property the developer can set on the `SwipeView` itself.
4. Owner's device runs Android with TalkBack available, so the accessibility criterion can be checked manually.

QUESTIONS
1. Which exact `SwipeView`/`SwipeItems` properties does the spec intend (`Threshold` on the `SwipeView`, or a different mechanism), and what is the target value, since "около ширины одного действия" is not a measurable number?
2. Does the spec want a long-press to keep working for Rename/Delete on Android, or is the swipe the only way? Step 5 suggests a "⋯" button, but the acceptance criteria only say "swipe or explicit button" without choosing.
3. Should the search results list (no `SwipeView`) be changed to match, or is it intentionally left as is? The Analysis uses it only as a comparison, not as a requirement.
4. Is the `TapGestureRecognizer` on the `Grid` expected to coexist with the `ContextFlyout` on Windows/Mac, and what happens on Windows when the user taps the row (is opening still the primary action there)?
5. The spec says "Зависит от: —" but Step 6 and the backlog reference `140` and the CI item `016`. Are these dependencies that block completion, or just reporting references?

RISKS
1. Step 1 moves the open action from a `Button` to a `TapGestureRecognizer`. On Android a `Grid` with a tap recognizer inside a `SwipeView` can still lose the gesture to the swipe recognizer, so the fix may not change the behavior; the plan has no step to verify that before the manual check.
2. The root cause is stated as a "known" `SwipeView` behaviour without a source or an issue reference. Step 6 wants this recorded as a fact in `docs/knowledge/maui.md` only after confirmation, but the confirmation step is the owner's manual check, so the hypothesis may be written down as fact too early.
3. The comparison test ("if search works, hypothesis confirmed") is weak: search rows may differ in more than the absence of `SwipeView`, so a difference does not prove the cause.
4. Step 2 sets `SwipeBehaviorOnInvoked="Close"`, which closes the swipe after an action but does not address the accidental opening on a small horizontal movement; the spec mixes two problems (accidental open vs. actions not closing).
5. Step 3 merges the Today and Earlier templates into one shared `DataTemplate`. If the two currently differ in any way the spec does not describe (grouping headers, bindings), the merge can silently break one of them.
6. The unit test in `ImageGen.Presentation.Tests/Design` checks XAML markup structure, so it can pass while the real Android tap behaviour is still broken. It does not guard the acceptance criterion it is meant to cover.
7. Step 4 ties row height to `IgControlHeight` (48 on Android) without a stated reason; on a row that now contains a tap area and labels, a fixed minimum may cut off two-line session titles or subtitles.
8. Acceptance says Windows and Mac Catalyst behaviour must not change, but Step 1 adds a gesture to shared row content and Step 3 changes the shared template; there is no plan to verify Mac Catalyst at all, only Windows via CI.
9. Android `ContextFlyout` long-press: the spec says it "should not interfere" but gives no test for it, and a long press that opens a flyout or swipe on Android could still conflict with the new tap gesture.
10. Dependency on the Android device for the final check means the spec cannot be fully verified in the Linux/Windows environment named in "Среда"; if the owner is unavailable, the item stays open with no fallback verification.
