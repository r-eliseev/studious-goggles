ASSUMPTIONS
- The stated "Среда: Linux или Windows" implies the 1-hour cutoff and the `File.GetLastWriteTimeUtc` check behave the same on both; the spec does not say whether NTFS or ext4 timestamps are trusted.
- `IImageFileStore` has no existing consumers outside DI that would break when a method is added; the spec assumes only test doubles need updating (step 4).
- The `Warning` log call is available in `FileImageStore` or `AppInitializer` (ILogger injection), but the spec does not say how logging is wired into the Data layer.
- The 32-hex suffix is always lowercase `N` format, as produced by `Guid.ToString("N")`; the regex `[0-9a-f]` depends on that.
- `AppInitializer` runs once per process start, so a single sweep is enough and no concurrent sweep from a second instance is expected.

QUESTIONS
- Criteria say "удаляются ... старше 1 часа" and the plan uses `now - lastWrite > olderThan`, but the spec never states whether the boundary is strict or inclusive, nor whether a future-dated timestamp (clock skew) should be deleted.
- Step 3 says the Presentation test should use a real `FileImageStore`, while the Presentation layer depends on `IImageFileStore`. Is `AppInitializer` expected to reach `FileImageStore` through DI in production, and does the test need the Data project reference?
- Step 2 says the defaults sweep covers "корень папки данных", but `DefaultAssistantModelFile` lives in that folder and `FileImageStore` may not know that path. Which class owns the defaults sweep: `FileImageStore` or `DefaultAssistantModelFile`?
- The "Анализ" section says the `ShellHarness` may create `AppInitializer` manually, with "проверить, вручную ли", yet step 5 treats it as optional. Should the harness be updated or is it fine to leave it on the old constructor?
- Step 4 changes the constructor of `AppInitializer` but the spec does not say whether a `ILogger` is also needed for the required Warning, and it is not in the constructor list.
- The "Порядок исполнения" section says to stop and ask if the code differs from the plan, but the plan itself was written against an unspecified `main`. Which commit is the baseline?

RISKS
- Deleting a file that a live writer is still writing: the 1-hour threshold protects against this only if the writer's `File.Move` happens within an hour; a stalled but alive process could lose its temp file, and the spec gives no guard beyond age.
- On Windows, a temp file may be held open by antivirus or another process, so `File.Delete` throws `IOException` and the Warning path is hit regularly; the spec does not say how repeated warnings are handled.
- `Directory.EnumerateFiles(..., AllDirectories)` on a large `images/` tree runs synchronously in `Task.Run` and may delay startup perceptibly; the spec does not bound this and does not say whether the sweep may be cancelled.
- Enumeration while files are being deleted (or created by a concurrent first-run image save) can throw or skip entries on some platforms; the spec does not address enumeration-time exceptions, only deletion-time ones.
- `AppInitializer.InitializeAsync` runs after `database.InitializeAsync`, but if that throws the sweep never runs; the spec does not say whether the sweep should run on that failure path too, and it does not define the ordering relative to `GenerationService` startup.
- The defaults template `defaults.json.<hex>.tmp` in the root could match a file written by an older app version with a different suffix scheme; the spec does not confirm that only the current writers produce these names.
- Using `File.GetLastWriteTimeUtc` as the age source means a file copied or restored from backup with an old timestamp is deleted immediately even if it was just created; the spec does not consider this.
