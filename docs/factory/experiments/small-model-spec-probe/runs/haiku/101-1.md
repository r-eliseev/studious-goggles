ASSUMPTIONS

1. The "Анализ" section's Levenshtein results (e.g. "watte"→"water" = 2, "lighthuse"→"lighthouse" = 1) were computed correctly and the current `ScoreWord` matches the described behaviour; I did not verify this against the actual `FuzzyMatcher.cs`.
2. "Не менять Unicode-токенизацию" implies the tokenizer already splits Cyrillic and digits correctly, and `Distance` works on UTF-16 code units, which is safe for the test strings used but may not be for supplementary characters (emoji in prompts).
3. The `IsTypo` pseudocode ignores case: I assume tokens and words are already lowercased before `ScoreWord` is called, since `token[0] != word[0]` is a case-sensitive comparison.
4. The existing `SessionSearchServiceTests.Search_ExactPrefixBeatsTypo` scenario (`"wate"` vs `"date palm"`) is expected to pass without changes, which assumes `"date"` has no typo-match to `"wate"` under the new rule (distance from "wate" to "date" is 2, so this holds).

QUESTIONS

1. The spec says the fuzzy-prefix rule is "описано в спецификации поиска", but the Анализ section says no such spec exists in `docs/specs/`; which document is authoritative, and should the rule be written before or after the code change?
2. The plan says to ignore the Android IME question for code ("код Presentation/MAUI не меняется"), yet the Критерии require it to be "выяснено и записано в Отчёте"; who performs the Android manual check, and what happens if no device is available before the task is marked done?
3. The `FirstIndex` expectations (e.g. `Match_MissingLetterInPrefix_Scores1` expecting index 4 in "two bridges") depend on how `FirstIndex` is defined (token index, character offset, or word index); the spec does not say.
4. The rule "слова от четырёх букв" is applied to the query token, but the Критерии say "короткие слова (меньше четырёх букв) опечатки не прощают" which could mean the text word too; the plan and the Анализ disagree on which one is meant.
5. Should the 2-letter-or-more transposition rule and the first-letter condition apply to whole-word typos too, or only to prefix typos? The plan keeps whole-word behaviour unchanged, but the Анализ example "cats"→"catalog" shows the new prefix path widens matches more than the spec acknowledges; is that acceptable noise?

RISKS

1. `IsTypo` runs `Distance` against every word of every session for every keystroke; the prefix path adds up to three extra Levenshtein calls per word, which may matter for large histories, and the spec sets no performance bound.
2. The 250 ms debounce in `SessionsPageModel.OnSearchTextChanged` combined with an incomplete IME composition on Android could cause the search to run on partial text and show "Nothing found" transiently; the plan defers this, so the Android acceptance check may fail for reasons outside this task.
3. The `length > 0 && length < word.Length` guard means a prefix of length `token.Length + 1` is only tried when it is shorter than the word; for a word exactly one letter longer than the token, the full-word distance check (`Distance(token, word) <= 1`) is the only path, which is not obviously equivalent and deserves a test.
4. Modifying `ScoreWord` changes which sessions match for common 4-letter query tokens (e.g. "cats" now matches "catalog"), and the Avalonia test `Search_FindsSessionByPromptWithTypo_ShowsSnippet` is run only as "без изменений", so a regression in snippet selection would not be caught by the new unit tests.
5. The task requires `scripts/release-task.sh 101` to run before `scripts/check.sh`, and the plan says unavailable manual checks must not leave the task `in-progress`; if the Windows or Android checks cannot run, the task has no defined terminal state other than being marked done without them.
