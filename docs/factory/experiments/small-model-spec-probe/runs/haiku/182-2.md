ASSUMPTIONS
1. The journal stores each cost as a `decimal`/`double` in USD, and `rows.Sum(...)` yields a numeric type whose `ToString("0.####", InvariantCulture)` rounding matches what `CostTextOf` does (the spec only says "как в CostTextOf", not the actual rounding rule).
2. `AppResources.CostFormat` is used with `string.Format` and is not culture-sensitive in its own text, so passing `InvariantCulture` affects only the number.
3. The zero case `$0` comes from `0.####` producing an empty fractional part, not from a special-case branch the spec would have to name.
4. `TotalUsd` on groups is a plain number and the page binds only `TotalText` for the total, so changing the total's format does not affect other bindings.
5. The test helper that replaces `CurrentCulture` is not shared with other tests in a way that conflicts with parallel test execution.

QUESTIONS
1. Should the total be rounded the same way as the per-row cost, or is the sum meant to show full precision? The spec says "`0.####`" but does not say whether rounding is half-even, half-up, or truncation, and `0.0345` in the test example has four decimals, which fits `0.####` only by coincidence of the inputs.
2. The acceptance criterion says "как в `CostTextOf`", yet the plan says to copy the logic inline and not extract a helper. Is the intent to match behaviour exactly, or to match only the format string?
3. What should `TotalText` be when there are no rows at all: `$0` (per the criteria) or an empty string, as the page may currently show for an empty state?
4. Does the spec intend `TotalText` to respect `CurrentCulture` for anything else, such as a decimal separator for the number, given that `InvariantCulture` now forces `.`? Is that a deliberate change for Russian users?
5. The plan references task 186 for removing duplication, but the spec does not say whether that task's result should be checked before implementing, or whether this change may create a conflict with it.

RISKS
1. Test setup: changing `CultureInfo.CurrentCulture` only restores it on the current thread in `finally`; if the test uses `async` continuations that resume on another thread, the culture may not apply and the failing test may pass or fail for the wrong reason. Confirm the step "падает именно по описанной причине" holds before the fix.
2. Floating-point summation: if the journal uses `double`, `0.03 + 0.0045` may produce `0.03449999...`, and `0.####` would render `0.0345` but a different rounding on other values could show `0.0344`; the test expects an exact string, so use `decimal` or round explicitly.
3. Culture on other threads: `ToString("C", CurrentCulture)` in the existing code runs inside `RefreshAsync`, which may be called after an `await` on a different thread; the fix with `InvariantCulture` removes this dependency, but other format calls in the same method (if any) still depend on the culture.
4. Negative or tiny totals: `0.####` turns a value like `0.00001` into `$0`, which hides real non-zero spend; the criteria do not say whether this is acceptable for the total.
5. The verification commands include `scripts/check.sh` and `dotnet format --verify-no-changes`, which may fail for reasons unrelated to this change (pre-existing formatting drift); the plan does not say how to handle a failure there.
6. Mixed scope: the plan says not to fix neighbouring findings, but `CostTextOf` and `ChatPageModel.FormatEstimate` may already differ in rounding; matching `CostTextOf` could silently copy a bug the spec calls the reference.
