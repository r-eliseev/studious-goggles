**ASSUMPTIONS**

1. The spec assumes `generation.id` is the primary key, so an UPDATE can never affect more than one row, and no other code path writes the same status transition (Analysis, step 2).
2. The spec assumes tasks 108, 110 and 111 are already in `main`, so the own-cancellation distinction, the `CapturingLogger` extensions and the `_running`/`Launch` structure exist (header "Зависит от", step 4).

**QUESTIONS**

1. Criteria say `SaveAndNotifyAsync` must not suppress failure, but step 5 keeps a catch for subscriber exceptions after a confirmed write. Should a subscriber failure reach the supervisor as Error, or only be logged?
2. Step 6 forbids the supervisor from writing a second Failed status. If the terminal update itself fails, is a generation left permanently Running in the DB, and is that accepted or handled elsewhere?
3. Which repository method performs the Running transition, and how is a concurrently deleted row classified: zero-row non-transient, or something else? The spec also does not define the "logging policy проекта" or the set of "safe" fields.

**RISKS**

1. The spec does not say how `SqliteException` (for example SQLITE_BUSY, "database is locked") is mapped, so transient DB errors may reach the caller as `IsTransient=false`, which conflicts with the intent of task 125.
2. If the UPDATE commits and then an own-token `OperationCanceledException` or a logger exception is thrown before the event, the DB and UI diverge silently. The spec does not state that `_running` removal in `Launch` still happens if the Error log call itself throws, and otherwise `WhenIdleAsync` could hang or fault.
3. When the Running-status update fails, the DB row stays Running and the slot is released only through the same finally path. Step 7 tests one failing job, not whether the slot is reliably reusable under concurrent launches.
4. Exception detail is logged only at Debug, so production failures lose their cause unless Debug is enabled. Conversely, provider exception messages can carry prompts, keys or URLs at Debug, which the sentinel check in step 4 does not cover.
5. In step 106's file-save path, the file is written before the terminal UPDATE. A non-transient zero-row failure therefore leaves an orphaned file until task 122, a window the spec does not explicitly accept.
