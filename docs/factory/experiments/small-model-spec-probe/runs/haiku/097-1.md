ASSUMPTIONS:
1. `ChatPageModel` exposes `Items` as an `ObservableCollection`-like type that raises `CollectionChanged` on `ReloadAsync`, and the Avalonia `OnItemsChanged` subscription is the only source of row-change signals; I assume no other code path replaces the collection without notifying (the spec says `ReloadAsync` clears and rebuilds).
2. `TranscriptFollower.IsAtEnd` receives the same `Offset`/`Viewport`/`Extent` units in both shells; for MAUI the spec instead uses `ItemsViewScrolledEventArgs` with indices, so I assume the MAUI side never calls `IsAtEnd` at all, which the spec's markup and handlers imply but do not state.
3. The Avalonia `Transcript` `ScrollViewer` exists under that name in `ChatView.axaml` and is not recreated on `DataContext` change, since the spec says "искать текущий Transcript" without saying where it is kept.
4. Headless tests in `TranscriptScrollTests` can drive real layout (`UpdateLayout`, window height changes) deterministically on the CI platform.
5. `CardUpdated` fires on the UI thread before the card's layout is measured, which is why the spec adds a separate `SizeChanged` hook on MAUI rows, but the Avalonia side has no equivalent row-level hook.

QUESTIONS:
1. S1: The spec says "Работа с ... 'Анализ' ... не дёргать ленту, если пользователь сам прокрутил вверх", yet decision (1) forces scroll on any `Items` change even when the user scrolled up. Which takes priority for "Повторить" or "Новый seed" when the user is reading older messages, and is that intended?
2. S2: Should `ViewportChanged` on keyboard open (095) scroll only when following, or must the last row be made visible even when the user had scrolled up? The criteria and decision (2) disagree on the second case in a way the spec doesn't resolve.
3. S3: The "Отдельный вопрос" about growing cards is answered by decision (2), but the MAUI section says `CardUpdated` must also be paired with row `SizeChanged`. Is `SizeChanged` on a row meant to replace `CardUpdated` or to supplement it, and what happens if both fire for one growth?
4. S4: The MAUI handler says "`VerticalDelta > 0` and reaching last index → `UserScrolled(true)`", but "last index visible" is explicitly not a measure of the bottom edge. Does the author accept that a tall last run may leave the bottom hidden while follow resumes?
5. S5: Step 4 says `OnTranscriptScrollChanged` must "запросить scroll, только если follower уже следовал" for extent/viewport deltas, yet the criterion says to scroll on content change regardless. Which governs?

RISKS:
1. Step 4 and 7 both classify scroll events by delta sign; a programmatic scroll and a layout-driven extent change in the same frame can be misread as a user gesture, flipping `IsFollowing` to false during a reply.
2. Step 7 `ScrollTo` with a `Dispatch` guard: `_programmaticScroll` is reset "после отложенного UI-dispatch", but if the `Scrolled` event fires synchronously or is coalesced, the guard may clear before or after the event, causing either a spurious `UserScrolled(false)` or a swallowed user gesture.
3. Step 7's MAUI `Scrolled` handling is fragile: `ItemsViewScrolledEventArgs.VerticalDelta` is not guaranteed to be signed consistently across Android and Windows handlers, and the Windows target is only checked by CI and manual step 016, so a sign inversion would go unnoticed until device testing.
4. Step 7 `SizeChanged` on row root views fires for every layout pass, including during `ReloadAsync` teardown when the view is being removed; `_active` alone may not prevent scroll on a detached `CollectionView`.
5. Step 4 `OnAppearing` resets the follower via `RowsChanged()` and requests a scroll even for an already-loaded model, but `OnDisappearing` detaches handlers before a pending `Background` callback runs, and the callback may still read a stale `_follower.IsFollowing` after re-appearance, scrolling the new view unexpectedly.
6. Headless Avalonia tests in step 3 expect `WaitUntilAsync` on "в конце" after 40 messages; with `Background`-priority scheduling and `RunJobs`, the test may pass vacuously if the initial layout already puts the list at the end before the scroll request, hiding the defect the step is meant to expose.
7. Decision (3) "возврат к концу включает" depends on `IsAtEnd` tolerance of 24 units; on high-DPI or large-font layouts the tolerance is in logical units while the bottom row may be taller, so the user can be "at end" by tolerance but not see the card bottom.
8. The `ReloadAsync` path clears and rebuilds `Items` on every action, so decision (1) means every re-render forces scroll-to-end; combined with `RowsChanged()` resetting `IsFollowing = true`, a user who scrolled up to read a message loses position on any background reload triggered by a generation status poll if one occurs.
