ASSUMPTIONS
1. The 2026-10-31 clarifications (full history indexed in one pass, separate "Meaning" mode) supersede the 2026-10-29 "Цель/Анализ" wording, and the plan section is the authoritative one. The spec does not say so explicitly.
2. `bge-m3` on OpenRouter returns 1024-dimensional float32 vectors and the `/embeddings` endpoint accepts a string array with a per-request input limit that the 64-item batch size respects; the spec defers this to a first call but the batch size of 64 is fixed in the plan.
3. The OpenRouter `usage.cost` field is returned for embeddings calls and its unit is unknown; the spec says not to label it USD until verified, so cost is treated as "unknown" until the first measured call.
4. `SessionChangeNotifier` already emits events for title, prompt, and image-description changes, not only for session creation.
5. The "Words" fuzzy search (079) and "Meaning" search are never merged; the UI shows two separate result lists, not one ranked list.
6. `runs.id` and `image_descriptions.id` are stable across Edit operations, or Edit creates a new run id as the spec says, so `prompt:<runId>` keys change on Edit and old vectors become orphaned rather than stale.

QUESTIONS
1. Stale-vector cleanup: when a prompt is edited (new run created), are the orphaned `prompt:<oldRunId>` rows deleted immediately, on the next pass, or never? The spec only covers deleting sessions and disabled mode.
2. The 10 000-text limit: is it applied before or after the "first 10 000 last" truncation on enable, and does the truncation apply to indexing (not indexed at all) or only to query-time memory? The text says both "перебор 10 000" and "поиск по первым 10 000 последним", which conflicts.
3. Mode switch semantics: if the user changes the active session list's search mode while indexing is running, does the "Meaning" control become disabled or does it query a partial index? The spec's disabled conditions list "индексация не завершена" but do not say whether partial results are shown.
4. Cost threshold: what is the confirmation dialog's cost estimate based on, given the unit of `usage.cost` is unknown and the spec forbids labelling it USD?
5. What is "Failed" recovery: after `Failed` on batch N, does EnableAsync restart from the beginning, from the last saved batch, or require explicit Retry?
6. Does Presentation or Avalonia test coverage have a fake OpenRouter client for the UI toggle tests, or are those tests expected to cover the transport layer too?

RISKS
1. Run-id keyed prompts (`prompt:<runId>`) mean an Edit on a prompt creates a new run, so the old vector is orphaned; with full-history indexing a single session edit may trigger repeated paid re-embedding of all unchanged texts if `content_hash` is computed on something other than the text alone.
2. The 10 000 text × 1024 float32 ≈ 40 MB figure is per-query memory, but the spec loads all vectors "при первом поиске" and keeps them cached; on Android (MAUI) this cache plus the LRU query cache could exceed reasonable heap limits, and the plan defers the measurement.
3. The 2-second debounce on `SessionChangeNotifier` recomputes all sources for a session, but a rename of a session with 200 prompts triggers a full session recompute, which may cause a burst of batched paid calls with no cost cap.
4. The batch loop writes each batch in its own transaction, but cancellation mid-batch after the HTTP response returns (paid but not persisted) is not addressed; the cost is recorded in the expense log only on success, so a cancelled-after-response call is paid and unrecorded.
5. Deleting a session cascades vectors via `ON DELETE CASCADE`, but in-flight batches that include that session's sources can still write vectors after the delete if the write is not guarded by a session-existence check in the same transaction.
6. Retries limited to 2 with 2 s and 8 s pauses are fixed in the plan, but the spec does not say whether `Retry-After` from a 429 response is honoured; ignoring it can trigger repeated 429s that consume the retry budget while still being charged by OpenRouter if any partial processing happened.
7. Cosine similarity on a zero-norm vector is skipped, but a NaN check happens only on the response; a NaN could still arise from normalization of a zero vector in the query path, so the query path needs its own check (not stated).
8. Quality acceptance relies on a 20-query manual run by the owner with a live key, with no defined pass threshold (the spec forbids inventing one), so the release gate is undefined in practice.
9. The Presentation test for the "Meaning" toggle depends on the state of `SemanticIndexService`; if the index-status read races with an indexing pass, the toggle may flip incorrectly, and the spec does not describe a state-change notification mechanism.
