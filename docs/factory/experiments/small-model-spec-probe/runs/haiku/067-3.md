ASSUMPTIONS
1. The spec's "≥ 840" breakpoint is a window width in logical px and applies identically to Avalonia's `ChatView` and MAUI's `ChatPage` (MAUI `AdaptiveTrigger` uses window width too, but the spec does not say whether the threshold is inclusive at exactly 840).
2. Tickets 066 and 072 supply the existing left-column markup, the `ConfirmAsync(..., destructive: true)` overload, and `SessionsPageModel` as a singleton; none of this is in the spec itself.
3. The 272 px column width and all colours, fonts and icons come from `docs/design/implementation.md` and `tokens.json`, and the prototype matches them.
4. `SessionItemViewModel` already exists with a settable or observable `IsCurrent`, and `ChatPageModel` can be loaded without a `SessionsPageModel` instance being present.

QUESTIONS
1. Which navigation semantics does "заменяет текущий чат" require: should the sessions list page stay underneath (so Back goes to the list) or should Back exit the screen entirely? The spec says Back "ведёт к списку" in the test, but the criteria do not state it.
2. On narrow screens, should selecting a session from the list open the chat through the same `ReplaceAsync` path, or through the existing push navigation? The spec only covers the wide layout.
3. What happens when the window is resized across 840 while a chat is open: is the list shown or hidden immediately, and is the selected session preserved?
4. Who owns the "New session" action on the chat screen: does it create a session and replace the chat, and what happens to an unsaved or empty current session?
5. What should happen when the currently open session is deleted from the embedded list: is the chat cleared, and to which session does the view move?
6. The spec says "Зависит от: 066, 072" but the plan also says to make the `INavigationService` change only "если нужен". Is the navigation decision made in advance, or is it left to the implementer?

RISKS
1. Plan step 2 and the "Проверка" commands rely on `$ANDROID_HOME` and an Android SDK; if the environment lacks them, the MAUI build step cannot pass and the plan gives no fallback beyond `blocked`.
2. The `ICurrentSessionTracker` event is raised from `ChatPageModel` load; if `SessionsPageModel` subscribes after the chat has already loaded, the initial `IsCurrent` mark is lost, so the subscription order and a current-value read on subscribe are needed.
3. Replacing the top page via `ReplaceAsync` in Avalonia may leave the previous chat's ViewModel alive or disposed twice, and the plan does not mention disposal of the old `ChatPageModel`.
4. Two `SessionsListView` instances (one on the list page, one inside the chat) share one `SessionsPageModel` singleton; any per-instance state such as selection, scroll position or `CommandParameter` bindings may conflict between them.
5. The plan mandates a Shell route like `//sessions/chat?...` for MAUI, but a `//` absolute route resets the navigation stack, which may break the Android hardware back button behaviour the spec expects.
6. `AdaptiveTrigger` on MAUI and the width handler in 066 on Avalonia are two different breakpoint mechanisms; the spec does not say they must agree at exactly 840 px, so they may switch at different widths on the two platforms.
7. The Android target is built on Linux, but the spec says runtime verification is manual (016), so the `SelectSessionInChat_ReplacesChat` behaviour is not covered by any automated test on MAUI.
8. Plan step 0 changes `SessionsPageModel.Delete` to use a destructive confirm; if the same model is also used by the embedded list in chat, deletion of the current session has no defined follow-up (see question 5), so the test would pass while the UI breaks.
