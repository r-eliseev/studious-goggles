ASSUMPTIONS
1. The mockup `docs/design/prototype.html` and the published artifact are the source of truth where the spec and the mockup disagree; the spec never says which one wins.
2. Resource keys such as `IgUserMessageAlignment`, `IgRoleFont`, `IgCardShowShortMeta` and `IgRadiusMd` already exist in `implementation.md` or will be added exactly as named; the spec says to add `IgCardShowShortMeta` to the dictionaries of 061 and 062 but gives no value.
3. Task 025's decision on `GenerationItemViewModel` (dated 2026-10-28) is already merged into the codebase, so the plan can build on its current shape rather than the pre-025 one.
4. `Generation` exposes `CreatedAt` and `CompletedAt` so `TimeText` can be computed, and the spec does not confirm either field exists.
5. The 3:2 image ratio and the 780 px max width are fixed values that apply to all three breakpoints unless `implementation.md` says otherwise.

QUESTIONS
1. The spec says the notice text is "per card, decision of the owner in 074", but 074 is described elsewhere as "Try again", so which task actually decides where the notice lives: this one or 074?
2. The "Filtered" text is given in English, but the spec does not say whether it is localised or whether the `IgWarnSoftBrush` and `Filtered` icon names are exact keys in `implementation.md`.
3. "Repeat and other actions stay as they are" conflicts with "one row of icon buttons": do the existing buttons get restyled to icons now, or is only the layout changed?
4. Step 5 says `docs/specs/chat-sessions.md` must not change, yet step 2 adds a new resource key that the docs describe; should `implementation.md` alone carry the key?
5. For the "running" state, is the placeholder an indeterminate `ProgressBar` only, or does the spec also require the "Assistant is thinking…" indicator to be a separate element, and where does it appear?
6. The acceptance criteria require the seed and time in the overlay on desktop only on hover, but the spec does not say what happens with keyboard focus or touch on desktop.

RISKS
1. Step 1 depends on `HeaderText` being recalculated when generations change, but the plan offers two options (a `PropertyChanged` subscription or recalculation from `ChatPageModel`) without choosing one, which invites inconsistent updates.
2. The Avalonia `:pointerover` pseudo-class does not apply on touch devices and does not fire reliably on the first hover after a layout change, so the overlay's visibility rule may behave differently from the spec's "on phones always" requirement.
3. Step 2 uses `IsVisible={DynamicResource ...}` bindings with a boolean-like resource; Avalonia's `DynamicResource` does not coerce strings to booleans, so the `IgUserMessageRoleVisible` and `IgCardShowFullMeta` bindings can fail silently and leave elements visible or hidden.
4. The `ProgressBar IsIndeterminate` placeholder under the image on a running card has no defined size, so the 3:2 ratio of the card may shift while the job runs.
5. The spec makes the `GenerationStatusKind` enum and `IsQueued`/`IsFiltered`/`IsCancelled` booleans both, so the status can be set in two places that disagree; there is no rule for which is the source of truth.
6. MAUI `OnIdiom` is evaluated once at page construction, so rotating a tablet or resizing a desktop window across the 840 px threshold will not switch between 2 and 3 columns unless the layout is handled separately.
7. The plan says to stop with `blocked` if a step fails, but the verification commands include `dotnet build` for Android, which needs `$ANDROID_HOME` set; the spec does not say what the agent should do if it is absent on Linux.
8. The "Cancelled" status has no placeholder, text or icon defined in the acceptance criteria, so a cancelled card may render blank.
9. The `Failed` status shows the error text, but the spec does not say whether that text is the raw provider message, which can be long or contain sensitive data, and does not limit its length.
