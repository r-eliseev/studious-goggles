ASSUMPTIONS
1. `RefreshAsync` currently builds `TotalText` with the sum of all rows in the period, and `rows` contains only USD entries; no currency conversion or mixed-currency rows exist.
2. `AppResources.CostFormat` (`${0}`) is used the same way in `CostTextOf` and `ChatPageModel.FormatEstimate`, so reusing it here is the intended consistency target.
3. The `"0.####"` pattern produces the same output for `CostTextOf` and the new total, including for values like 0.0345 and for `0` (which the spec says must render as `$0`, but `0.####` on zero yields `0`, so the result matches only if the pattern formats zero this way).
4. The test fixture for `RefreshAsync_MonthPeriodGroupsByProviderAndModelAndCountsUnknown` can be reused without changing its setup, and the "current month" is determined from a clock the test can control.

QUESTIONS
1. The acceptance criteria say zero shows as `$0`, but `0.####` formats 0 as `0`, so `$0` only results if the code special-cases zero; should the spec state which mechanism guarantees this, and is it the same behaviour as `CostTextOf` for zero?
2. Is the expected output `$0.0345` correct for the test sum 0.03 + 0.0045, given that the rounding or truncation rule for values below 0.0001 is not stated?
3. Should the group values (`SpendingGroup.TotalUsd`) and the total also be formatted with the same `$` rule, or does the spec intend to leave group rendering untouched on purpose, which would leave the screen showing mixed formats?
4. Does "в остальном приложении" mean `CostTextOf` and `FormatEstimate` already use identical code, or do they differ, and if they differ, which one is the reference?
5. Does the task require the total to reflect a culture-independent decimal separator, given that the spec only says `InvariantCulture` but the test asserts a dot, which may conflict with a stated UI requirement for localized numbers?

RISKS
1. The planned test sets `CurrentCulture` only; if the code reads `CultureInfo.CurrentUICulture` or if the test runs in parallel with other tests that also change culture, the static culture swap can leak and cause flaky failures.
2. Summing `decimal` or `double` costs in the spec is not stated: floating-point addition of 0.03 and 0.0045 may produce a value like 0.034499999…, which with `0.####` rounds to `0.0345` but could expose precision issues for other values or for thresholds such as "sum below cent".
3. The `0.####` format on large totals (no thousands separator, no fixed grouping) may produce inconsistent output with other screens if they use grouping; this is not covered by the test plan.
4. The plan says to test only the Russian culture; cultures whose `CurrentCulture` uses a comma or other negative-number conventions are not exercised, so a regression could pass the single test.
5. If `rows` is empty, `Sum` returns 0 and the zero branch is needed; the plan does not include a test for the empty-period case, so the `$0` criterion is unverified.
6. The verification step runs `dotnet format --verify-no-changes` on two projects but the fix touches only the presentation project; if the test project lacks a required format configuration, the check may fail for reasons unrelated to this change.
