**ASSUMPTIONS**

1. The spec assumes `Convert.FromBase64String` skips exactly ASCII space, tab, CR and LF on both Linux and Windows. It does not name the .NET version, and the runtime may also skip other characters such as `\f` or `\v`. The guard's counting set must match the decoder's, or valid payloads are rejected or oversized strings pass the guard.
2. The spec assumes "MiB" means 1024×1024 bytes, that `ProviderResponseLimits.Image` caps decoded bytes, and that the 72MiB JSON cap is measured on raw UTF-8 bytes with escape sequences counted (`\r\n` costs 4 bytes, `+` may become `\u002B`).
3. The spec assumes "Unknown" is a defined result or exception type that both direct clients can surface. It never defines it.

**QUESTIONS**

4. "Зависит от: —" contradicts step 6, which says to return 112 to done only after 150 and 152, and the spec mentions 143 and 127. Which tasks actually block this one?
5. The criteria say invalid base64 "остаётся Unknown", but step 4 says the direct client keeps throwing `FormatException` and only the queued adapter maps it to Unknown. Which layer owns the Unknown contract?
6. Which whitespace positions are permitted: leading, trailing, between padding `=` characters? Are data-URI prefixes or URL-safe alphabets accepted? Step 4 requires tests for "всех разрешённых позициях", which cannot be written without this.
7. When whitespace pushes a 50MiB decoded payload over the 72MiB JSON cap, which limit should win? The criterion "decoded 50MiB принимается" does not answer this.

**RISKS**

8. With CRLF every 76 characters, a 50MiB payload is about 70MiB of JSON, close to the 72MiB cap. Denser whitespace makes the transport-level JSON limit reject payloads that the decoded-size check would accept, so the acceptance criterion cannot hold for all whitespace layouts.
9. Production-constant boundary tests hold a ~67–70MiB JSON string, its UTF-16 copy (~135–140MB) and a 50MiB decoded array per test. The non-parallel collection limits concurrency but not total memory or CI time, and the spec sets no budget.
10. The criterion that errors and logs contain no base64 is not covered by the plan, which forbids changing debug logging in step 6. If existing response-body logging or exception wrapping already prints payloads, this fix leaves that leak in place.
