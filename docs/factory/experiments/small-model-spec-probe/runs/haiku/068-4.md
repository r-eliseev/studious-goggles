ASSUMPTIONS
1. The three external docs (`implementation.md`, `tokens.json`, `prototype.html`) and ADR 0014 are in the repo at the stated paths and are the source of truth for resource keys, values and icon names; the spec does not say what to do if they disagree with the plan text.
2. Tasks 025, 055, 057, 063, 064, 067 are already merged, so `GenerationItemViewModel` and `RunItemViewModel` have the shape the Analysis section describes (e.g. `DetailsText`, `SummaryText`, `RunPromptFormat`).
3. `Generation` carries `CreatedAt` and `CompletedAt` (or equivalent), and the seed/cost/model fields exist, since the spec says "проверить" for time but not for the others.
4. Keys `IgCardShowShortMeta`, `IgUserMessageRoleVisible`, `IgRunBorderThickness` and similar exist or will be created in the theme dictionaries of tasks 061/062 in the same resource format on both Avalonia and MAUI.
5. "Actions stay as is" means the current action buttons are reused unchanged and only re-laid out into one row of icon buttons; no new commands are needed.
6. The Presentation layer already exposes a way to know whether a parameter was dropped or a seed was not applied (`Update_SeedNotApplied_ShowsSeedNotSupported`, `Update_DroppedParameter_FillsNotice`), i.e. the data is available, not just the text.

QUESTIONS
1. Step 1 says `HeaderText` is updated via a `PropertyChanged` subscription on generations or recomputed in `ChatPageModel`. Which one is intended, and who owns the recalculation when a generation changes status?
2. The Criteria say the Gallery shows model and cost under the image, but the Analysis says `NoticeText` (parameter lines) is per card, not under the prompt. Is `NoticeText` shown in the card body, under the image, or in the short block? The spec references "решение владельца в 074" but task 074 is described as "Try again", which looks like a mismatch.
3. The Criteria list six statuses but the Analysis `GenerationStatusKind` lists six values including `Running`; how is "идёт" mapped to `Running`, and what does `IsQueued`/`IsFiltered`/`IsCancelled` add beyond `StatusKind`? Two sources of truth for one status is a risk.
4. The Filtered and Failed card texts: the spec gives the exact Filtered text but not the cancelled text or the error-state layout. What text, and is "Cancelled" a status label with text only, or does it carry a placeholder?
5. Which resource set governs the Notebook frame on MAUI, given the spec says the MAUI page uses `StyleClass` but the Gallery/Notebook differences are in `implementation.md` section 2.4? Is section 2.4 identical for both platforms?
6. The Plan says "phone: 2 columns (`OnIdiom`)" but the Avalonia part says "2 columns below width 840". Are the breakpoints meant to be the same on both platforms?
7. Step 4 names test `GalleryStyle_UserMessageAlignedRight`; how is "Gallery" selected in a headless test, and where is the style switch defined?
8. Is `docs/specs/chat-sessions.md` supposed to stay unchanged even if the new `IgCardShowShortMeta` key changes behaviour described there? The spec says "поведение то же", which should be confirmed.
9. The verification list includes `scripts/check.sh` but does not say what it runs; is it expected to pass without the Windows/desktop checks (016, 046), and does it include the MAUI Windows target?

RISKS
1. Step 2 places `IgCardShowOverlay` on `:pointerover` with `IsVisible`, but `IsVisible` bound to a pointer state is not a Avalonia pseudo-class; the hover reveal likely needs a style selector or `Opacity`, and the spec does not say which.
2. The spec asks that `IgCardShowFullMeta` and `IgCardShowShortMeta` be inverse values via two separate resources, which is fragile: if one is updated and the other is not, both blocks show or both hide. A single source would be safer, but the spec fixes the two-key design.
3. `DynamicResource` bindings to `IgUserMessageAlignment` (a horizontal alignment value) and `IgRunBorderThickness` (a thickness) must be typed correctly in both XAML dialects; a wrong type fails at runtime, not at build, so `dotnet build` and `dotnet test` may pass with a broken layout.
4. The Plan's TDD ordering is inverted for the Avalonia view: step 2 builds the view before step 4 writes the view tests, so the "red" test is written after the code is already in place.
5. The "stop and report `blocked`" rule in the Plan is good, but the MAUI build requires the Android SDK and `$ANDROID_HOME`; if the executor environment lacks it, the Plan has no fallback and the step will stall.
6. `ProgressBar IsIndeterminate` for the running state inside a `WrapPanel` of cards can cause repeated layout passes and visible jitter; the spec does not mention virtualization for a long chat feed.
7. `RunItemViewModel.HeaderText` recomputed on each generation change while generations stream in can trigger many `PropertyChanged` events; the spec does not address throttling or the thread on which these updates arrive (UI thread vs background).
8. Cancelled and queued generations may have no `CompletedAt`, so the time calculation `CompletedAt - CreatedAt` can produce a negative or null value; the spec only says "если есть", without a rule for the missing case.
9. Concurrency with tasks 025, 055, 057 that touch the same files: the spec does not state a merge order or who rebases, so the executor may overwrite changes from those tasks.
10. The Gallery/Notebook style is applied via resources only, but the Criteria forbid "проверок стиля" in markup; the Step 4 tests check alignment and border presence, which may require style checks in tests and could be read as a contradiction with the rule.
