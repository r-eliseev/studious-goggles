ASSUMPTIONS:
1. The spec's "Items" and "CardUpdated" names refer to the actual `ChatPageModel` members, and `ChatPageModelTests` helpers (`StartRunAsync`, `WhenIdleAsync`, `release`) already exist exactly as used in the test steps.
2. `ShellHarness`, `SummaryMarkerTests` and `IChatMessageRepository.AddAsync` behave as the spec's test steps assume, including that `Routes.ChatFor` navigation completes before `WaitUntilAsync` begins.
3. Card and run rows in the Avalonia and MAUI transcripts are views whose size can change after the `CardUpdated` event, so the `SizeChanged` hook on row roots is the intended way to detect image-driven growth.
4. `TranscriptFollower` is a pure policy class with no platform types, and the `offset/viewport/extent` values passed to it are in the same units on both platforms.

QUESTIONS:
1. Step 3 asks that the "scrolled up" test show `t.Offset.Y == 0` after a window resize, but the decision list says a resize scrolls only when following. Is the expected behaviour for a resize while scrolled up "stay put" (as tested) or "keep the same distance from the end"?
2. Decision (1) says any `Items` change scrolls to the end even if the user scrolled up, but step 4 `OnItemsChanged` routes through `RowsChanged()` which also sets `IsFollowing = true`. Does a user who is reading history lose their position on any reload, including the "Новый seed" action, and is that the intent?
3. `ViewportChanged()` is wired to size changes in both shells, but the keyboard case (095) may arrive as an insets change rather than a size change on Android. Which signal does 095 actually produce?
4. The MAUI `Scrolled` handler treats `VerticalDelta < 0` as "user scrolled up" and always disables follow, but `ItemsUpdatingScrollMode`/`ScrollTo` and layout-driven growth can also produce negative deltas. How is programmatic versus layout motion distinguished on MAUI, given the spec only guards `_programmaticScroll` and `_scrollPending`?
5. The plan says the pending callback "scrolls to the last index" but the Avalonia step asks for `ScrollToEnd` and MAUI asks for `ScrollTo(..., End)`; when a row grows after the last index is already visible but its bottom is clipped, what defines "bottom visible" on MAUI, which exposes no offset/extent?

RISKS:
1. `OnTranscriptScrollChanged` in Avalonia calls `UserScrolled` from `OffsetDelta.Y` without guarding against content/viewport-driven offset changes that happen during `ScrollToEnd`; the `_scrollPending` guard may drop a real user gesture that arrives in the same dispatch window.
2. The MAUI `Scrolled` event fires with `VerticalDelta` values that may be reported after the programmatic `ScrollTo` completes, so resetting `_programmaticScroll` "after the deferred UI dispatch" may either swallow a user drag or re-trigger a `UserScrolled(true)` on the last index.
3. Repeated `OnAppearing`/`OnDisappearing` with unsubscribe-then-subscribe can leave a pending `Dispatch` callback that captures the old `_model` or `Transcript`; the spec says to read the current one but does not say how a removed page is detected.
4. Row-root `SizeChanged` handlers in MAUI fire for every row during initial layout and during `CollectionView` recycling; with `ContentChanged()` returning `IsFollowing` this can cause repeated scroll requests on open, and the spec does not bound the rate.
5. `ReloadAsync` clears and rebuilds `Items` on every action, so `RowsChanged()` always forces follow; combined with `OnItemsChanged` firing for each Reset/Add in a rebuild, the pending guard is the only throttle, and its behaviour under a rebuild that is itself interrupted by navigation is untested.
