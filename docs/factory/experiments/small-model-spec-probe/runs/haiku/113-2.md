ASSUMPTIONS:

1. The Data implementation of `UpdateGenerationAsync` is the only write path for generation status, so no other code updates the same row without going through this method.
2. "Safe" ids (GenerationId, SessionId, ProviderId, Status) are non-sensitive for operational logs, and a prompt, API key, or URL never appears in them.
3. `CapturingLogger` (from 110) already exists in main, or the spec's "локально совместимо" fallback is acceptable; the spec does not say which.
4. The `GenerationUpdated` event handler is invoked synchronously or via a known dispatcher, so "subscriber exception after successful DB write" can be isolated from the persistence path.
5. Own cancellation (task 108) is identified by a specific token or flag, and the spec assumes `Launch` can distinguish it from an unexpected `OperationCanceledException`.

QUESTIONS:

1. Criterion "zero/multiple rows → non-transient" conflicts with step 2, which says multiple rows is unreachable by schema. Should the multiple-rows branch be tested at all, or only documented?
2. Step 5 says "LogStatus выполняется ровно один раз на подтверждённый transition", but the Running-status failure path (criterion 4) also needs a status log. Is a failed Running write logged as a transition, and if so, with which status?
3. Criterion "operational Error содержит только безопасные ids/status" and step 6 "не пытаться сохранять второй Failed status" — should a supervisor-observed failure leave the generation in its last persisted status (e.g. Running) indefinitely? The spec does not state the resulting DB state.
4. Step 5 says the subscriber exception is logged "выше Debug" with safe ids, but the subscriber's own exception message may contain sensitive data. Is the same redaction rule applied there?
5. Does `WhenIdleAsync` need to complete only after the supervisor observed the failure, or may it complete earlier? The criterion says "без fault" but not on what condition.

RISKS:

1. Step 1 says `StorageWriteException` carries `IsTransient` and that zero-row sets it false, but the real `SqliteException` (e.g. SQLITE_BUSY, locked) is not mapped; a transient DB error could surface as a non-transient exception, breaking the retry in task 125.
2. The `RunRepository` guard "count != 1" runs after `ExecuteNonQueryAsync`; if the update succeeded partially or the connection is in a transaction, the count check alone does not guarantee the write is durable, so "confirmed update" may be overstated.
3. Step 5 removes the catch around the repository update, but if `LogStatus` runs after the update and throws, the transition is persisted without a log entry and the event is not published; the spec does not define that path.
4. Step 6 relies on catching an unexpected exception before `finally`/removal; if `Launch` is async and the exception occurs after `await` continuation on a different context, the `_running` removal and slot release may race with `WhenIdleAsync`'s completion check.
5. Step 7 requires the provider not to be called after a Running update failure, but if the provider call is already started concurrently for another job sharing a provider client, the slot-release test may pass while the provider concurrency invariant is not verified.
6. The boundary test in 106 (step 8) changes expectations from "no fault" to "fault observed by supervisor"; if other callers rely on the previous silent behaviour, the change may break them without a listed file in the file list.
