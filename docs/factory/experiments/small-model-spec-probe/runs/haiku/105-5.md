ASSUMPTIONS

1. The spec's "Уточнение 2026-10-31" overrides the earlier analysis where they conflict: whole history is indexed in one pass at enable time, and "Meaning" is a separate mode whose results are not merged with word search. I assume the earlier "fuzzy/semantic score merge policy" question is therefore closed.
2. `ExpenseKind.Embedding` and the 021 expense journal (stage A) are assumed to exist in main; the plan says stage 2 cannot close without them, but does not say what happens if they are missing at implementation time.
3. Source keys `title:<sessionId>`, `prompt:<runId>`, `desc:<descriptionId>` are assumed to be stable across edits. The spec says an Edit creates a new run, so the prompt key changes and the old vector must be deleted; the spec does not say that explicitly.
4. The "10 000 most recent" cap is assumed to apply to sources, not sessions, and to be applied at indexing time, not at search time.

QUESTIONS

1. "Уточнение" says the "Meaning" toggle is disabled when indexing is incomplete, but the plan also describes incremental re-indexing after edits (2 s debounce). Is "Indexed" a sticky Ready state after the first full pass, or does every edit flip it back to Indexing and disable Meaning search?
2. The spec requires a confirmation with the source count and "paid", but cost is unknown in unit (`usage.cost` unit unverified). What does the confirmation dialog show as the price estimate, and what is shown if the first call reveals an unexpected unit?
3. Re-indexing of old data is listed as a required decision before `planned`, and the 2026-10-31 decision says "indexed at once". Is the bulk pass the only enable path, or is there a resume-after-crash UX and a way to re-run it after a model change (dimension change, model id change)?
4. Where is the 10 000 cap enforced for the query side versus the index side? "Сверх неё — сообщение в журнал и поиск по первым 10 000 последних" does not say what "last" means (by created_at, by session date, by source key) or whether the user sees the truncation in UI.
5. The privacy rule forbids sending anything except allowed texts, but the spec does not say whether the query string typed by the user is sent to OpenRouter, nor whether it is cached (LRU of 50 by query text) in a way that persists beyond the session.
6. Phase 3 says "косинусная близость по всем векторам", but does not state whether vectors are L2-normalised at write time, and whether the zero-norm skip is applied before or after the cache lookup.

RISKS

1. Memory: 10 000 × 1024 float32 ≈ 40 MB is stated as a fact, but the spec says the vector dimension must be measured first. If the model returns a different dimension (or the provider returns float64 or base64 by default), the 40 MB estimate and the 10 000 cap are both wrong, and the "load all vectors on first search" cache has no eviction policy.
2. Re-embedding on edit: `content_hash` is SHA-256 of the normalised text, but the normalisation rule is not specified. Whitespace or case changes could trigger paid re-indexing, or conversely a meaningful change could be missed if normalisation is too aggressive.
3. Partial batch failure: a retry policy of 2 retries for 429/5xx with a 2 s and 8 s pause can still charge for batches that the provider accepted but the client timed out on. The spec says each successful batch is saved, but does not say how a timed-out-but-billed batch is recorded in the expense journal.
4. Session deletion during an in-flight batch: the plan says the response must not be written, but the cost of that batch is still incurred and must still be journalled; the spec does not say whether the cost is recorded against a deleted session.
5. Concurrency between indexer and edits: the 2 s debounce plus a single in-flight request can race with a rapid second edit; the spec does not define whether the second edit's hash is compared against the stored hash or the in-flight batch's hash, which can cause a stale vector to be stored under the new text.
6. Disable and re-enable: `DisableAsync` deletes vectors, but `StopAsync` leaves saved batches. After disable-then-enable, the spec does not say whether a stopped pass with a changed model or dimension is detected and the old vectors discarded, so mixed-dimension vectors could coexist in one table.
7. Platform: the file `search.json` lives in the data folder on both Linux and Windows, and on MAUI Android the data folder is app-private. The spec does not address the atomic write of this flag file relative to the SQLite transaction; a crash between the two leaves the flag and the data out of sync.
8. Cancellation of query: the LRU cache keyed by (model, text) stores vectors for queries that were cancelled mid-flight, and a stale response is only stated to be "not written" for indexing, not for the query path.
