ASSUMPTIONS

1. The `docs/design/implementation.md` key names, values, and icon names (`Repeat`, `NewSeed`, `Edit`, `Describe`, `More`) exist and match the prototype exactly, since the plan says to copy them verbatim without giving them in the spec itself.
2. `GenerationItemViewModel` already exposes `ModelText`, `SeedText`, `CostText`, `TimeText`, `IsFinished`, and the existing Repeat/New seed/Edit/Describe/Write-from-image commands, and the `Describe image` and `Write a prompt from image` actions are the same command set as the card's five buttons.
3. `CommunityToolkit.Maui` is already referenced in the MAUI project and its installed version provides `TouchBehavior.LongPressCommand`.
4. Error and filtered generations keep only the Repeat button visible; the spec does not say whether they also get the ellipsis/long-press menu on phones.

QUESTIONS

1. Item 1 of ASSUMPTIONS in the spec: the spec says the bottom menu on phones shows a title with model, seed, price, and time, but does not say what happens when a value is empty (e.g., no seed for a failed generation) or how the separator is handled then.
2. The spec lists "Write a prompt from image" in the menu, but the planned `ChooseAsync` options list and the tests `ShowActions_ChoosesRepeat_RunsRepeat` and `ShowActions_Cancel_DoesNothing` do not say how option labels map back to commands; should labels be localized, and how is a label-to-command mapping kept stable across localizations?
3. The spec says "ShowActionsCommand is available when IsFinished", but the Avalonia error/filtered card requirement (Repeat always visible) is not reflected in the menu rules; should the menu be available for error and filtered items, and with which actions?
4. Is `ChooseAsync` expected to return an index or the label string? Returning a localized string makes the mapping fragile when two options share text.
5. The plan says `dotnet build ... -f net10.0-android` runs on Linux, but the spec's environment section says Windows-target and Mac behaviour (MenuFlyout) is verified only by CI or manual check; which tests cover the Windows/Mac `ContextFlyout` path at all?
6. The plan references `ShellDialogService.cs` and `ChatPage.xaml`, while the Analysis section refers to `ChatView.axaml`; the MAUI file names and page class are not confirmed in the spec.
7. The dependency on tasks 068 and 072 is stated, but the spec does not say what those tasks change in `AvaloniaDialogService`; the merge order and conflicts are unknown.

RISKS

1. Plan step 3 says there is no ready-made long-press gesture in MAUI and proposes `TouchBehavior.LongPressCommand`; this is a toolkit-specific API whose availability and exact member name depend on the toolkit version, and the plan's "проверить версию" leaves the executor to guess. If it does not compile, the plan requires `blocked`, which the spec should expect.
2. `Border.card:focus-within` is not a standard Avalonia selector; Avalonia has `:focus-within` only in some versions, and the spec's claim that focus-within reveals the buttons may not work, which would break the keyboard accessibility requirement.
3. Long-press and right-click (ContextFlyout) on a card that contains buttons may conflict: inner button clicks can swallow pointer events, so the menu may not open or may open on the wrong element.
4. On Avalonia, showing the action row by `:pointerover` on touch-only devices or with pointer leaving the card mid-click can cause the buttons to disappear before a click registers (flicker).
5. `ChooseAsync` on MAUI via `DisplayActionSheet` returns the cancel label or null when dismissed; the plan's `ShowActions_Cancel_DoesNothing` must handle both null and the cancel string, and on Android the back button may return differently.
6. Modal dialogs opened from `ShowActionsCommand` while a generation is in progress or being updated could act on a stale item; the spec does not say what happens if the item state changes while the menu is open (e.g., Repeat becomes unavailable).
7. Running `Repeat`/`Edit` from the menu may trigger navigation or prompt-dialog flows that themselves call `IDialogService`, creating nested dialogs on Avalonia where the dialog implementation is a window, which can deadlock or stack incorrectly.
8. The plan's TDD step expects the menu logic to be tested via `IDialogService` substitution, but the menu's title composition with empty values and the "не придумывай обход" stop rule make it likely that a small model stops at step 2 on the Avalonia XAML compile error without a clear fallback.
