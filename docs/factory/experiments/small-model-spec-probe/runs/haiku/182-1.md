ASSUMPTIONS
1. The "Тест при CurrentCulture = ru-RU" criterion assumes that setting `CultureInfo.CurrentCulture` is enough to change the behaviour under test, but the spec does not say whether the test or the production code uses `CurrentCulture` or `CurrentUICulture`, nor whether `ru-RU` is available on the CI Linux image (ICU/invariant globalization mode).
2. "Сумма 0.0345 → `$0.0345`" assumes that `SpendingGroup.TotalUsd` and the journal sum are `decimal`; if they are `double`, the `0.####` formatting and the expected string may differ through floating-point rounding.
3. The fix assumes `CostTextOf` and `ChatPageModel.FormatEstimate` use the same `0.####` pattern and the same `AppResources.CostFormat`; the spec cites them but does not confirm their current code.
4. "Ноль показывается как `$0`" assumes that a zero total is produced by `0.####` (which yields `0` for zero, not `0.0000`), and that an empty journal also yields a total of zero, not an empty or hidden label.

QUESTIONS
1. The plan says to fix only `TotalText`, while the Analysis says the groups are formatted in markup. Does the group-level cost text in markup also need `$`/invariant formatting, or is it out of scope?
2. Should the total be rounded to a fixed number of decimal places before formatting? With `0.####`, a sum such as 0.00001 becomes `$0` while the spec says "всё меньше цента округляется до нуля" is the defect, so it is unclear what the expected output is for very small non-zero sums.
3. The spec says "Файлы" are only two files, but the Analysis mentions `AppResources.CostFormat`, which lives elsewhere. Should it be verified or changed, and is it localized per culture (resource files for `ru`)?
4. Is there a case where the total should be shown in the system currency (e.g. a user setting for currency), which the current `C` format was meant to support? The spec does not say whether the USD-only decision is final.
5. The "Порядок исполнения" section says to stop and ask if the code diverges from the plan, but the plan's test name pattern and the existing test name are not verified against `main`. Who confirms the current state before the failing test is written?

RISKS
1. Changing `CurrentCulture` in the test with a manual `try/finally` is not safe if the test runs in parallel with other tests in the same class or assembly, since `CultureInfo.CurrentCulture` is process/thread-scoped and can leak into other tests.
2. On Linux with ICU missing or in invariant globalization mode (`InvariantGlobalization=true`), `new CultureInfo("ru-RU")` may throw or silently fall back to invariant, so the test may pass for the wrong reason. The failing-first step should prove the test actually fails before the fix.
3. Culture-sensitive comparison of the result string: `"$0.0345"` is compared with `Assert.Equal`, which is ordinal, so this is fine, but the `$` in `AppResources.CostFormat` passed through `string.Format` with a culture-sensitive `{0}` argument could still introduce separators if the formatted number is not already invariant; this must be verified after the fix.
4. `decimal` sums of many small journal entries may not equal the expected value exactly if the journal stores `double` values converted to `decimal`, which may produce `0.03449999` and fail the `$0.0345` expectation in a way unrelated to culture.
5. Shared formatting logic is being duplicated instead of extracted (the spec explicitly defers this to task 186), so `CostTextOf`, `FormatEstimate`, and the new code can drift apart if `CostFormat` or the pattern changes before 186 lands.
6. The plan does not state how `RefreshAsync` behaves on a journal read failure or when the page is refreshed concurrently; a stale `TotalText` could be displayed from a previous run if the new assignment is skipped on an exception path.
7. The check command `bash scripts/check.sh` is not described; if it runs `dotnet format` or other tools that modify files, the "verify-no-changes" steps may conflict with it, and its contents are unknown to the reviewer.
8. Running `dotnet test` steps sequentially is required by the plan, but the verification commands in the spec pass `--project` to `dotnet test`, which is not a valid option for the `dotnet test` command in the standard SDK; the correct form is passing the project path as a positional argument.
