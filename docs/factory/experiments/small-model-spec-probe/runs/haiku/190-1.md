**ASSUMPTIONS**

1. The spec does not say how `FileImageStore` learns the data folder root. I would assume it is the same folder where `DefaultAssistantModelFile.SaveAsync` writes `defaults.json`, since step 2 scans that root.
2. Step 2 requires a Warning on failure, but the spec does not say how `FileImageStore` gets a logger. I would assume an `ILogger` is injected, though neither the constructor nor the DI registration is described.

**QUESTIONS**

3. Step 2 says the scan runs "в фоне", but step 4 awaits `Task.Run(...)` inside `InitializeAsync`. Does startup wait for the whole scan, and if so, is that acceptable for a large `images/` tree?
4. Where in `InitializeAsync` is the call placed relative to `GenerationService` and other startup work? The spec does not say whether an image write can already be in progress when the scan runs.
5. Which `TimeProvider` does the Presentation test use to make files "two hours old"? Step 4 registers `TimeProvider.System`, and the spec does not say whether a controllable provider is referenced in the test project.

**RISKS**

6. The "запуск не падает" criterion covers only per-file delete errors (`IOException`, `UnauthorizedAccessException`). `Directory.EnumerateFiles(..., AllDirectories)` can throw partway through enumeration on an inaccessible subfolder, which would abort the traversal or fail startup. The spec does not say enumeration errors are caught.
7. Age is judged by `now` from `TimeProvider` against `File.GetLastWriteTimeUtc`. A forward clock jump, a timezone or UTC mismatch, or a network share with coarse timestamps could make a fresh in-progress temp file look older than one hour and delete it.
8. The scan does not account for a live writer. Another app instance on the same data folder, or a write stalled for over an hour, could lose its temp file, and then `File.Move` in `AtomicImageFileWriter` would fail. The spec does not define that failure path or assume single-instance operation.
9. The name patterns are duplicated from `AtomicImageFileWriter` and `DefaultAssistantModelFile`. If either template changes, the cleanup silently stops working, and nothing in the plan ties the two together.
10. Adding a method to `IImageFileStore` in Core forces every implementation to change, including test doubles in projects outside the verification list (for example, MAUI platform code). The ShellHarness check is still open ("проверить, вручную ли").
