ASSUMPTIONS

1. The "ready" state that gates the action row and `ShowActionsCommand` is `IsFinished`, and error and filtered generations are treated as finished too, though the spec only states the Repeat-always-visible rule for them.
2. Existing `GenerationItemViewModel` commands (Repeat, New seed, Edit prompt, Describe, Write prompt from image) already exist and can be invoked directly from a single dispatch point, so no new commands are needed.
3. Tasks 068 and 072 have already landed in `AvaloniaDialogService` and `IDialogService`, and their current method signatures are the ones the new `ChooseAsync` must sit alongside.
4. `CommunityToolkit.Maui` is already referenced in the MAUI project at a version that actually ships `TouchBehavior.LongPressCommand`; the plan itself says "проверить версию".

QUESTIONS

1. Should Repeat on error and filtered cards be the only visible action there, or should the rest of the row be hidden and the menu reduced to Repeat alone? The spec says Repeat is "always visible" but does not state what happens to the other buttons.
2. Which platforms should use `ActionSheet` versus `MenuFlyout`? The criteria say phones use `DisplayActionSheet` and Windows and Mac use `MenuFlyout`, but the MAUI project also targets Android and iOS tablets, and the spec does not say which branch a tablet takes.
3. The spec says the action sheet title is "модель, сид, цена, время" joined by " · ", but does not say how a missing or null `SeedText` or `TimeText` is rendered, or whether the title can exceed the platform limit.
4. Should `ChooseAsync` return the label string or an index, and how are localised labels mapped back to commands if the same string appears twice or the labels are translated?
5. Does the Avalonia "More" button open the context menu at the button or at the card, and must the context menu item set match the button set exactly, including Describe and Write-prompt-from-image, which the button row does not show as separate labels in the plan?
6. The spec says tooltips use `ToolTip.Tip` and accessible names, but does not say whether the strings come from `docs/design/implementation.md` keys or must be newly added; the plan says to copy strings verbatim, which assumes they exist there.

RISKS

1. The plan's CSS-like selector `Border.card:focus-within` is not a documented Avalonia selector; `:focus-within` may not exist, so the keyboard-focus reveal could silently never trigger and the row would be unreachable by keyboard.
2. `ChooseAsync` is async and modal; if the card is recycled or the item removed while the sheet is open, `ShowActionsCommand` may run its chosen command against a stale or disposed view model.
3. `ShowActionsCommand` is gated on `IsFinished`, but a generation can change state while the sheet is open (for example, a repeat started by another path), so the executed command may run against a state it no longer matches.
4. `DisplayActionSheet` on Android and iOS requires a page context through `Shell.Current`, which is null or wrong during navigation or while a modal is already presented, so the call can throw or return without showing.
5. `TouchBehavior.LongPressCommand` combined with a tap on the same card can conflict with scrolling in the chat list, causing accidental action sheets during a fling gesture.
6. `ContextFlyout` on Windows and `ContextMenu` in Avalonia are attached to the card, but the card also hosts the always-visible Repeat button on error cards, so right-click on that button may open the wrong menu or both.
7. Duplicate state transitions: if `ChooseAsync` returns null after the user taps Cancel and the platform reports cancel as a separate event, the plan does not define how the Presentation test distinguishes "cancelled" from "no option matched".
8. The build command passes `-p:AndroidSdkDirectory=$ANDROID_HOME` to a Linux host, but the Windows and Mac `MenuFlyout` branch is never compiled or tested by any step in the plan, so a platform-specific compile error there would only surface in CI.
9. The plan requires the agent to stop with `blocked` if a step fails, but the verification commands include `scripts/check.sh` with no defined pass criteria, so a partial pass could be reported as done.
