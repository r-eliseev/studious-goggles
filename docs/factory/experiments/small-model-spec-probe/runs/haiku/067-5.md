**ASSUMPTIONS**

1. Items 066 and 072 are assumed to already provide the left column that moves into `SessionsListView`, the `SessionsPageModel` singleton, `AvaloniaNavigationService`, and the `ConfirmAsync(..., destructive: true)` overload. If any of these differ, steps 0 and 3 cannot be done as written.
2. The 840 breakpoint and the 272 px column are assumed to use the same unit in both shells (DIP for the MAUI `AdaptiveTrigger`, `Bounds.Width` in Avalonia) and to match the prototype without DPI scaling. The spec does not say so.

**QUESTIONS**

3. On a wide window, does `SessionsView` still exist as a separate page at ≥ 840? Criterion 3 and test 5 say "назад — к списку", but the list is also embedded in the chat, so it is unclear what back should reach.
4. The spec leaves the replacement mechanism open ("выбрать при реализации": `ReplaceAsync` or a `//chat?` route), yet test 5 depends on it. Should the choice be made now?
5. What does the chat area show on wide when no session is selected, when the current session is deleted, or after "New session"? Does "New session" open the new chat immediately, or only add it to the list?
6. Step 0 (destructive confirm on delete) is not in "Описание" or the criteria. Is it in scope here, or does it belong to 072?

**RISKS**

7. When the user switches sessions while the previous chat is still loading or streaming, the old `ChatPageModel` may set `CurrentId` or update state after the new chat has loaded, leaving `IsCurrent` on the wrong item. The spec defines no cancellation or ordering rule.
8. Crossing the 840 breakpoint with a chat open changes the navigation stack shape, because wide mode never pushes a list page. Back after a narrow resize may therefore reach an unexpected page, and the spec does not define this.
9. In MAUI step 4, the `SessionsListView` inside `ChatPage` must have its `BindingContext` set explicitly to the singleton `SessionsPageModel`. Otherwise it inherits `ChatPageModel`, and the bindings fail silently with no build error.
10. The verification commands look unreliable as written: `dotnet test --project ...` is probably not a valid form, and `scripts/check.sh`, the `ANDROID_HOME` requirement, and the `net10.0-android` target are not described anywhere in the spec.
