ASSUMPTIONS:

1. The design keys, values, fonts and icon names referenced in `docs/design/implementation.md` (`Repeat`, `NewSeed`, `Edit`, `Describe`, `More`, `card-actions`, `ghost`, `icon`, `small`) exist there verbatim, and the Avalonia and MAUI styles that define them are already in the project.
2. Tasks 068 and 072 are already merged, so `AvaloniaDialogService` and `IDialogService` are in the state the spec assumes.
3. "Repeat always visible" for error and filtered cards means the existing `Repeat` command is enabled for those states; the spec does not say whether Repeat is hidden on other finished states.
4. `ShowActionsCommand` is available only when `IsFinished`, so the action sheet is not shown for in-progress or errored items, even though errored items get a visible Repeat button.
5. The header text (`ModelText`, `SeedText`, `CostText`, `TimeText`) already exists on `GenerationItemViewModel` with the formatting the spec describes.

QUESTIONS:

1. The spec says "Действия те же, что сейчас", but the menu also includes "Write a prompt from image" and "Describe image" as separate items. Do you mean these are the existing command names, and is there a single existing command for each?
2. Should `ChooseAsync` return the selected option as a string, or an index? Returning a string makes duplicate or localized labels ambiguous, and the spec does not say how that is handled.
3. On the Avalonia side, should the `ContextMenu` and the `More` button open the same instance, or two instances? The spec says "тот же", but a single `ContextMenu` cannot be shown from two places without a placement decision.
4. Which items are shown on error and filtered cards on desktop: only Repeat in the icon row, or the full context menu?
5. The spec gives `ChooseAsync` a `cancel` parameter, but the planned tests only cover choose and cancel. What is the expected return value for cancel, and does `null` also mean "dialog dismissed by the platform"?
6. Does the MAUI "…" button appear only on phones, or also on Windows and Mac? The criteria say both "на телефонах" and "на Windows и Mac — видимая кнопка «…»", so the platform split for that button is unclear.

RISKS:

1. In the plan step 3, the spec says there is no ready-made long-press gesture in MAUI and then proposes `CommunityToolkit.Maui` `TouchBehavior.LongPressCommand`. The toolkit version must support that property, and the spec's own "проверить версию" leaves that unverified; the plan should say what to do if it is missing.
2. The Avalonia visibility rule `Border.card:focus-within StackPanel.card-actions` depends on whether the Avalonia version in use supports `:focus-within` as a selector pseudo-class. If it does not, keyboard focus will not reveal the icon row, which breaks the accessibility criterion.
3. A `ContextMenu` that is attached to the card will also fire on right-click inside the child icon buttons, so the icon buttons may show two menus or the wrong one. The spec does not say how event routing is handled.
4. Plan step 1 changes `IDialogService`, but the plan does not say how `ShellDialogService` and `AvaloniaDialogService` will reject concurrent `ChooseAsync` calls (for example, a double long-press or two "…" taps while the first sheet is open). This can leave overlapping dialogs.
5. `DisplayActionSheet` on Android returns `null` when the user taps outside it, while the Avalonia dialog may return a different value on window close. Without a common contract for dismissal, the same `ShowActions_Cancel_DoesNothing` test can pass on one platform and fail on the other.
6. The plan says to stop with `blocked` if a step fails, but the design files are referenced by a local `python3 -m http.server` URL and the published artifact. If the prototype differs from `implementation.md`, the developer has no rule for which source wins.
