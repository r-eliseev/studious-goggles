ASSUMPTIONS
1. The spec's "Уточнение 2026-10-31" overrides the earlier "Анализ" section: the owner's decision is full-history indexing at enable time, and a separate "Meaning" mode with results not merged with word search. I assume the older "переиндексация отдельно решена до planned" criterion is now satisfied, since the plan section already states the strategy.
2. Source keys (`title:<sessionId>`, `prompt:<runId>`, `desc:<descriptionId>`) are stable across app restarts and across Edit operations, so that `content_hash` comparison is what drives invalidation rather than key churn.
3. `search.json` in the data folder is the single source of truth for the enabled flag, and it is consistent with the `text_embeddings` table after a crash mid-enable or mid-batch.
4. The OpenRouter `/embeddings` endpoint accepts a batch of 64 strings in one request and returns `index` per item; the batch size and the 10 000 cap are not tied to a provider-side input limit that the spec has verified.
5. Full-history enablement covers the same text set as `ListAllAsync` today (titles, prompts, descriptions), and the "N texts" count shown in the confirmation dialog is computed before the user confirms.

QUESTIONS
1. Criterion "переиндексация старых данных решена до planned" versus the plan's "первым вызовом проверить размерность": is the 1024-dimension assumption a precondition for the cost estimate shown in the confirmation dialog, or is the dialog allowed to show only a text count?
2. What is the cost unit of `usage.cost` (USD, credits, or unknown), and does the confirmation dialog show "paid" with an amount, or only "paid"? The spec forbids labelling an unknown unit as USD but does not say what the UI shows in that case.
3. When the user disables semantic search, do the `text_embeddings` rows get deleted immediately, and what happens to an in-progress run that is still writing batches?
4. The 10 000 cap: does "последних 10 000" mean the most recent by session date or by source creation, and is the cap applied at index time or at query time? The spec says both "перебор 10 000" and "поиск по первым 10 000 последних" without clarifying.
5. Stop-and-resume: is the resumed run required to reuse the same `content_hash` snapshot, or does it re-read sources and possibly pick up new texts added during the pause?
6. Mode switch: does "Meaning" mode query the same index that the word-search path reads, and is there any requirement for a non-empty result set to be distinguishable from "index not ready"?
7. The quality gate (20 RU/EN queries judged by the owner) has no pass criterion, while the spec forbids inventing a threshold. What decides that the feature may be marked done?

RISKS
1. Full-history indexing on enable runs in one pass with paid calls; if the app is closed or the device sleeps mid-pass (Android MAUI especially), the background work may be killed. The spec's resume-from-last-batch point depends on the batch transaction being durable, so verify that the Android background lifecycle does not discard the in-flight request without a clear failed state.
2. The `SessionChangeNotifier` 2-second debounce per session is a timer that must be cancelled on disable and on session delete; otherwise a delayed recompute can write vectors for a deleted session or after the feature is off, re-creating rows the privacy rule says were removed.
3. Race between an in-flight embedding response and a session deletion or an Edit: the spec requires the response not be written, but the `content_hash` check and the insert are described as separate steps, so a changed title between them could attach a stale vector to the new text.
4. Memory: 10 000 × 1024 × 4 bytes ≈ 40 MB plus `float[]` object overhead and the LRU query-vector cache; on a mobile MAUI target this is a real peak-memory risk that the spec only plans to measure after implementation.
5. Retry policy: up to 2 retries per batch on 429/5xx with 2 s and 8 s pauses, multiplied by a per-batch paid call, can double cost on a rate-limited key; the spec records cost per batch but does not cap total retry spend or stop after a budget threshold.
6. `ProviderResponseLimits.Json` may cut off a 64 × 1024-float JSON response (roughly 1–2 MB of text) if the limit is set for smaller responses; the limit must be checked against the batch size, or valid responses will fail as provider errors.
7. Ranking "best match per session" combined with "first 20" and tie-break by session date: a session with many prompts could dominate the list, and the spec does not say whether the per-session maximum is computed over all its sources or only its title.
8. Deleting a session cascades to `text_embeddings` via `ON DELETE CASCADE`, but the in-memory vector cache used by `SemanticSearchService` is only reset on index change; a session deleted without an index change may keep appearing in results until the cache is invalidated.
