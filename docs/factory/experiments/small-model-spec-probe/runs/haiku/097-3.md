ASSUMPTIONS
1. The spec's "Среда" line says Linux or Windows, but step 7 and the verification list require an Android SDK build; I assume the executor has Android SDK access, or the task is blocked at step 7.
2. I assume `ChatPageModel.Items` is an `ObservableCollection`-like type raising `CollectionChanged`, since `OnItemsChanged` and the MAUI subscription depend on it; the spec never states this.
3. I assume `ShellHarness.Window.Height` and `FindControl<ScrollViewer>("Transcript")` work headless on Avalonia, since step 3 tests depend on real layout passes.
4. I assume "пункт S2.6 и его продолжение" in `chat-sessions.md` exists as described, since step 8 anchors the new item to it.

QUESTIONS
1. Step 2 says `CardUpdated` fires only when the card is found in `_cards`, but the spec does not say what happens when a generation finishes or fails: should `CardUpdated` fire on the final state too, and is that covered by the three listed tests?
2. Acceptance criterion "нижний край последней карточки остаётся виден" conflicts with step 7's rule that the last visible index alone "не доказывает" the bottom edge, yet the MAUI `Scrolled` path only uses the index; which measure is authoritative on MAUI?
3. Decision (1) says any `Items` change scrolls even if the user scrolled up, but step 7's `OnItemsChanged` calls `RowsChanged()` which also does this; should `ReloadAsync` triggered by "Повторить" while the user is scrolled up really force-jump?
4. Step 4 says "сначала отписаться от старого" when `_subscribed` differs, but `OnDisappearing` already nulls it; is a model swap without disappearing possible in Shell navigation?
5. Step 7 says the `SizeChanged` handler on row views should call `ContentChanged()`, but the spec gives no name or XAML location for the row template root, so which row template is meant?

RISKS
1. Step 4's `OnTranscriptScrollChanged` classifies `OffsetDelta.Y == 0` as non-user, but on Avalonia extent/viewport-only changes can shift the offset without a user gesture, so the `IsFollowing` flag may flip to false during a resize and break `ScrolledUp`/`AtEnd` tests.
2. Step 7's `Dispatcher.Dispatch` callback guards with `_programmaticScroll` cleared "после отложенного UI-dispatch", but `Scrolled` events from `ScrollTo` on Android may fire asynchronously after the guard is cleared, so user-scroll detection can misfire and cancel following.
3. Step 7 `ScrollToEndLater` checks `_model.Items.Count` inside the dispatched callback but the callback may run after `OnDisappearing` has nulled or disposed `_model` references, creating a null/ObjectDisposed path the spec does not handle.
4. The `CardUpdated` event is raised inside `BeginInvokeOnMainThread`, and handlers on Avalonia scroll with `DispatcherPriority.Background`; for a long run the repeated `ScrollToEndLater` calls are coalesced by `_scrollPending` only on Avalonia's side, so the coalescing contract is inconsistent between the two shells.
5. Step 7 handles row growth via `SizeChanged` on row roots, but `SizeChanged` fires during layout, and calling `ScrollTo` from inside a layout pass on Android can be ignored or cause a layout loop; the spec does not state a deferral.
6. The guarantee "Новые сценарии ... должны сначала продемонстрировать дефект" in step 3 cannot be verified for `OpenChat_LongHistory_TranscriptAtEnd` and `AtEnd_WindowShrunk_StaysAtEnd` if the current Avalonia code already passes them, so the TDD gate is unclear.
7. `ReloadAsync` clears and rebuilds `Items` on every action, so a generation that finishes during reload can race with `CardUpdated` and the `_scrollPending` guard, and the spec does not describe the ordering.
8. The `ScrolledUp_Reload_ScrollsToEnd` test expects reload to force-scroll, which relies on `RowsChanged()` resetting `IsFollowing` before the first layout; if the Avalonia `Items` event fires before `Transcript` is re-measured, `WaitUntilAsync` may pass on a stale extent.
