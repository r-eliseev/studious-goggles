ASSUMPTIONS:
1. The spec author's `scripts/release-task.sh 097` and `scripts/check.sh` exist, and the task-status convention (`in-progress`, `blocked`, moving files between `backlog` and `v0.1`) is as the spec implies; the spec does not define the release script's effect.
2. `IChatMessageRepository`, `ShellHarness`, `WaitUntilAsync`, `Routes.ChatFor`, and `MauiStylesTests`'s `MauiRoot()` already exist with the signatures the spec relies on, since the spec only describes them by name.
3. Tasks 095 and 096 are complete before 097 starts, and the keyboard-resize behaviour in 095 is already testable on the target Android device.
4. The `CollectionView` in `ChatPage.xaml` uses `ItemsSource="{Binding Items}"` and the `Items` collection is an `ObservableCollection`-like type whose `CollectionChanged` fires for Reset as well as Add/Remove.
5. Android Maui and Avalonia share the `ImageGen.Presentation` project, so `TranscriptFollower` is compiled into both without platform-specific conditional code.

QUESTIONS:
1. Step 4 and step 7 both say "follow" should resume when the user scrolls to the end, but step 7 only resumes on the last index while the Avalonia step uses a pixel tolerance of 24. Should the two shells use the same end-detection rule, given decision (4) says the rule is shared?
2. Decision (1) says any `Items` change scrolls to end even if the user scrolled up, yet `RowsChanged()` in step 1 is specified to return `true` and the spec itself says "Reset" triggers a scroll. Is a Reset from the pending-scroll path intended to override a user who is mid-read on an older message?
3. Step 7 says the user scrolling down to the last index sets `UserScrolled(true)`, but the acceptance criterion says the bottom edge must be visible. What is the expected behaviour when the last row is taller than the viewport and the user has reached the last index but not its bottom?
4. The MAUI row-level `SizeChanged` handler in step 7 calls `ContentChanged()`, while the rule in decision (2) names "обновление карточки" and "смена размера ленты" as the triggers. Is the row `SizeChanged` meant to be a third trigger, and does it also apply to non-last rows?
5. The spec does not say what happens to `_programmaticScroll` if the `Scrolled` event for the programmatic `ScrollTo` never fires (e.g. the list is already at the end). The guard could stay set and swallow the next real user gesture.
6. Step 8 adds S2.7 with the text "(задача 097)" and the knowledge note asks whether the behaviour was verified on device, yet the manual checks are deferred to 140. Should the docs be written before the device verification, or should the note be left open?

RISKS:
1. The Avalonia `OnTranscriptScrollChanged` handler classifies layout-driven offset changes as user gestures unless `ExtentDelta`/`ViewportDelta` are both zero; a content growth that also moves `Offset` could flip `IsFollowing` to false incorrectly, so the early-return ordering in step 4 needs careful testing.
2. In MAUI, `ScrollTo` with `animate: false` on a `CollectionView` whose item template contains a `SizeChanged` handler can trigger a new `SizeChanged`, which calls `ScrollToEndLater` again; the `_scrollPending` guard prevents a loop only while the callback is in flight, not across the next layout pass.
3. `Dispatcher.Dispatch` in step 7 captures `_model` and `Transcript` by reference; if `OnDisappearing` runs before the dispatched callback, the `_active` check protects the scroll but not the `Transcript` field itself, which may be null or detached on Android after navigation.
4. The Avalonia `_scrollPending` is reset in `finally`, but the `DispatcherPriority.Background` callback can run after `OnDisappearing` sets `_active = false`; the step says the callback checks `_active`, but it is not stated whether pending is reset on disappearing, so a later `OnAppearing` could see a stale pending flag and skip the initial scroll.
5. Step 2 raises `CardUpdated` inside `BeginInvokeOnMainThread` after `card.Update`, but card layout (picture load) happens later; the event fires before the new height is measured, so the follower depends entirely on the row `SizeChanged` in MAUI and on `ExtentDelta` in Avalonia, which step 4 handles only by requesting scroll when already following.
6. The `ChatPageModel` tests in step 2 depend on `WhenIdleAsync` ordering with `release.SetResult`; if the event is raised after idle is signalled, `CardUpdated_GenerationOfThisSession_Raised` can be flaky.
7. Step 3's `ScrolledUp_Reload_ScrollsToEnd` expects `ReloadAsync` to clear and rebuild `Items`, but if the rebuild produces the same count, `Items.CollectionChanged` may fire only once or not at all in the Reset path, so the test could pass for the wrong reason or fail without a real defect.
8. The `dotnet format --verify-no-changes` gates for the MAUI project and the Android build require the Android SDK and workload; on a Linux agent the build may fail for reasons unrelated to this change, and the spec's fallback ("подготовить инструменты") gives no concrete target.
