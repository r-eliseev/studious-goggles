## ASSUMPTIONS

1. **Normalisation.** I would assume tokens and words are lowercased and normalised identically before `ScoreWord`. The `token[0] != word[0]` check and the test `["lighthu"]` against «Lighthouse on a rock» depend on this, and so does the Cyrillic case. I would also assume `Distance` and `word[..length]` work on UTF-16 code units, which is fine for Cyrillic and Latin but not for surrogate pairs.
2. **Which word `FirstIndex` points to.** The spec does not say what `FirstIndex` means when several words in a text match with different scores. I would assume it is the best-scoring word, with ties going to the earliest. The new rule makes this visible: «watte» against «waterfall water» could point at either word.

## QUESTIONS

1. **Ranking across text kinds.** The criterion «точное начало выше, чем совпадение с опечаткой» only holds within one kind. A typo in a Title scores 1×3 = 3, which ties with an exact prefix in a Description (3×1). It also beats a substring match in a Description (2×1). Is that acceptable, and what is the tie-break? `Search_ExactPrefixBeatsTypo` only covers two Prompts.
2. **Step 1 regression tests.**
   - «Запустить: первые четыре падают, остальные проходят» is wrong for `Match_CyrillicTypoInPrefix_Scores1`. «водопо»→«водопад» has distance 2 to the whole word and is matched only by the new rule, so it fails before the change.
   - `Match_DigitToken_ExactPrefixWins` has no input or expected value.
   - `Match_EmptyQuery_ReturnsNull` and `Match_EmptyText_ReturnsNull` assume the current behaviour is `null`. Is that confirmed?
3. **Which tokens get the prefix-typo rule.** The motivation is that only the last word is incomplete, yet the rule applies to every query token. In a multi-word query the earlier, completed words get the extra fuzziness and its noise. Should it apply only to the last token, or is that deliberately rejected?
4. **Criterion 4 against the plan.**
   - The criterion requires that it be «Выяснено и записано в «Отчёте»» whether Android updates on composing text. The plan only hands a manual scenario to 140 and forbids code changes.
   - Does the handoff count as meeting the criterion?
   - The owner's screenshot already shows «Nothing found» for «watte», which suggests the text did reach `SearchText`. Can that be recorded as evidence?

## RISKS

1. **Noise is larger than the analysis says.**
   - For a 4-letter token the rule matches any word whose 3-, 4- or 5-letter prefix is within one edit, not just words sharing the first three letters.
   - Examples: «rain»→«ruins» (prefix «ruin»), «cats»→«capsule» (prefix «caps») and «cats»→«castle» (prefix «cas»). None of these is reachable by a three-letter query.
   - The analysis claims it is «не больше того, что уже даёт запрос из трёх букв», which is not true.
   - Because typo matches in a Title are multiplied by 3, such matches can outrank exact prefixes in other kinds.
   - The negative tests cover only one case with a 5-letter token and a whole word (house/hound), and no 4-letter-token noise case.
2. **Cost per keystroke.** Each (token, word) pair now costs up to four Levenshtein computations plus a slice allocation. This runs over every session's texts, including long prompts, on each debounced query, and on Android. The pseudocode has no cheap length or first-letter pre-check before the repeated `Distance` calls, so the cost depends on whether `Distance` has its own early exit.
3. **Numeric and ID-like tokens.** Digit tokens of four or more characters («2024», «1024») are treated as typo-eligible. The new rule extends the existing noise to longer numbers, e.g. «2024» matching «2025…», or a resolution or seed matching a different one. The plan neither excludes nor tests this.
4. **Snippet and highlight.** The spec does not say how `FirstIndex` or the matched span is used for the snippet and highlight in the UI. For prefix-typo matches the matched text length differs from the token length («brige» against «bridges»). The only Avalonia test, `Search_FindsSessionByPromptWithTypo_ShowsSnippet`, covers a whole-word typo, so truncated or misplaced highlighting would go unnoticed.
