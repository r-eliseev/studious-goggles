ASSUMPTIONS
1. The 840 threshold is in device-independent units (DIPs in MAUI, Avalonia logical pixels), and the layout switches live on window resize, not only at startup. The spec says "as in 066" but does not say whether the boundary is inclusive for the handler (≥ 840) or how it behaves on resize.
2. The "current" mark is cleared (`SetCurrent(null)`) when the user leaves the chat or deletes the current session. The spec defines only how the mark is set.
3. Step 2 ("if needed") means `ReplaceAsync` is added to `INavigationService` unless an existing method already does the same. Which of the two routes is chosen is left to the executor and documented in `docs/knowledge/`.
4. The singleton `SessionsPageModel` already holds a loaded list when the chat opens, either from 066 or by loading on demand. The spec does not say who triggers the load if the chat is the first screen, for example after a deep link or restoring state.
5. The `destructive: true` overload from 072 already exists with that exact signature. Step 0 is only a call-site change.

QUESTIONS
1. Step 0 (destructive delete confirmation) is unrelated to the feature title and the acceptance criteria. Is it intentionally part of this task, or should it be moved elsewhere? It is not in "Критерии готовности".
2. What should happen if the user deletes the currently open session from the list inside the chat? Does the chat navigate away (to what?), show an empty state, or open another session?
3. What does "New session" do in the wide chat? Does it replace the current chat like selecting a session (same `ReplaceAsync`), and is the new session marked current immediately, before the first message?
4. Does the list in the chat need the same search, filter, and empty or loading states as on the 066 screen? Since the same `SessionsPageModel` is shared, should filter and scroll state persist across screens?
5. What should happen when the user selects the already current session? A no-op, or a reload of the chat?
6. If the window is narrowed while the chat is open, the list is hidden. Is the user expected to reach the list via "back" as before, and does back still go to the sessions page in that case?
7. Is the acceptance criterion "назад не возвращает к прошлому чату" meant to hold for the Windows MAUI target as well? Step 5 tests only Avalonia, so the MAUI behaviour has no automated test.

RISKS
1. `ICurrentSessionTracker` is a singleton with a `Changed` event, and `SessionsPageModel` is a singleton that subscribes to it. If `ChatPageModel` (probably transient or per-page) never unsubscribes or never clears `CurrentId` on disposal, stale marks and leaks appear. When the chat for A is replaced by the chat for B, the order "B reports itself, then A clears" could erase B's mark.
2. The `SessionItemViewModel.IsCurrent` mark depends on the session list being loaded. If `SetCurrent` is called before the items exist or after the list reloads, the mark is lost. The tracker's `CurrentId` should be reapplied on every list refresh.
3. In MAUI Shell, replacing a page via `//sessions/chat?...` or `../chat?...` has known pitfalls: query parameters are applied to the old page instance, route registration conflicts exist if `chat` is registered both as a Shell route and as a hierarchy route, and `..` navigation plus push can animate or flash. The plan chooses at implementation time without a test, which is risky.
4. A `SessionsListView` as a `ContentView` with a `BindingContext` taken from DI, used on two pages, shares one singleton view model. Two live view instances (the list page, kept in the Shell stack, and the chat) bind to the same collection at once. Selection or scroll state and `CollectionView` virtualization may then behave inconsistently.
5. An `AdaptiveTrigger` in MAUI on Windows depends on window width, but on Android the page width can differ from the window width (split-screen, foldables). Hiding the column may also leave a 272 px empty gap if the `ColumnDefinition` is not collapsed along with the view.
6. Replacing the chat while a generation is in progress. The old `ChatPageModel` may keep running requests or cancel them, and its completion may report to the tracker after the new chat has loaded. The spec does not cover cancellation or unsaved draft input.
7. Avalonia headless tests of width (`WideChat_ShowsSessionsList`) depend on a layout pass and on the window size being applied. The width handler "as in 066" may fire only on a size change event, so the initial state can be wrong if the window is already wide at creation.
