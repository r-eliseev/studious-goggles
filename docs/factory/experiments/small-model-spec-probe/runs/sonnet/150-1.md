ASSUMPTIONS
1. Convert.FromBase64String's accepted whitespace is exactly space, tab, CR and LF (step 1). The plan assumes this for every target runtime, and the single-pass counter must match it exactly.
2. "Significant characters" includes '=' padding. The guard compares the count against ((Image+2)/3)*4, which is the padded length of the maximum decoded size.
3. A payload that is only whitespace, or empty after whitespace is ignored, keeps the current behaviour. The spec only says that a missing or empty b64_json gives EmptyResponse, so a whitespace-only string is undefined.
4. The two clients differ today (OpenRouter DecodeImage vs OpenAiCompatible). The spec assumes that the extracted decoder can replace both without changing their other behaviour, such as data: URL prefixes or field selection.
5. The 72MiB JSON cap is enforced by the existing reader before DecodeImage is called. "Not increased" therefore means the plan only has to verify the existing cap, not enforce it.
6. The decoded 50MiB case is accepted even though the temporary decode buffer is near the limit. Memory pressure in tests is assumed acceptable.

QUESTIONS
1. Where is the 50MiB+1 case rejected: by the new pre-allocation guard, or by the post-decode check? The criterion says "отклоняется Unknown", but the plan leaves the direct client's exception type unspecified. What exception should the direct client throw for an oversized payload, and is it the same one the adapter maps to Unknown?
2. Should the whitespace-heavy attack case be bounded in some way? Unlimited whitespace inside a 72MiB JSON is allowed, but a payload with an excessive significant-character count is not. Is the single linear pass over up to 72MiB acceptable in cost?
3. Step 3 says the decoder takes a "byte limit", while the guard needs a char count. Does the decoder return byte[] or write into a buffer? The spec does not say which, and "no additional copy of the whole string" is only stated for the string.
4. Is the reference to tasks 150+152 a hard prerequisite for the final step? Those files are not named in "Зависит от: —", so the dependency is contradictory. What should happen if they are not done when this task finishes?
5. Why does the spec say that "invalid base64 remains Unknown" while step 4 says the direct client must throw FormatException? Unknown is only the adapter's mapping, so the criterion should name the layer.
6. Is the exclusive xUnit collection a new one or an existing one? Which existing size tests from task 112 must be moved into it?

RISKS
1. Convert.FromBase64String has its own rules on whitespace placement, for example around padding or between '=' characters. The guard can pass strings that the decode then rejects, or the other way round. Test coverage for "whitespace in all allowed positions" has to match the runtime behaviour, not the plan's reading of it.
2. A 50MiB decoded payload needs about 67MB for the string, 50MB for the result and the JSON buffer at the same time. The large tests run on both clients and may cause OOM or LOH fragmentation on CI. Even in a non-parallel collection, the GC must release memory between tests.
3. If the loop counts only ASCII whitespace but the string contains other characters (NBSP, other Unicode), the count includes them and the guard may reject before FormatException would have fired. The expected error type for such inputs is therefore ambiguous: oversized vs invalid.
4. The "Assert JSON<72MiB" check for 49MiB of zero bytes with CRLF is sensitive to how the serializer escapes CR/LF (`\r\n` is 4 bytes per break). The margin has to be computed with that escaping, or the test will fail for the wrong reason.
5. Returning task 112 to done depends on 150+152, which are outside this fix. The state transition could be forgotten or done too early, since the spec says only the evidence is written here.
6. Integer overflow is possible in ((Image+2)/3)*4 if Image is ever configured as int and large in the unit-test helper with a configurable limit. Counting characters in a loop over a string of up to 72M chars needs a long or a checked comparison.
