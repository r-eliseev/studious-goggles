**ASSUMPTIONS**

1. I would assume `FuzzyMatcher` lowercases and normalizes both the token and the word before `ScoreWord`. Otherwise `token[0] != word[0]` and `Distance` could disagree, and the "Lighthouse on a rock" / "lighthu" test would fail. I would also assume the "≥ 4 letters" threshold and the `L ∈ {|t|−1, |t|, |t|+1}` lengths count UTF-16 code units. In that case `word[..length]` can split a surrogate pair for non-BMP characters, and the spec does not say whether that matters.
2. The spec does not say which word's score and `FirstIndex` are used when several words match one token. I would assume the best score wins, and on a tie the first word. The new rule makes 1-point hits far more common, so an early weak typo hit could set `FirstIndex` ahead of a later exact prefix (the "exact prefix first" rule, criterion 2).

**QUESTIONS**

3. Criterion 4 requires the Android IME question to be answered and recorded in the "Отчёт". Step 6 and "Ручная проверка" move that check to task 140, and the completion paragraph forbids leaving the task `in-progress`. Is the task done with criterion 4 unmet, or should the criterion be reworded as "scenario handed off to 140"? The claim that the owner's "watte" symptom is "fully explained" by the rule is also unverified on a device.
4. Step 1 says the first four tests fail and the rest pass. But `Match_CyrillicTypoInPrefix_Scores1` ("водопо" → "водопад", whole-word distance 2) is new behaviour and must fail before step 2, despite being called a regression. `Match_DigitToken_ExactPrefixWins` has no input or expected values at all.
5. Should numeric tokens get the prefix-typo rule? "2024" would match "20251" or "2023-05", and the spec only discusses letter noise ("cats"/"catalog").
6. How are `FirstIndex` and the matched range used for the snippet and highlight in the Avalonia/MAUI list? With prefix typos the matched word ("lighthouse") is longer than the token ("lighthu"). If the highlight uses the token length, it may be wrong, and `Search_FindsSessionByPromptWithTypo_ShowsSnippet` may not catch it.
7. The hand-off list is inconsistent. The completion paragraph names 016, 046 and 140, but "Файлы" and "Ручная проверка" mention only 016 and 140. Step 5 also assumes `S1.3` exists in `docs/specs/chat-sessions.md` and that the number `S1.4` is free.

**RISKS**

8. The criterion "exact beginning ranks above a typo match" does not hold across text kinds, because the weights are unchanged. A Title typo scores 1×3 = 3, which ties with a Description exact prefix (3×1) and beats a Description substring (2). A Prompt typo (1×2) ties with a Description substring (2). Step 3 tests only two Prompt texts, so this goes unnoticed, and the tie-break order is unspecified.
9. Each token now runs up to three extra Levenshtein calls per word, each on a freshly allocated substring. These run over all texts of all sessions on every debounced keystroke. The spec has no data on the number of sessions or the text length, so there is no basis for judging whether this stays responsive on Android.
10. On Android the keystroke path of the owner's original case (a half-typed "watter" shown as "watte") may still differ from what the tests model. If the IME does not deliver composing text into `SearchText`, the fix looks ineffective on the device even though the core tests pass. The task closes before that check happens.
