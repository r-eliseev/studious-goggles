ASSUMPTIONS
1. Index key stability: I would assume `prompt:<runId>` is a stable key for dedup. A prompt shared by several runs or generations then yields several vectors (or `DISTINCT` collapses them) and the same text is paid for repeatedly. The spec does not say which.
2. "Normalized text" for `content_hash` (SHA-256) is undefined (trim, Unicode normalization, case, whitespace). I would pick trim plus NFC and treat the hash as covering text only, not model or dimension.
3. A model change or a dimension change is handled by re-indexing everything. The spec stores `model` and `dimensions` per row but defines no rule for mixed rows.
4. The `search.json` flag is per-device. The data folder may be synced or shared, and the spec does not say whether the flag must match the DB state.
5. The 10,000 cap is applied at search time over the "last 10,000" (by what date?). Indexing may still send everything and pay for it, which contradicts the cap's purpose.
6. `CostUsd?` is unknown-unit per the Analysis, but the plan names it `CostUsd` and writes it to the expense log. I would assume it is stored as "unknown unit" and not labeled USD.

QUESTIONS
1. The 2026-10-31 decision says the whole history is indexed in one pass. The cap says only 10,000 are searchable. Should the confirmation dialog and the cost warning cover all N texts, or only the first 10,000? What happens at N > 10,000?
2. Stage 2 states that without 021 stage A, "the price goes only to the application log, the task is not closed". Does stage 2 still merge, and who tracks the open remainder? Also, `ExpenseKind.Embedding` and the operation id = batch id are not defined in 021. Is that contract agreed?
3. What happens to old rows when the data is updated? `ListSourcesAsync` is incremental by key, but the spec does not say whether the "status" counters (Indexed/Pending) count removed sources.
4. Query-time embedding is a paid call per search. Is there a cost/consent indicator in the search UI, or is consent at enable time enough? Is there a per-session or daily cap against a typing loop (400 ms debounce, LRU 50)?
5. Are there limits on text length per input (bge-m3 token limit, request body size, very long prompts)? How are over-limit or empty texts handled (skipped, truncated, failed batch)?
6. What does "Failed" mean for the user? Can they retry manually? Does the next app start automatically resume indexing? The spec forbids hidden repeat paid requests, so the resume policy needs to be explicit.
7. The spec says "Meaning is unavailable if indexing is not finished". Should partial results be usable during Indexing, or is the mode fully disabled until Ready? How does this interact with the incremental updates after Ready (state returns to Indexing)?
8. Is the API key shared with the existing image-generation flow? Does the consent text cover that prompts and descriptions leave the device through this key?

RISKS
1. `SessionChangeNotifier` re-index with 2 s delay: a rapid-edit race. A response for an old `content_hash` may arrive after the text changed or the session was deleted. The tests cover deletion only during a request, not a stale hash on write. The write should be conditional on the current hash and on the session still existing, which is not stated.
2. Deleting a session cascades vectors, but a batch in flight that includes that session's text can insert a row with an FK to a missing session. The insert fails and may fail the whole batch transaction, wasting the paid call and losing the other 63 vectors.
3. Retry on 429/5xx can duplicate charges if the provider billed a failed or timed-out request. The spec's "no hidden repeat paid requests" conflicts with 2 automatic retries. Cost on a failed attempt is also unrecorded.
4. Cost is recorded per batch after the response, so a crash between the response and the transaction commit loses the price record or the vectors. The operation id = batch id gives no idempotency if the batch is re-formed differently on resume.
5. In-memory brute-force over all vectors with a cache invalidated on every index change: during initial indexing, each batch invalidates the cache and the next search reloads about 40 MB. This is a likely stall or memory spike on mobile (MAUI Android), and the memory limit is only "measured" in the report.
6. `Edit` creates a new run, so old run prompts stay in `runs` and keep their vectors. Search can return the same session via stale prompts and show a snippet that no longer matches the current content. The spec does not say whether obsolete prompts are retained.
7. Float32 little-endian BLOB with a dimension check: a corrupt or truncated BLOB, or a dimension different from the stored value, must be skipped rather than crash search. Only the roundtrip is tested.
8. Disabling the mode (`DisableAsync`) while a pass is running: a pending batch can write vectors after deletion, so privacy-motivated deletion is not guaranteed. Likewise `StopAsync` versus a batch in flight, and the flag written before the pass starts and not rolled back on failure.
9. Cosine ranking across mixed model/dimension rows, or a dimension mismatch between the query vector and stored vectors, is not specified. The query vector should be compared only against rows with the same model and dimension.
10. Quality: "20 RU/EN queries judged by the owner" gives no pass criterion and no threshold, so "done" is subjective, while the spec forbids an invented threshold. Semantic results will always return 20 items, even when irrelevant.
