ASSUMPTIONS
1. "Card is finished" means `IsFinished` is true for success only. The spec also says Repeat is always visible on error and filtered cards, so I assume those states are either `IsFinished == true` or handled separately. The spec does not say which.
2. The menu items for error and filtered cards are assumed to be the same five actions, with some disabled by each command's `CanExecute`. Nothing says whether Edit and Describe make sense without an image.
3. I assume the action labels come from existing resource keys in `implementation.md`. The new `ChooseAsync` returns the chosen label string, so the view model must map the label back to a command. I assume the labels are unique and localised.
4. I assume Windows and Mac both use `MenuFlyout` and the "…" button is visible there. "Phone" is assumed to mean Android and iOS by `DeviceIdiom`, not by window size.
5. I assume the "Cancel" label passed to `ChooseAsync` is a localised resource key that the spec does not name.

QUESTIONS
1. Step 1 makes `ShowActionsCommand` available only when `IsFinished`. Does that cover error and filtered cards? If not, the phone "…" and long-press give no way to repeat them, while the desktop Repeat is "always visible".
2. "Repeat is always visible" on error and filtered cards: does this apply on desktop only, or on MAUI too? Does it replace the hover row, or is it shown alongside it?
3. Step 3 is vague about MAUI: how is `FlyoutBase.ContextFlyout` kept separate from the phone path? Is it chosen per platform or by idiom, and does Windows get long-press too?
4. Step 2 gives no placement, size or visibility rules for the "…" button on touch-capable Avalonia targets. Does Avalonia have a phone or touch mode, or is it desktop only?
5. The header joins `ModelText`, `SeedText`, `CostText` and `TimeText` with " · ". What happens when a part is empty, for example no cost or no time? Should empty parts be skipped?
6. How should the Avalonia `ChooseAsync` window behave on Escape or on closing with the window button? It should return null the same way "cancel" does. The spec also does not say what the window is parented to.
7. Tasks 068 and 072 both change `AvaloniaDialogService`. Which one merges first, and how should the new method be added to avoid conflicts?

RISKS
1. `:focus-within` is not a built-in Avalonia pseudo-class. Depending on the version, the selector `Border.card:focus-within` may fail to parse or never match. A custom class or `IsKeyboardFocusWithin` binding may be needed. Step 3's "blocked" rule would stop on this, but step 2 has no fallback and the test `Actions_VisibleOnFocusWithin` depends on it.
2. `IsVisible: False` removes the buttons from the focus order, so the keyboard can never reach them and `:focus-within` never triggers. The hidden row would need opacity or another way to stay focusable. Hover-only visibility also does not work on touch screens.
3. `TouchBehavior.LongPressCommand` in CommunityToolkit.Maui behaves differently per platform and version, and may consume taps. Its `LongPressDuration` and the `CommandParameter` binding inside a `DataTemplate` are common problem points. A long press may also trigger the Android context menu or scrolling, so the gesture can conflict with the list's scroll.
4. `Shell.Current.DisplayActionSheet` is null-unsafe when no shell is active and is not thread-safe. If `ChooseAsync` is called off the UI thread, or twice by a double long-press, a second sheet may stack. `ShowActionsCommand` is not guarded against re-entry. Check that `AsyncRelayCommand` blocks concurrent execution.
5. If the item state changes while the menu is open (generation completes, is deleted, or re-runs), the chosen action may run against a stale or disabled state. The spec does not say whether the command re-checks `CanExecute` after the choice.
6. Right-click on Avalonia and long-press on touch may both open the menu, and the "More" button must open the same `ContextMenu` programmatically. `ContextMenu.Open()` needs the correct placement target, and a right-click inside a child control, such as the prompt text, may open a different menu.
7. The tests only check the existence of items and names. Nothing tests that disabled commands are disabled in the menu, `ToolTip.Tip` on each button, or the MAUI part, which is only built and never run. Step 4 includes no test for the `ChooseAsync` window itself.
