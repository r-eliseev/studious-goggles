ASSUMPTIONS
1. "Whitespace" means only ASCII space, tab, CR and LF, per step 1. I assume this matches what `Convert.FromBase64String` accepts on all target runtimes, and that the spec does not require counting whitespace differently between Linux and Windows ("Среда: Linux или Windows").
2. The guard counts non-whitespace characters, padding `=` included, against `((Image+2)/3)*4`. I assume padding is counted as significant, so the 50MiB decoded case with its exact padding passes and 50MiB+1 fails.
3. The new decoder is assumed to return `byte[]` or equivalent and to be called from the same place in both clients. I assume the existing empty/missing `b64_json` check (`EmptyResponse`) stays outside the decoder, before the call.
4. The "Unknown" classification is assumed to be produced only by the queued adapter. That adapter maps the oversize case and `FormatException` to Unknown, but the spec does not say which exception type the guard throws on oversize.
5. The 72MiB JSON limit is assumed to be enforced before `DecodeImage`, in the HTTP/JSON reader, and not to need a change.

QUESTIONS
1. What exactly does the guard throw when the count exceeds the limit: the same exception type as today, or a new one? Step 4 pins `FormatException` only for invalid base64, so the oversize path is undefined for the direct-client tests and for the adapter's Unknown mapping.
2. Does `Convert.FromBase64String` accept whitespace between padding characters, or after `=`? Step 4 says "whitespace во всех разрешённых позициях", but "allowed" is not defined, and the one-pass counter must agree with the library on every such case.
3. How should an input consisting only of whitespace, or with a significant length of 0, behave? It is probably not `EmptyResponse`, since the string is non-empty, yet it is also not valid base64 for any image. Which error is expected?
4. Criterion 1 says "decoded 50MiB accepted", but the guard is only an upper bound on the encoded length. Can an input pass the guard with a malformed length (not a multiple of 4) and then fail with `FormatException` in the library? Is that the intended order of failures?
5. Step 6 says to return 112 to done only after 150+152. Is that action part of this task's acceptance, or only a note in the evidence file?

RISKS
1. A counting pass followed by `Convert.FromBase64String(string)` is two scans, which is fine. But the library still allocates the decoded `byte[]` internally. "Pre-allocation guard" therefore protects only the decode, not the memory already held by the string, which comes from the 72MiB JSON. Peak memory is not covered by any test.
2. The wrapped test case may not be self-consistent. 49MiB of zero bytes becomes about 65.3M base64 characters plus CRLF every 76 characters, so the JSON is roughly 66MiB. That is under 72MiB, but only because of the zero bytes, and the assertion in step 5 is tied to this arithmetic. The exact-boundary wrapped case (50MiB decoded with whitespace) is not specified and could exceed 72MiB, so it cannot be tested end-to-end.
3. Large end-to-end tests allocate several tens of MiB each (string, JSON, byte arrays, two clients). Even in a non-parallel collection this may cause memory pressure or flakiness on CI, and the spec gives no memory budget. Step 5 also bans permanent static buffers without saying how to share data between tests.
4. Both clients must share one decoder, but their JSON models may differ (e.g. nullability of `b64_json`, the field name, error mapping). Moving the logic can silently change one client's behaviour on edge cases, such as a null value or a data URL prefix, that the regression tests do not list.
5. An xUnit collection only serializes classes within the same assembly that are marked with it. Existing size tests from plan 112 that are not moved into the collection can still run in parallel with it. The spec says "объединить", but does not name the classes, so some could be missed.
