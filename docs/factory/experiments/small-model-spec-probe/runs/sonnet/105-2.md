ASSUMPTIONS
1. The "Meaning" mode shows only sessions that match semantically; the spec does not say whether it uses a similarity cutoff. Since a fabricated threshold is forbidden, I would assume top-20 by cosine with no cutoff, so even irrelevant queries return 20 results.
2. "Normalized text" for `content_hash` is not defined (trim, Unicode normalization, case, whitespace). I would assume trim plus NFC and no case folding, and the same normalization is applied to the text that is actually sent.
3. `search.json` holds a single global flag, not a per-profile or per-key one. Changing or removing the OpenRouter key does not disable the mode or clear the index.
4. The cost journal (021) accepts `CostUsd?` as is. For an unknown cost, I would assume a null/unknown record rather than 0, given the analysis section's warning about the unit of `usage.cost`.
5. The "first 10,000 most recent" cap is by session date, and the other sources of older sessions are simply left unindexed.

QUESTIONS
1. The status contract has `Indexed`/`Pending`, but the cap of 10,000 is not reflected. Is `Pending` capped, and what do the confirmation dialog's "N texts" and the progress "X of N" show for N above 10,000? What does "message to the journal" mean (application log or expense journal), and is the user told in the UI that search covers only part of the data?
2. The first pass sends all history after one confirmation. Is there a maximum cost or volume warning (e.g., an estimate before consent, given that cost is unit-unknown)? How are the volume and paid status shown if the price cannot be estimated up front?
3. `Failed` after two retries: does the user restart manually via Enable/Stop, or is there a Retry button? Is the state persisted across app restarts, and does the app resume the pass automatically at startup while the flag is on (a hidden paid call)?
4. The plan keys prompts by run id, and "Edit creates a new run". What happens to the old run's vector (orphaned, but the text is still in history)? Are prompts that are `DISTINCT` by text across runs now duplicated per run id, multiplying cost and vectors for identical text?
5. Which texts are sent: is there a maximum text length or token limit per input for `bge-m3` and per request (64 texts of long prompts)? Truncate, split, or skip?
6. The criteria require a "model/dimension/format/source-version" column set; the plan's table has model, dimensions, content_hash but no explicit format or schema version. Is the format column dropped, or implied by the little-endian float32 rule?
7. Is the 400 ms debounce, being in the PageModel, supposed to cancel the in-flight HTTP request? Does a query embedding count as a paid call per keystroke pause, and should there be a rate limit?
8. What happens to the semantic query when indexing is only partially complete: is "Meaning" unavailable until fully done (as stated in stage 4), while the Stop button leaves a partial index? Can the user then ever use partial results?
9. Delete of a session removes vectors, but what about the privacy of texts already sent to OpenRouter, and does Disable have any provider-side implication to mention in the consent dialog?

RISKS
1. Changing the embedding model or its dimension later: stored vectors with a different `model`/`dimensions` are mixed in the brute-force pass, and the plan does not say they are filtered or reindexed. A dimension mismatch between query and stored vectors will throw or give garbage cosine; it needs an explicit guard.
2. Batch save plus "deletion during request" race: the plan says a response for a deleted session is not written, but with a batch of 64 spanning many sessions the FK `ON DELETE CASCADE` insert may fail the entire transaction and lose the batch's paid result. It needs per-row handling, and the cost must be journaled even if vectors are dropped.
3. The 2 s per-session debounce via `SessionChangeNotifier` could run in parallel with the full pass, violating "one request at a time"; both paths also write to the same table, and a stale content hash may be written. A single serialized queue is needed.
4. Cost journaling with "operation id = batch id" and retries: a retry after a timeout may have been billed by the provider, but the plan journals only successful batches. Hidden spend on failed attempts is not recorded, and an idempotent journal write after a crash between the DB save and the journal write could double-count or lose the entry.
5. Memory: 10,000 × 1024 floats ≈ 40 MB, but the load into `float[][]` plus BLOB `byte[]` copies at first search can briefly double or triple that on Android. Cache invalidation "on every index change" during an active pass will trigger reloads repeatedly, so searches during indexing may be slow.
6. LRU cache keyed by (model, text) keeps user queries in memory, and `Unavailable` handling is vague for HTTP 402/insufficient credit, which is neither "no key" nor "no network". The UI state for this case is not defined.
7. Using `DISTINCT` prompt text with run ids: the source list can change between `ListSourcesAsync` calls (new runs mid-pass), so "Pending" counts and "X of N" can move or exceed 100%.
8. Dependencies: stage 2 needs 021 stage A in main, but stages 1, 3 and 4 do not. The plan says the task cannot be closed without it, yet it is unclear whether stage 2 can merge with "price only in app log", and whether that violates the owner's decision that cost goes to the expense journal.
9. The quality check depends on the owner running 20 queries with a live key. If this is not done, nothing blocks completion, and "no invented threshold" has no verification step.
