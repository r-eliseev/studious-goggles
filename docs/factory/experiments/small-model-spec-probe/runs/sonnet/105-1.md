ASSUMPTIONS
1. The 10,000-text cap ("search the first 10,000 most recent") is assumed to apply at both indexing and query time. It is unclear whether the "full pass" indexes everything, or only the latest 10,000 and logs the rest. The spec says "whole history at once" and also sets a 10k limit.
2. "Normalized text" for `content_hash` (stage 2) is undefined. I would assume trim plus whitespace/Unicode normalization, and that the same normalization is what gets sent to the provider.
3. The `search.json` flag is assumed to be a per-device setting, not synced or tied to a user. It is not stated what happens when the file is missing or corrupt (I would assume "Off").
4. "Unavailable" is assumed to cover no key, no network and provider failure alike. The spec also defines `Failed` for the indexing pass, so the boundary between the two states is assumed.
5. A single `CostUsd?` field is assumed. Per the analysis, the unit of `usage.cost` is unconfirmed, yet the interface and `ExpenseKind.Embedding` are named in USD.

QUESTIONS
1. The status/consent dialog says "N texts … paid", but the cost is unknown beforehand. Should it show an estimate (tokens, or an approximate price), or only the count? "Confirmation of volume and paid nature" is the owner's decision, but the content of the dialog is not fixed.
2. Dedup: prompts are `DISTINCT` from `runs`/`generations`, yet the key is `prompt:<runId>`. Are identical prompts in different runs embedded repeatedly and billed again? Should the vector be reused by `content_hash`?
3. How are generations "without their own prompt" mapped? The spec says the run's prompt is used, but the key is the run id. Does a generation's prompt then duplicate the run's source, or is it a separate source?
4. When a text is changed, how does a prompt "Edit" interact with deleting old sources? A new run means a new key. Is the old run's vector deleted when the run is deleted, or does it stay while the session exists (privacy)?
5. With a deleted/changed source, the spec says deleted sources are removed from the index. What triggers the cleanup when the session still exists but a run or description was deleted? Does `SessionChangeNotifier` carry this event?
6. What should the UI show when the pass reaches `Failed` after retries? Is there a "Retry" button, or does the user have to toggle the setting? Does the next launch resume automatically (a hidden paid retry, contradicting the criteria), or only on explicit action?
7. What happens when the 10k limit is exceeded: where exactly is the message in the "expense log" written, given that the log records costs rather than messages? Which 10k are chosen ("latest" by session date, or by source)?
8. Do "Words" and "Meaning" modes share the query field, and is the mode choice remembered? What happens to the 400 ms debounce when the mode is switched mid-query?
9. Is there any minimum relevance threshold for "Meaning"? The criteria say "no invented threshold", but top-20 by cosine will always return something, even for nonsense queries.

RISKS
1. The `ISearchTextSource.ListSourcesAsync` contract still has no pagination or "updated version", and the plan loads all texts. At 10k texts plus 1024 dims, memory on mobile (vectors ≈ 40 MB, plus the SQLite BLOB read and the managed copy at load) can exceed the estimate. The plan stresses that peak memory is measured only after the fact.
2. The batch of 64 texts has no token/size limit. Long prompts or descriptions may exceed bge-m3's context or the request body limit, and the whole batch fails. A single bad text then blocks the pass permanently, since only network errors/429/5xx are retried and the rest go to `Failed`.
3. A retry after a timeout may have already been billed on the provider side. The spec's "no hidden repeat paid requests" conflicts with up to 2 automatic retries, and the cost of a failed batch is not logged because `usage.cost` is absent from the error response.
4. Transactional batch saving plus cost logging are two storages (the vector table and the 021 log). A crash between them gives either a paid batch without a log entry or a duplicate entry on resume. The operation id = batch id is not stable across restarts, since the batches are re-formed from a changed "pending" set.
5. Concurrency: the full pass, the debounce-driven recomputation of a session (2 s) and a user query all run at once. The spec says "one request at a time", but it does not say whether this is shared across the three. A session deleted during a request is covered only by a test, and the cascade-delete race with a write in a batch (FK violation) is not described.
6. `DisableAsync` during a running pass: the in-flight batch may be written after the vectors are deleted, leaving data after "off". The same applies to the in-memory cache of loaded vectors (not reset on disable), so the search keeps working on deleted data.
7. A model/dimension change (the first call returns not 1024, or the provider silently swaps a model version) leaves old vectors incompatible. The cosine on different dimensions has no stated handling beyond the stage-1 check within one response. A stale-vector policy for `model` is not specified.
8. Stage 1 sorts by `index`, but the check covers only the response. OpenRouter may return fewer vectors for filtered inputs, or `float` vs `base64` encoding by default. The spec does not fix `encoding_format`, so a parser expecting a float array may break.
9. Dependencies: stage 2 requires 021 stage A in main, while the task is "not closed" without it. If 021 slips, there is no acceptance path, and the cost-journal fallback (app log only) contradicts the criterion that the user sees the cost.
10. The status is `todo` and the spec says no approved plan exists and the owner's decision is needed before `planned`. Yet the 2026-10-31 clarification already contains the decisions and the plan. It is unclear whether the status condition is now satisfied or the document is stale.
