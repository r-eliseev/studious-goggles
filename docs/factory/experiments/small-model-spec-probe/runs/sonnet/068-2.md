ASSUMPTIONS
1. The "Chat: run and statuses" mockup and `implementation.md` §2.4 are taken as the source of truth. Where they conflict with the spec text, I would assume the spec text wins (for example, notices on every card instead of under the prompt).
2. Tasks 025, 055, 057, 063, 064 and 067 are merged before this one starts. I would assume `GenerationItemViewModel`, `RunItemViewModel` and `ChatView.axaml` already have the shape 025 and 057 leave them in. The plan's step 1 names are written against the pre-025 state.
3. `IgCardShowOverlay`, `IgCardShowFullMeta`, `IgUserMessageAlignment` and the other `Ig*` keys already exist in the Avalonia and MAUI theme dictionaries (from 061, 062 and 063). Only `IgCardShowShortMeta` is new.
4. Header chips (Models, Assistant, Parameters) are visual only. I would assume their existing commands or navigation stay unchanged, because the spec only says "Button with chip look". The "Assistant" chip is not mentioned in the plan's step 2 at all.
5. "Cancelled" is shown as a status label with text, with no special placeholder. The spec gives no placeholder for it.

QUESTIONS
1. The `StatusKind` list has six values, but the plan's tests cover only `Filtered`. What maps to `Failed` vs `Filtered` vs `Cancelled`, and where does that come from in the domain `Generation` (status enum, error code, provider flag)? What does a generation in an unknown or new status look like?
2. Step 1 lists `Update_SeedNotApplied_ShowsSeedNotSupported`, but "seed not supported" has no text, rule or source in the spec. What exact string and condition should `SeedText` use, and how does it differ from "no seed"?
3. How is `TimeText` computed when `CompletedAt` is null (running, queued, failed, cancelled)? Should it be empty, hidden, or live-updating? What format should be used (1.2s, 12 s, 1:05)?
4. The mockup shows the unsent-parameters line under the prompt, but the plan puts `NoticeText` on every card. Does this mean the same line repeated N times in a run? Is the run-level line removed entirely? The decision is attributed to "074", which is described elsewhere as the Try again task, so is that reference correct?
5. The `HeaderText` example is "2 models × 3 · 2 of 6 done · $0.028". How should it be formatted when cost is unknown, when some generations have no price, when there is a single model or a single image ("1 model × 1"), or when some are failed, filtered or cancelled? Does "done" count only successes or all finished? How is the number of models computed, and is currency or localisation involved?
6. The "Assistant" chip, the Gallery overlay strip content and the placement of the Repeat and other action buttons in "a single row of icon buttons" are not specified. Which icons and order, and does the row show in all styles and statuses (e.g. Repeat on a running card)?
7. The grid is "3 columns (2 below width 840)". Is that on the run block width or the window width? On MAUI phones it is 2 columns by idiom, so what about tablets and narrow desktop windows?

RISKS
1. `IsVisible` from `IgCardShowOverlay` combined with `:pointerover` cannot be expressed as one `DynamicResource` binding in Avalonia. It needs a style selector or a multi-binding, and the criteria say there must be no style checks in the markup. MAUI has no hover on phones, and touch-only Avalonia devices never get `:pointerover`, so the "always visible on phones" rule may not be met on Avalonia mobile or on touch laptops.
2. Resources like `IgUserMessageAlignment` and `IgRunBorderThickness` are `DynamicResource`. Avalonia's headless tests only reflect a theme switch if the test explicitly loads the right dictionary. The tests `GalleryStyle_…` and `NotebookStyle_…` may pass vacuously if the default theme is applied.
3. `HeaderText` depends on generations' `PropertyChanged`. Subscriptions from a run to its generations may leak, may fire many times per update, or may be stale if generations are replaced by 025. They may also race if updates arrive from background threads without marshalling to the UI thread.
4. The `ProgressBar IsIndeterminate` at the bottom of the image runs an animation per running card. With many cards (several models × N) this may be costly on Android and may hang headless tests that wait for idle.
5. Status is accessible only by text, but the criteria require the label text always exist. A card label used as `Border.status` with a status class could still be missing a text for `Queued` or `Cancelled`. The accessibility test covers only Avalonia, and nothing in the plan covers MAUI `SemanticProperties`.
6. The plan lists only four Avalonia style tests. `Failed`, `Cancelled`, the 3:2 ratio, the overlay visibility rule and the MAUI phone grid have no tests, and MAUI is only built, never run. A regression in those would go unnoticed.
7. `PromptText` currently has a "Prompt: " prefix, while the new prompt block is a styled `Border`. Dropping the prefix changes `RunPromptFormat`, and existing tests and the accessible name may depend on it. After 057 the prompt may already be shown elsewhere, so it may show twice.
