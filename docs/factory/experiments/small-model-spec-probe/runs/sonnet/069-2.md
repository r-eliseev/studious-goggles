ASSUMPTIONS
1. "Card is ready" (the Avalonia hover row) is assumed to mean the same as `IsFinished`. The spec says error and filtered cards always show Repeat, but does not say whether `IsFinished` is true for those states, so `ShowActionsCommand` may be disabled on them.
2. The action set in the menu is assumed to be the existing `GenerationItemViewModel` commands, with the labels from the mock-up. The spec does not say where the label strings live (resource keys in `implementation.md` or hardcoded), or whether they are localized.
3. "Phone" versus "Windows/Mac" in MAUI is assumed to be decided by `DeviceIdiom`/`DevicePlatform`. The spec gives no criterion, so iPad, Android tablets and foldables are undefined.
4. The Avalonia `ChooseAsync` is assumed to be a modal window that returns the option string, and a null result means cancel or close. Matching the choice back to an action by label string is assumed to be acceptable.
5. The `ShowActionsCommand` header is assumed to skip empty parts of `ModelText`/`SeedText`/`CostText`/`TimeText`. The spec only says to join them with " · ".

QUESTIONS
1. For error and filtered cards, which actions does the "…"/context menu offer, and does the Avalonia hover row show only Repeat? The spec only says Repeat is always visible, while `ShowActionsCommand` is available only when `IsFinished`. This is contradictory for phones: how does an error card get a "…" menu?
2. The "More" button on a finished Avalonia card is said to open the same `ContextMenu`. Should "Edit" and "Describe" in the hover row duplicate menu items, and should the menu's "Write a prompt from image" have its own command? The spec lists five menu items but the existing commands are not named, so is there a command for each?
3. Is `ChooseAsync` required to take a `CancellationToken`? Is the "cancel" argument also used by the Avalonia window, and what should the Escape key do there?
4. Which MAUI platforms get the `MenuFlyout` and a visible "…" button? Linux/Avalonia is separate, but is the `MenuFlyout` for Mac Catalyst only (MAUI Windows is WinUI)? Is a long press also expected on Windows/Mac touch screens?
5. What accessible names and tooltip texts should the Avalonia icon buttons have? Are they new resource keys, or existing ones in `implementation.md`? The `IconButtons_HaveAutomationNames` test needs concrete values.
6. Is the "…" on phones always visible, or only for finished cards? The spec says nothing about its position and size, nor about touch target size.

RISKS
1. Avalonia has no built-in `:focus-within` pseudo-class in some versions. Check that the installed version supports it, or the selector `Border.card:focus-within StackPanel.card-actions` will silently never match. The step 4 test `Actions_VisibleOnFocusWithin` may also not trigger it in headless mode.
2. Hidden buttons (`IsVisible: False`) are not focusable, so keyboard focus can never enter the card to trigger `:focus-within`. Keyboard users therefore may never reach the icons unless the card itself is focusable.
3. In MAUI, `TouchBehavior.LongPressCommand` and a tap/scroll gesture on the card can conflict, and the long press may fire together with the tap. On Android a long press inside a `CollectionView` or `ScrollView` can be swallowed by scrolling. `TouchBehavior` may also break the card's own tap behaviour or accessibility.
4. `Shell.Current.DisplayActionSheet` can be null or called off the UI thread, for example if `ShellDialogService` runs from a command that is not on the main thread. Also, `ChooseAsync` returns null on cancel, but an option whose label equals the cancel text would be ambiguous.
5. Concurrency and state: if the card changes state (`IsFinished` goes false, the item is deleted or repeated) while the menu or bottom sheet is open, the chosen command runs on a stale item. `ShowActionsCommand` should be re-checked with `CanExecute` after the dialog returns.
6. Step 3 already fixes a specific library workaround and the plan tells a small model to stop with `blocked`. The MAUI build is checked only for Android, so the `MenuFlyout` and Windows code path (including `FlyoutBase.ContextFlyout` on non-Windows targets) is never compiled locally. A Windows-only compile error will appear only in CI.
7. Tasks 068 and 072 both change `AvaloniaDialogService`, so merge conflicts or a changed dialog pattern are likely. The new `ChooseAsync` must also be added to every test double, and any missed implementation breaks the build.
