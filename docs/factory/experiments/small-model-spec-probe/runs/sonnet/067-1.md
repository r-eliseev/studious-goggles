ASSUMPTIONS
1. The "Анализ" section leaves the replacement mechanism open ("выбрать при реализации"), while step 2 says `ReplaceAsync` is added "если нужен". I would assume the minimal route is a new `INavigationService.ReplaceAsync(string route)`, implemented in both shells.
2. The spec does not define "current session" when the chat is a new, unsaved session. I would assume `CurrentId` is `null` and no list item is highlighted until the session has an id.
3. Step 0 (destructive confirm) is unrelated to the wide-window title. I would assume it is a prerequisite fix from 072 that must be done here, and that `ConfirmAsync(..., destructive: true)` already exists.
4. The 840 threshold is assumed to be inclusive (≥ 840), identical to the handler in 066. The MAUI `AdaptiveTrigger` uses `MinWindowWidth`, so I assume 840 is the value there.
5. I assume the single `SessionsPageModel` singleton is shared by the list screen and the chat screen. Therefore the list's scroll position, selection and loaded state are shared too.

QUESTIONS
1. "New session" on the wide chat creates a session: does it also replace the current chat, or push it onto the stack? The acceptance criteria only describe replacement for selecting an existing session.
2. What happens when the user selects the session that is already open in the chat? Should it be a no-op, or reload the chat?
3. If the user deletes the currently open session from the side list (step 0), where should the chat go? The spec does not say whether to navigate to an empty state, another session, or the list.
4. The tracker contract is unclear. Who clears `CurrentId` when the chat is closed or the user goes back to the list? Otherwise the list screen (066) would show a stale highlight.
5. Is `ICurrentSessionTracker` mandatory, or only used "если это ломает тесты"? The "Анализ" section and step 1 disagree, and the tests `OpenChat_MarksSessionCurrent` and `OpenAnotherChat_MovesMark` depend on the choice.
6. How does the narrow-to-wide transition behave at runtime (window resize, rotation)? In particular, if the user resizes while on the list screen, should it jump into a chat?

RISKS
1. Back-stack semantics differ between the shells. MAUI `//sessions/chat?...` or `../chat` may re-create or re-register the page differently from Avalonia. The test `SelectSessionInChat_ReplacesChat` covers only Avalonia, so MAUI replacement behaviour is unverified, since Windows runs are manual (016).
2. Replacing the chat while a generation is in progress or the draft is unsaved may leave the old `ChatPageModel` running, or lose the draft. The spec does not describe cancelling or disposing it.
3. Ordering and race: if `ChatPageModel` reports the new session to the tracker on load, a quick succession of selections can leave `CurrentId` pointing at the wrong item. The old chat's unload could also reset it after the new chat's load.
4. A singleton `SessionsPageModel` with a `ContentView` bound via DI `BindingContext` is hosted in two pages. In MAUI, the old page's list view may keep subscriptions alive after replacement, causing leaks or duplicated handlers. In Avalonia, a single view instance cannot be attached to two visual trees at once, which is why each screen needs its own `SessionsListView` instance.
5. `IsCurrent` is set only on loaded items. If the list reloads, filters or paginates after `SetCurrent`, new `SessionItemViewModel` instances lose the mark unless `SetCurrent` is re-applied.
6. Headless Avalonia tests check width-based visibility via the handler "как в 066". Visibility that depends on layout passes may be flaky unless the test forces layout at a given size.
