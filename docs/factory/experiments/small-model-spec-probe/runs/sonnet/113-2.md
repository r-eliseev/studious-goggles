ASSUMPTIONS
1. "Safe ids/status" is assumed to mean GenerationId, SessionId, ProviderId and the status enum. Prompt, file paths, provider error text and `exception.Message` are assumed to be excluded. The spec lists the fields only for the supervisor Error (step 4) and does not define "safe" for the subscriber-failure log in step 5.
2. Step 6 says the supervisor does not persist a second Failed status. I assume a generation whose terminal update (Completed/Failed) fails stays in its last persisted status, for example Running, in the DB. The UI shows nothing for it until 125/122 or a restart. The spec does not say this is acceptable.
3. The "Debug" detail record is assumed to be written by the same logger, under the "logging policy of the project". That policy is not quoted, so I assume it exists and that Debug is off by default in production.
4. "Own cancellation 108" is assumed to mean the cancellation token owned by the generation job. An `OperationCanceledException` from a provider timeout or a foreign token would then count as an unexpected Error. The spec does not define the distinction.
5. Repository `UpdateGenerationAsync` is assumed to be the only write path that must be strict. Other `RunRepository` methods that suppress zero-row results are assumed to be out of scope.

QUESTIONS
1. In "Failure of the intermediate Running status stops work before the provider call", is the Running update itself the failing call? Does the exception go through the same `Launch` supervisor (one Error log, no event)? Or is it handled separately, given that no Failed status can be saved?
2. When a repository exception propagates out of `SaveAndNotifyAsync`, who owns cleanup of already-created state? This covers a file already saved when the terminal update fails (the "DB/file may diverge" problem from the description). Step 8 says there is no file cleanup, so is a file orphaned from the DB the accepted outcome until 122?
3. The criteria say "no false terminal event". Does that also cover a subscriber throwing after a confirmed update? Step 5 keeps that catch, but the event has already fired. Is the event then true, and should it be logged as an Error or a Warning?
4. Is `IsTransient` deliberately false for any exception thrown by `ExecuteNonQueryAsync` (for example `SQLITE_BUSY`)? Or does Data map `SqliteException` to transient now? Step 1 only specifies zero-row, and 125 needs that mapping.
5. The step 2 test relies on the primary key to rule out affected>1. If the table has no PK or unique constraint on the id, or the query filters on a different column, does the "multiple rows" branch need a real test?
6. Does `StorageWriteException` need the generation id as a property, or only in the message? The tests check for a "safe generation id", and the logger must not log the message.

RISKS
1. Step 6 logs no exception on the Error, yet `StorageWriteException.Message` carries the generation id. The Debug record includes the full exception, so inner `SqliteException` text (SQL, file paths) could reach logs. Confirm that the Debug-only rule covers `InnerException` and `ToString()`.
2. Subtle ordering: the repository update must come before `LogStatus` and the event, and `LogStatus` must run once per confirmed transition. If the retry in 125 wraps the whole `SaveAndNotifyAsync` rather than only the update, success logs and events will duplicate. The spec guards this only by comment.
3. Failure of Running before the provider call must release the slot and remove the `_running` entry. A catch placed before finally but after slot release, or an exception thrown inside the supervisor itself (for example the logger throwing), could skip cleanup or fault the Task. This breaks "Task completes without fault" and `WhenIdleAsync`.
4. Cancellation versus failure: if the token is cancelled while a repository update is in flight, the DB write may or may not have committed. The exception type (`OperationCanceledException` versus `StorageWriteException`) then affects whether it is logged as Error. A "cancelled but committed" state is possible with no event.
5. Existing substitutes or tests that mock `UpdateGenerationAsync` to return a completed Task on a nonexistent id now follow a different path. Tests that rely on silent success may start failing beyond the 106 boundary test mentioned.
6. SQLite via ADO.NET: `ExecuteNonQueryAsync` returns -1 for statements that are not UPDATE/INSERT/DELETE, and triggers do not count towards the total. Check that `RunRepository` uses a plain UPDATE with no triggers or `INSERT OR REPLACE`, otherwise "exactly 1" may be wrong.
