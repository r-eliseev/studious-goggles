ASSUMPTIONS

1. `ChatPageModel.Items` is assumed to be one `ObservableCollection` instance that `ReloadAsync` clears and refills (Reset, then Adds). The MAUI plan subscribes to `_model.Items.CollectionChanged` once in `OnAppearing`, so a replaced collection would silently lose the subscription.
2. I assume `ScrollTo(Count-1, ScrollToPosition.End, animate: false)` on Android shows the bottom edge of a last row taller than the viewport. The analysis says a visible last index does not prove the bottom edge is visible, yet the MAUI side relies on `ScrollToPosition.End` for exactly that case. This is unverified, and RecyclerView often aligns an oversized item by its top.
3. I assume every `OnAppearing`, including returning from another page, resets follow and jumps to the end through `RowsChanged()`. That discards any scroll position the user had before leaving. It is consistent with "открытие → в конец", but the spec does not state it.

QUESTIONS

4. Which actions call `ReloadAsync`: only user actions, or also generation completion or status changes? Decision (1) makes every `Items` change scroll to the end even if the user scrolled up. If a reload fires when a generation finishes, it contradicts decision (3) and the manual scenario 4 ("прокрутить вверх во время генерации → не дёргается").
5. The criterion "Поведение совпадает с Avalonia" conflicts with decision (4), which rewrites the Avalonia behaviour. What is the reference: old Avalonia, new Avalonia, or the rules in `TranscriptFollower`? Also, MAUI gets only a markup test (`Transcript_IsNamedCollectionView`). Is the task done without any automated check of the MAUI scroll logic, with the Android check deferred to 140?
6. Step 7 says to "дополнить Avalonia headless-тесты" for four scenarios, but they are not specified. How should a run card grow in headless mode when the image zone is fixed at 264×176 and 133 has not landed? Which test names and fixtures apply? Without that, "рост последнего run" is not testable as written.
7. When exactly are `_programmaticScroll` (Avalonia) and the MAUI guard reset? The spec says "после отложенного UI-dispatch" for MAUI and says nothing for Avalonia. Layout-driven `ScrollChanged` and `Scrolled` events arrive later than the synchronous `ScrollToEnd`/`ScrollTo` call. Resetting too early lets self-inflicted events flip follow; resetting too late swallows real user gestures.

RISKS

8. MAUI `ItemsViewScrolledEventArgs` carries no extent or viewport deltas, so layout-driven scrolls look like gestures. Keyboard opening, viewport shrink, `Clear()` clamping the offset and row shrink can all produce `VerticalDelta < 0`, which calls `UserScrolled(false)`. A following list would then stop following, and the following `SizeChanged` would not scroll, so the last row stays hidden under the keyboard (manual scenario 5).
9. The per-row `SizeChanged` handler `OnTranscriptRowSizeChanged` in the `DataTemplate` fires on initial measure and on recycling during any scroll, not just on image growth. While `IsFollowing` is still true, a user's first upward flick can be overridden by a `ScrollTo` triggered by a row measure, before `Scrolled` flips follow. A `ScrollTo` → measure → `SizeChanged` → `ScrollTo` loop is also possible. Coalescing through `_scrollPending` does not remove this.
10. On first open, `Dispatcher.Dispatch` after `OnAppearingAsync` may run before `CollectionView` has measured its rows. With variable-height, virtualised rows, `ScrollTo(..., animate: false)` can then be a no-op or land short, which violates "при открытии сессии лента стоит в конце". In Avalonia, ignoring `ScrollChanged` while `_scrollPending` can likewise drop a genuine user scroll that arrives in that window. The Avalonia tests set `t.Offset = 0` programmatically and rely on `ScrollChanged` being classified as a user gesture, which depends on delivery order and the guard flags and may be flaky.
