ASSUMPTIONS:
1. I would assume `IgCardShowShortMeta` is simply the logical inverse of `IgCardShowFullMeta` in every theme, and must be kept in sync by hand in both the Avalonia (061) and MAUI (062) dictionaries. The spec does not say who guarantees this.
2. I would assume the "Notice" lines (`NoticeText`) are shown on every card in every status, including Failed, Filtered and Cancelled. The spec only says "on each card" and does not say whether they are hidden when there is no image or generation.
3. I would assume `TimeText` is empty when `CompletedAt` is missing (Running, Queued, Failed, Cancelled). The Analysis says only "if present in `Generation`, check `CompletedAt - CreatedAt`", and the time format is not given.
4. I would assume `IgCardShowOverlay` and the hover/always-visible behaviour on phones come from resource values per platform. "Always visible on phones" is not described as a resource for Avalonia, which has no `:pointerover` on touch, so I would have to decide how it is enforced.
5. I would assume the 840 breakpoint (2 columns) is implemented by width-based logic in Avalonia. The spec names no mechanism, and `UniformGrid` columns do not adapt by themselves.

QUESTIONS:
1. The "Prompt: " prefix in `RunPromptFormat` and the "show the prompt once" check after 057 are left open. What is the expected result, and should the prefix be removed in favour of the `IgPrompt*` block with its own label?
2. The criteria say "no style checks in markup", yet the plan requires `IsVisible` bound to `IgUserMessageRoleVisible` and `IgCardShowOverlay`/`:pointerover`. Is a resource-bound `IsVisible` allowed, and is `:pointerover` considered a style check?
3. Which statuses does `StatusKind` map from, given that `Generation` states are not listed? How are Cancelled and Failed told apart, and what happens when the status is unknown or changes mid-run (Running → Done)?
4. What text and format does `HeaderText` use for edge cases: 1 model × 1 (singular?), 0 done, failed/filtered/cancelled counts, unknown cost, and different currencies? Do failed or filtered generations count as "done"?
5. The Description says unsent-parameter lines come "under the prompt" (the mockup), while the plan puts them on each card. Which wins, and does a run with N cards repeat the same line N times?
6. Where do the header chips (Models, Assistant, Parameters) lead? The Description lists three chips, but the plan lists only Models and Parameters. Is Assistant omitted on purpose, and are the chips functional or only visual?
7. How does the 3:2 image placeholder behave while the image is loading or if loading fails? Are there separate states for "Done but image missing"?
8. The Analysis says that for `Update_SeedNotApplied_ShowsSeedNotSupported`, "seed not supported" is shown. What exact string and resource key are used, and is it localized?
9. How are the accessibility test (mentioned in the criteria) and the "status text on the label" requirement checked? The plan lists no accessibility test, only four style tests.

RISKS:
1. The dependencies 025, 055 and 057 modify the same `GenerationItemViewModel` and chat files. Merge conflicts or a changed `Update` signature are likely, and the plan's step 1 does not say what to do if these have already changed.
2. `HeaderText` depends on subscribing to `PropertyChanged` of each generation, or on a recalculation in `ChatPageModel`. This risks leaks when generations are added or removed and recalculation races on background updates (UI thread marshalling), and the spec does not say which of the two options to choose.
3. `:pointerover` on the Avalonia overlay does not work for touch or keyboard users, so the strip's seed/time stays hidden on desktop to keyboard and screen-reader users. This conflicts with "status/data not conveyed by colour only" and the accessibility test.
4. `DynamicResource` bound to non-brush values (`HorizontalAlignment`, `Thickness`, `bool` for `IsVisible`) in Avalonia and MAUI is fragile. MAUI `DynamicResource` does not accept all types equally, and a type mismatch or a missing key at runtime fails silently. Theme switching at runtime must also re-evaluate these.
5. Wrapping the image in a `Border` with `ClipToBounds` and a `CornerRadius` from `IgCardImageCornerRadius` may clip differently in MAUI (rounded corners need `RoundRectangle`/`Clip`), and the MAUI step is just "the same" with no detail. The MAUI build is only checked on Android, so Windows-specific failures are caught late by CI.
6. A `UniformGrid`/`WrapPanel` that is 3 columns wide with a 780 max width gives about 250px cards. A long error or filtered text, or very long model names, may overflow or change card height, and the spec sets no truncation rules.
7. Phone detection through `OnIdiom` in MAUI versus a width breakpoint in Avalonia can give different results on tablets and narrow desktop windows. There is a "Gallery strip always visible on phones" requirement, but no test covers it.
8. Step 4 tests check only Gallery and Notebook styles and two statuses. Failed, Cancelled, Running and the assistant error card have no test, and the headless Avalonia tests check no hover behaviour.
