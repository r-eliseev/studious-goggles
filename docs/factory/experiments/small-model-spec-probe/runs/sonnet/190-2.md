ASSUMPTIONS:
1. The "hidden" image temp file is matched only by name, so `images/<session>/.<name>.<32 hex>.tmp` is deleted wherever it appears under `images/`. I assume no legitimate user file matches `^\..+\.[0-9a-f]{32}\.tmp$`. Recursion into all subfolders is assumed to be intended, not just one level of session folders.
2. "Older than 1 hour" is judged by `LastWriteTimeUtc` alone. I assume an in-progress write keeps updating the mtime, or finishes within the hour, and that clock skew is negligible.
3. Hex is lowercase only, because `Guid.ToString("N")` yields lowercase. I assume the regexes must stay case-sensitive, and that on Windows the name checks are not meant to be case-insensitive.
4. `FileImageStore` already knows the data folder root and the `images/` path, and has a logger for the Warning. The spec never confirms either, and 177 may change that file.

QUESTIONS:
1. The spec says "Warning (имя файла и тип исключения)", but step 2 only names `IOException` and `UnauthorizedAccessException`. Should other exceptions, such as `PathTooLongException` (an `IOException` subclass) or `SecurityException`, also be caught? Should a failure while enumerating a directory (as opposed to deleting a file) also be non-fatal? The criterion says startup must not crash.
2. Should `DeleteOrphanedTemporaryFiles` return only successful deletions? The Data test list covers only the success counts and the missing-`images` case.
3. Which Presentation tests are required for the failure path? The criteria require a Warning and continued traversal, but the plan has no test for a locked or undeletable file, and none for a failing `fileStore` inside `AppInitializer`.
4. Is `AppInitializer` supposed to guard the `Task.Run` call with try/catch? Step 4 puts the call after `database.InitializeAsync` with no handling. An exception that escapes the traversal, such as a failing directory enumeration, would abort initialization and contradict "запуск не падает".
5. Step 4 says "в фоне" in step 2, but the code awaits `Task.Run`. Should startup wait for the cleanup to finish, or should it be fire-and-forget? Awaiting delays startup on a large `images/` tree.
6. The criteria say "Среда: Linux или Windows", but step 5 builds `ImageGen.Maui` for Android. Does the cleanup run on Android, where the data folder and filesystem behaviour differ?

RISKS:
1. `Directory.EnumerateFiles(..., AllDirectories)` throws mid-enumeration on an unreadable subfolder or one deleted concurrently. If the try/catch wraps only the delete, a single bad directory aborts the whole sweep and possibly startup. The plan should use `EnumerationOptions { IgnoreInaccessible = true }` or equivalent.
2. Deleting while enumerating can behave differently across platforms. Materializing the list first is safer.
3. `File.GetLastWriteTimeUtc` returns 1601-01-01 for a nonexistent file instead of throwing. If the file is removed between enumeration and the check, it looks very old and then fails or no-ops on delete. Also, a file copied or restored with an old mtime could be deleted despite being fresh.
4. A race with an active writer: a temp file whose mtime was set at creation but is still being written for over an hour, such as a very large or slow image, would be deleted. On Linux this unlinks the file under the writer, so the final `File.Move` fails.
5. Adding a method to `IImageFileStore` in Core breaks every implementation, including those in Maui and Avalonia test doubles. The plan only greps `*Tests*`, so a non-test implementation, such as an Android-specific store, could be missed until the Maui build.
6. The new constructor parameters of `AppInitializer` change DI resolution. If `IImageFileStore` or `TimeProvider` is not registered in a head project (Maui or Avalonia), startup fails at runtime, not at compile time. The `ShellHarness` check in the plan is only a "verify".
7. The Presentation test uses a real `FileImageStore` and sets the file time with `SetLastWriteTimeUtc`, while `AppInitializer` takes `now` from `TimeProvider`. If the test provider is a fake with a fixed date, the "2 hours old" arithmetic may not match. The test must use the same time source.
8. The ordering dependency on 177, "делать после её слияния", is not checked in the plan. If 177 renames the temp-file patterns or moves the writer, the regexes will silently drift from the actual names. A shared constant or a test that generates a name with the real writer would prevent this.
