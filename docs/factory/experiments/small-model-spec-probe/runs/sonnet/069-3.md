ASSUMPTIONS
1. Step 2 says `Border.card:focus-within`, but Avalonia has no built-in `:focus-within` pseudo-class. I would assume it must be added (a custom pseudo-class set from focus events or a `FocusAdorner`/`IsKeyboardFocusWithin` equivalent), although the plan treats it as a plain selector.
2. The "phone" versus "Windows/Mac" split in the MAUI step is assumed to rely on `DeviceInfo.Idiom` or `DeviceInfo.Platform`. The spec does not name the check, nor how tablets (Android/iPad) are classified.
3. The "visible Repeat button always" rule for error and filtered cards is assumed to apply on both desktop and phone, and to override the hover-only hiding. How it fits the `card-actions` row (the Repeat alone, or the whole row) is not stated.
4. The `ShowActionsCommand` option labels are assumed to be existing resource strings from `implementation.md`. The spec lists "Edit prompt…" and "Describe image" in the menu but "Edit" and "Describe" in the icons, so I assume different label sets for each.
5. I assume `ShowActionsCommand` shows exactly the five actions in the same order as the desktop menu. The spec does not say whether actions disabled by their own `CanExecute` are omitted or shown.

QUESTIONS
1. The `ShowActionsCommand` title joins `ModelText`, `SeedText`, `CostText` and `TimeText` with " · ". What happens when one is empty (for example no price or time yet)? Should the separators be dropped?
2. Does `ChooseAsync` return the option string, so the view model must map the string back to a command? How are duplicate or localized labels handled, and should it return an index instead?
3. The Avalonia `ChooseAsync` is "a window with a list of buttons". How does it handle Escape and a click outside the window, and does it return null for them like Cancel? Does it use the `cancel` string as a visible button?
4. For "More" opening the same `ContextMenu`, where does it anchor, and how is it made keyboard-accessible (Enter or Space on the button, Shift+F10 or the Menu key on the card)? The spec requires accessible names only for the icon buttons.
5. The criteria and the plan say the Windows/Mac `MenuFlyout` is used with a visible "…" button. Which test or step covers this, given that Windows is only checked manually (016)? The plan has no step for Mac Catalyst or iOS.
6. "Depends on 068, 072 (both change `AvaloniaDialogService`)": what are they, and do they conflict with the new method? Should the work wait for them?

RISKS
1. `FlyoutBase.ContextFlyout` and `MenuFlyout` are not supported on Android and iOS in the same way. If the `#if`/platform check is wrong, a phone could get both the flyout and the action sheet, or neither.
2. `TouchBehavior` from `CommunityToolkit.Maui` has `LongPressCommand` but also changes visual states and can intercept taps. It may conflict with the "…" button's tap and with scrolling in a `CollectionView`. The plan says "check the version" but gives no fallback beyond `blocked`.
3. `ShowActionsCommand` is available when `IsFinished`, but the plan does not say how it relates to error and filtered cards. If they count as finished, the sheet would offer actions that don't apply. If not, long-press does nothing on them.
4. Hover-only visibility (`IsVisible: True` in the style) removes the buttons from the layout and the focus order when hidden. Keyboard users therefore cannot tab into the card to trigger `:focus-within`, which defeats the accessibility goal. Likewise `Actions_VisibleOnFocusWithin` in headless tests may pass while real keyboard use fails. Using opacity instead of `IsVisible` is one alternative.
5. Right-click and the "…" button can open a menu on a card whose state changes meanwhile (generation is repeated, deleted or re-seeded). A menu or sheet opened from `ShowActionsCommand` may run an action after the item leaves `IsFinished`. Repeated taps may also open `ChooseAsync` twice, since there is no re-entrancy guard.
6. The headless tests do not cover the new `ChooseAsync` window in Avalonia (focus, return value, cancellation), nor the MAUI action sheet beyond a build. The "Проверка" section only builds the Android target, so XAML errors in the Windows-specific parts would show up only in CI.
