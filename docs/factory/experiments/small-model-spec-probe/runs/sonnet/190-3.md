ASSUMPTIONS:
1. The "defaults.json" pattern is matched only in the data-folder root (TopDirectoryOnly), and the image pattern only under `images/`. Temp files in other places, such as `images/` root files not inside a session folder, are assumed either out of scope or covered by AllDirectories. The spec does not say which.
2. "Older than 1 hour" is assumed to mean strictly greater (`now - lastWrite > olderThan`), judged by last-write time. A file that is still being written keeps updating its mtime, but a long write with no flushes could look stale. The spec treats mtime as a sufficient "in use" signal.
3. The regex is assumed to be case-sensitive lowercase hex, because `Guid.ToString("N")` yields lowercase. The image pattern `^\..+\.[0-9a-f]{32}\.tmp$` is assumed to run against the file name only, not the full path.
4. `IImageFileStore` is assumed to have no implementations outside the repository's test doubles, and Maui/Android has no other `AppInitializer` construction path. The spec only mentions Avalonia tests and `ShellHarness`.
5. The data folder root is assumed to be reachable from `FileImageStore`, since the spec has it scan both `images/` and the root. The spec never says how `FileImageStore` obtains that path, or whether `defaults.json` lives in the same root.

QUESTIONS:
1. Step 2 says "Warning" on `IOException`/`UnauthorizedAccessException`. Should failures from `EnumerateFiles` itself (a session folder deleted or locked mid-walk) also be caught? The acceptance criteria say "launch does not fail", but the plan only wraps per-file deletion.
2. Step 4 puts `DeleteOrphanedTemporaryFiles` on `IImageFileStore`. That interface is about images, yet the method also deletes `defaults.json` temp files. Is that placement intentional, or should the defaults cleanup live elsewhere?
3. Should the Warning log include the file path, or only the name? The criteria say "имя файла и тип исключения", and a bare name could be ambiguous across session folders. Should the deleted-count or each deletion be logged at Info?
4. The plan runs the cleanup inside `InitializeAsync` and awaits it via `Task.Run`, while the "Анализ" section says "в фоне". Does startup block on the scan, or should it be fire-and-forget? On a large `images/` tree this affects startup time.
5. The "Критерии готовности" require tests in Data and Presentation, but the check list also runs Avalonia and Maui builds. If `ShellHarness` constructs `AppInitializer` through DI, is it expected to compile unchanged, and who decides between "manual" and "DI"? The spec leaves that to be checked.
6. The `ILogger` source for `FileImageStore` is not mentioned. Does it already have a logger injected, or must the constructor change, and does that affect DI and tests?

RISKS:
1. The cutoff relies on `File.GetLastWriteTimeUtc`. On a missing file (deleted by a concurrent writer's `File.Move` between enumeration and check) it returns a 1601 sentinel instead of throwing, so the file would count as ancient and the delete is attempted. `File.Delete` on a missing file does not throw, so the count could be inflated. Check existence or catch it properly.
2. A temp file can be renamed or deleted by a live writer between enumeration and `File.Delete`. Deleting a file that a writer on Windows holds open raises `IOException`, which is handled. On Linux the delete succeeds and the writer's later `File.Move` then fails. The 1-hour guard makes this rare but not impossible, for example after a clock jump or an old-mtime file copied in.
3. Startup cleanup can race with the very first generation or save if `InitializeAsync` finishes the DB step and other code starts writing while the scan runs. The mtime guard protects only fresh files.
4. `Directory.EnumerateFiles(..., AllDirectories)` throws on the first inaccessible subdirectory unless `EnumerationOptions.IgnoreInaccessible` is used. One bad session folder could abort the whole sweep. Note that `SearchOption` overloads default differently from `EnumerationOptions` here.
5. The image pattern `^\..+\.[0-9a-f]{32}\.tmp$` is greedy and loose. A user's hidden file like `.foo.<32 hex>.tmp` is deleted, which contradicts "чужие файлы не трогаются". The spec accepts this, but a stricter check (for example requiring an image extension before the hex) would reduce the risk.
6. Time-dependent tests use `File.SetLastWriteTimeUtc` plus a `TimeProvider`. On Windows and on some Linux filesystems timestamp resolution or timezone handling can cause flakiness near the 1-hour boundary, and the plan has no boundary test (exactly 1 hour).
7. Adding a method to `IImageFileStore` breaks every implementation in the repo, including the Maui project, which is not in the "Файлы" list. Combined with the Luna rule "do not change files outside the Файлы line", a missed test double or a Maui implementation would stall the task.
8. Wrapping synchronous I/O in `Task.Run` inside `InitializeAsync` means exceptions other than the two caught (for example `PathTooLongException`, `SecurityException`, `DirectoryNotFoundException`) would propagate and fail startup, contradicting "запуск не падает". The catch list in step 2 is too narrow.
