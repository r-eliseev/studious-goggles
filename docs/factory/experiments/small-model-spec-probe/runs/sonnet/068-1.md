I assume `IgUserMessageBackgroundBrush`, `IgRunBorderThickness`, `IgCardShowOverlay` and similar keys already exist in both dictionaries exactly as named in `implementation.md` section 2.4. Only `IgCardShowShortMeta` is added by this task.
2. "On phones always visible" for the Gallery overlay strip is decided by idiom (`OnIdiom`) in MAUI only. I assume Avalonia has no phone target, so the strip there depends on `:pointerover` alone.
3. `TimeText` comes from `CompletedAt - CreatedAt` when both exist. I assume it is empty or hidden otherwise, and for Running, Queued and Cancelled cards. The format (e.g. "4.2 s") is not specified.
4. `NoticeText` (parameter lines) is shown on every card in every style. This replaces the mockup, which shows it once under the prompt.
5. "Cancelled" has no stated placeholder. I assume a neutral background and a `Cancelled` label, with no dedicated icon or soft brush.

QUESTIONS
1. The Notice-per-card decision contradicts the mockup and the "run block" description ("a line about parameters not passed"). Is that line also supposed to appear in the run block? Which is authoritative for acceptance? The "решение владельца в 074" also references a task that is not in the dependency list.
2. How should `IsVisible` combine `IgCardShowOverlay` and `:pointerover` in Avalonia? A pseudo-class cannot be combined with a DynamicResource binding in `IsVisible` directly. Is a style selector with a setter intended, and where does the rule live, given "no style checks in markup"?
3. What does `Update_SeedNotApplied_ShowsSeedNotSupported` expect as the exact string and source (a resource string or a hard-coded one)? Localisation of the new strings ("Filtered by the provider…", "Assistant is thinking…", the `HeaderText` format) is not mentioned; are they resource strings (the spec says "строки")?
4. `HeaderText` ("2 models × 3 · 2 of 6 done · $0.028"): how are "models" counted (distinct models in the run?), what is "×3" (images per model?), what counts as "done" (Succeeded only, or also Failed, Filtered and Cancelled), and how is cost shown if some prices are unknown or the currency differs?
5. Both the 3-column and the 2-column (<840) layouts are specified for Avalonia. Is 840 measured against the window or the feed (max 780)? With a 780 maximum feed, 3 columns at ≥840 window width gives narrow cards. Does `UniformGrid` support a responsive column count, or is a container query needed?
6. What are the keyboard and accessibility requirements of the Avalonia accessibility test? Specifically: the accessible names for the icon-only chips, the clip and send buttons, and the "Assistant is thinking…" indicator. Does `SummaryText` need to include the status text?
7. The message-input behaviour (attachments, send disabled while empty or while running) is not described. Is it unchanged from the current implementation?

RISKS
1. Dependencies 025, 055 and 057 change the same files (`GenerationItemViewModel`, `ChatView`), so merge conflicts are likely. The plan builds on property names (`DetailsText`, `PromptText` with the "Prompt: " prefix) that may already have changed. Step 1 should start with a re-check of the actual state.
2. `HeaderText` must refresh when generations change status. Subscribing to `PropertyChanged` on every generation leaks handlers when items are replaced or the chat is reloaded. Recomputing from `ChatPageModel` can race with background updates not marshalled to the UI thread.
3. `StatusKind` and `IsQueued`/`IsFiltered`/`IsCancelled` duplicate one state. `Update` could set them inconsistently during transitions (e.g. Queued→Running→Done), leaving stale placeholders or two overlapping ones. Retried or repeated generations that reuse the same view model have the same problem.
4. `ClipToBounds` plus `IgCardImageCornerRadius` on an image with a fixed 3:2 ratio. The ratio itself is not defined for Avalonia (no `AspectRatio` property), and there is no fallback when the image is missing or is not 3:2.
5. `Border.status` with a status class: the status class must be toggled when the status changes. Stale classes (e.g. both `running` and `done`) are a typical bug. Also, `ProgressBar IsIndeterminate` keeps animating even when the card is off-screen, which is a possible performance problem in long chats.
6. The `:pointerover` overlay is unreachable by keyboard or touch on Avalonia desktop. Seed and time are then reachable only by mouse, which conflicts with "status not conveyed by colour only" and with the accessibility test.
7. MAUI: `DynamicResource` for `IsVisible` and `Padding` with `OnIdiom`, in a `DataTemplate` chosen by `ChatItemTemplateSelector`, behaves differently from Avalonia. Resource changes at runtime (a style switch) may not re-render items in a `CollectionView` that has already been created. The Android build is the only check on Linux, so layout errors will not be caught until a manual Windows run.
8. The test list is thin. `ChatViewStyleTests` cover 4 of the 6 statuses and nothing covers Failed, Cancelled, the assistant error, the thinking indicator, the 2-column mode, or the overlay visibility under `IgCardShowFullMeta`. The criterion "tests pass" therefore does not prove the stated acceptance criteria.
9. The plan's rule "on any failure, mark `blocked` and stop" combined with new keys (`IgCardShowShortMeta`) added to the 061/062 dictionaries means a missing key at runtime throws or yields a silent default. There is no test that both dictionaries contain the same set of keys.
