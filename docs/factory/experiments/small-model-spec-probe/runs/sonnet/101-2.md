**ASSUMPTIONS**

1. Per query token, `Match` takes the best-scoring word, and `FirstIndex` is the index of that word. The spec does not say how scores combine over several matching words. The expectation `FirstIndex` 4 for «brige» in «two bridges» depends on this.
2. By the time `ScoreWord` runs, tokens and words are already case-folded and non-empty, and comparing them as UTF-16 chars is enough. The `token[0] != word[0]` check and the `word[..length]` slice depend on this.

**QUESTIONS**

3. Criterion 4 requires finding out in this task whether Android search updates on not-yet-committed keyboard text, and fixing it or splitting it out. The plan defers the check to task 140 and forbids changing Presentation/MAUI code. Can the task be closed as `done` without that finding in the «Отчёт»?
4. Does the new prefix-typo rule apply to every query token or only to the last one? The motivation is that only the last word is unfinished. Applying it to all tokens widens the noise in multi-word queries, where every token must match.
5. Should prefix-typo tolerance apply to numeric tokens? A token like «2024» would match any word starting with «202». The plan covers digits only with `Match_DigitToken_ExactPrefixWins`, and its input is not given.
6. `Match_EmptyQuery_ReturnsNull`, `Match_EmptyText_ReturnsNull` and `Match_DigitToken_ExactPrefixWins` have no inputs or expected values. `Match_CyrillicTypoInPrefix_Scores1` is called a regression, but «водопо»→«водопад» has whole-word distance 2 and fails today. This contradicts «first four fail, the rest pass».

**RISKS**

7. The noise estimate in «Анализ» (no more than a 3-letter query) is too optimistic. For a 4-letter token, a substitution inside the 4-letter prefix also matches (`L=|t|`). «rain» matches «ruined» and «cats» matches «carton», and neither starts with a 3-letter prefix of the token. Also, a user typing «wate» now also matches «watch» at score 1.
8. «Exact prefix ranks higher without changing weights» holds only within one text kind. A Title typo (1×3) ties with an exact Description prefix (3×1) and loses to a Prompt substring (2×2). The tie-break order is unspecified, and `Search_ExactPrefixBeatsTypo` only covers the same kind (Prompt).
9. More fuzzy matches make it likelier that `FirstIndex` points at a weak earlier typo match instead of the exact one. That would shift the snippet and highlight. The existing Avalonia test `Search_FindsSessionByPromptWithTypo_ShowsSnippet` only covers a whole-word typo, so it will not catch this.
10. The new branch runs for most words, up to three `Distance` calls plus three `word[..length]` string allocations per word per token. This repeats every 250 ms while typing, over all sessions' texts, on a phone. That could cause lag on large histories.
