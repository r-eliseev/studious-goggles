ASSUMPTIONS
1. The spec's `Items` is the same `ObservableCollection` instance for the page's whole lifetime. MAUI `OnAppearing` subscribes `_model.Items.CollectionChanged` before `OnAppearingAsync`, and `OnDisappearing` unsubscribes it again. If `ReloadAsync` or the model ever replaces the collection, the subscription goes stale and nothing scrolls.
2. `ReloadAsync` is only triggered by user actions, as in "после каждого действия", and not by generation completion or background events. Otherwise decision (1) ("любое изменение `Items` скроллит в конец") yanks a user who scrolled up to read during generation, which contradicts decision (3).
3. `ScrollToPosition.End` aligns the bottom edge of an item taller than the viewport, on both Android and Windows. The spec itself says the last run can be taller than the viewport, and the whole MAUI design depends on this unverified behaviour.

QUESTIONS
4. Step 7, `OnTranscriptScrolled`: any downward movement when the last index is visible gives `UserScrolled(true)` plus `ScrollTo(End)`. With a tall last row, a user who scrolled up inside it and then nudges down is snapped to the end before reaching the bottom, which contradicts manual scenario 6 ("доскроллить к концу"). Should follow resume only when the bottom edge is actually reached, for example by an offset check like `IsAtEnd`?
5. The row-template `SizeChanged` handler (`OnTranscriptRowSizeChanged`) is attached to every row, not only the last. Recycled or virtualized rows fire it whenever they are measured, including during a user's scroll. Should it filter to the last row, and what is the `ContentChanged()` result while the user's gesture is still in progress?
6. The last bullet of step 7 adds Avalonia headless tests inside the MAUI step, with no names. How do they simulate "рост последнего run" when the image zone is fixed at 264×176 in main? Which tests cover the MAUI code-behind logic (guards, `Scrolled` filtering)? Currently only a markup test exists.
7. The criterion "Поведение совпадает с Avalonia" is circular, because Avalonia is itself being rewritten onto `TranscriptFollower` and changes behaviour (it no longer scrolls on user scroll-up for card updates). Is the reference the old or the new Avalonia behaviour? Also, 133 changes card sizes but is not in "Зависит от". Is it merged, and should it be a dependency?
8. How long does `_programmaticScroll` stay set? MAUI says "после отложенного UI-dispatch", and Avalonia gives no timing at all. Native scroll events (Avalonia layout pass, Android `RecyclerView`) can arrive after that point. The spec needs a defined release condition.

RISKS
9. Misclassifying programmatic or reset scrolls as user gestures in MAUI. `Items.Clear()` in `ReloadAsync` makes `RecyclerView` jump to offset 0, which gives a negative `VerticalDelta`, and the late result of `ScrollTo` can also arrive after the guard is cleared. Either one flips `UserScrolled(false)` and permanently stops follow for `CardUpdated` and row growth. Windows `Scrolled` semantics differ from Android and are not accounted for.
10. `ScrollToEndLater` runs `ScrollTo(Count-1)` once per dispatch with no retry. After Clear plus re-adding rows, or on first open before the `CollectionView` is measured, the item may not be realized yet and the call can silently no-op or land short. Gestures made while `_scrollPending` is true are also dropped, so the user can be pulled back to the end right after a scroll-up.
