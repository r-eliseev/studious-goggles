ASSUMPTIONS:
1. The hex in both temp-file patterns is lowercase, because `Guid.ToString("N")` and `{Guid:N}` produce lowercase and the regexes `[0-9a-f]{32}` assume it. Matching is therefore case-sensitive, which on Windows is a deliberate departure from the usual case-insensitive filesystem behaviour.
2. "Older than an hour" means `now - lastWrite > olderThan` by `GetLastWriteTimeUtc`. I assume a writer that is still writing keeps updating the mtime, or finishes well within the hour, so mtime is a safe proxy for "orphaned".
3. The "data folder" and the `images/` root inside it are obtained inside `FileImageStore` from its existing constructor or configuration. The spec names no accessor, so I assume none is needed.
4. The method should not follow symlinks or reparse points in `images/`, and unreadable subfolders should be skipped. The spec does not say so.

QUESTIONS:
1. The "Критерии готовности" say deletion happens "after database initialization". Should a failure of the cleanup itself (for example `DirectoryNotFoundException` or an `UnauthorizedAccessException` during enumeration, not only during delete) also be caught? Step 2 only catches `IOException` and `UnauthorizedAccessException` per file, and the criteria say startup must not crash.
2. Step 2 covers `Directory.EnumerateFiles` over `AllDirectories`, but the acceptance criteria only mention a failure to delete one file. If enumeration of one subfolder throws, should the whole sweep stop or continue with the other sessions?
3. The test list has `.a.png.tmp` (no hex) as a keeper, but the image regex `^\..+\.[0-9a-f]{32}\.tmp$` is greedy on `.+`. Is a name like `.x.<32 hex>.tmp` with no original extension expected to match? Is a nested case in `defaults.json.<hex>.tmp` inside `images/` expected to be left alone?
4. Which logger is used in `FileImageStore`, and is it already injected? The Warning requirement (file name and exception type) needs an `ILogger`, but the plan does not say whether the constructor changes. That would affect DI registration and the existing tests.
5. Is there a test of `Task.Run` in `AppInitializer` that relies on the clock? The "Presentation" test needs a fake `TimeProvider` or file mtimes relative to the real clock. Which one is preferred?
6. Does `ShellHarness` create `AppInitializer` by hand? The spec says "проверить, вручную ли", but `ShellHarness.cs` is listed as "при необходимости" while step 5 says to fix all manual creations. What should happen if the harness is not in the file list but needs changes?

RISKS:
1. Adding a method to `IImageFileStore` breaks every implementer, including fakes or mocks in Avalonia, Maui or other test projects. The `rg` in step 4 searches only `*Tests*` globs, so a non-test implementation (for example in `ImageGen.Maui`) would be missed. The Android build in the verification list is the only thing that would catch it.
2. Android and Maui: the plan says "Linux or Windows", but the verification builds `net10.0-android`. On Android the data folder, the `images` path and the file mtime behave differently, and the cleanup runs on the real device at startup. The spec does not say whether that is in scope.
3. A concurrent writer at startup: another `AtomicImageFileWriter` or `DefaultAssistantModelFile.SaveAsync` may be running while the background cleanup runs. A file under an hour old is protected, but a temp file whose mtime is old (for example, a copied or restored file, or a clock change) could be deleted mid-write. `File.Delete` on Windows may also fail with `IOException` when the file is open, which is handled only by the Warning.
4. `await Task.Run(...)` inside `InitializeAsync` still blocks startup until the sweep finishes, although step 2 says "в фоне". If `images/` is large, with many sessions, this delays `EnsureInitializedAsync`. It is unclear whether it should be fire-and-forget, and fire-and-forget would make the Presentation test racy.
5. Time-of-check vs. time-of-use: the file can be removed or replaced between the mtime check and `File.Delete`. `File.Delete` on a missing file does not throw, but a `DirectoryNotFoundException` on a removed session folder is not in the caught list.
6. The temp files' mtime can be in the future (clock skew, restored backup). `now - lastWrite` is then negative and the file is never deleted. Is that acceptable?
7. The dependency on task 177 touching the same `FileImageStore.cs`: if 177 renames or changes the temp-name template, or the path handling, the two regexes silently stop matching, and the tests would pass only because they use the regex's own template. A test that builds the name via the real writer would guard against drift.
8. The regex `^\..+\.[0-9a-f]{32}\.tmp$` runs on the file name only. If the implementation applies it to the full path or to `Path.GetFileName` inconsistently, the `^\.` anchor would fail on Windows separators. Also, the `AllDirectories` scan on `images/` will treat a user-supplied attachment whose real name looks like `.x.<hex>.tmp` as an orphan and delete it.
