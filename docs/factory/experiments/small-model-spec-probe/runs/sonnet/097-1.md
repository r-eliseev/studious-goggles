ASSUMPTIONS:
1. The spec assumes the card is cut off because the list is not scrolled, not because the `CollectionView` (row 1 of the grid) extends under the input row. The screenshot only shows a card clipped by the input field. If the viewport overlaps the input, `ScrollTo` will not fix it.
2. It assumes that on keyboard open the `Transcript.SizeChanged` event fires, which is how `ViewportChanged()` is meant to work. How 095 handles the keyboard (`adjustResize` and a resized row, versus a translated or margined input) is not stated. If the list is not resized, decision (2) and manual scenario 5 have no trigger.
3. It assumes `ScrollTo(Items.Count - 1, ScrollToPosition.End, animate: false)` on Android aligns the bottom edge of the last row. This is expected to hold for rows that are still unmeasured or taller than the viewport. The criterion "нижний край последней карточки остаётся виден" depends on it, and the spec itself says the last index does not prove the bottom edge is visible.

QUESTIONS:
1. Does `ReloadAsync` run when a generation finishes ("после каждого действия")? If so, decision (1) pulls a user who scrolled up during generation back to the end. That contradicts the intent of decision (3) and manual scenario 4.
2. The criterion "Поведение совпадает с Avalonia" is circular, because Avalonia is itself being rewritten onto `TranscriptFollower`. Avalonia resumes follow by pixels (`IsAtEnd`), while MAUI resumes at the last index. Which one is the reference when the last run is taller than the viewport?
3. When is `_programmaticScroll` cleared on Avalonia? For MAUI it is cleared "после отложенного UI-dispatch", but for Avalonia nothing is said. `ScrollChanged` is raised on a later layout pass, so the timing decides whether programmatic scrolls are mistaken for user gestures.
4. How will the headless tests produce card growth ("рост последнего run")? Card size is fixed at 264×176 until 133 lands. These tests are also added at the end of step 7, after the Avalonia step that is supposed to turn the tests green. No automated test covers the MAUI code-behind logic at all.

RISKS:
1. On Android, `Scrolled` and `VerticalDelta` are known to be unreliable, and `ScrollTo(animate: false)` events can arrive after the guard is reset. A negative delta caused by layout (a row above shrinking, the keyboard) is classified in step 7 as a user scroll up and silently turns follow off. Conversely, dropping events while `_scrollPending` loses real user gestures.
2. With a tall last run, scrolling down to the last index calls `UserScrolled(true)` and immediately requests `ScrollToPosition.End`. This jumps a user who is still reading the middle of the run. It also contradicts manual scenario 6 and the spec's own note that the last index is not proof of visibility.
3. In Avalonia `OnTranscriptScrollChanged`, the `ExtentDelta`/`ViewportDelta` check runs first and exits. A user's scroll-up during generation, when the extent is also growing, is therefore swallowed and `IsFollowing` stays true. The next `CardUpdated` then drags the list back down, which is the exact case in manual scenario 4.
4. A `SizeChanged` handler on every row template root fires on initial measure and on every realization or recycling of rows. This can cause scroll storms while following. `ScrollTo` may also run before the handler or items are ready (empty list, binding not yet applied), where the index may be invalid or the handler null.
5. The `CardUpdated` event is raised inside a queued `BeginInvokeOnMainThread` lambda. The test `CardUpdated_AfterDisappearing_NotRaised` passes only if that lambda re-checks the unsubscribed state, which the spec does not require. In MAUI and Avalonia the pending callbacks, `-=`/`+=` re-subscription and `_subscribed` handling must all agree across rapid appear/disappear. Otherwise there are double scrolls or calls on a detached view.
