# Скриптовый харнес вокруг готовых агентов

Тема добавлена владельцем 2026-11-17 («условно, я запускаю Claude Code в ACP-режиме с задачами, и скрипт его контролирует»). Здесь: что проверено по первоисточникам, как это связано с остальным, что не решено. Метки: **✔** прочитано на странице, **[синтез]** наш вывод.

## Что такое «скрипт контролирует агента»

Вместо того чтобы агент сам читал правила и вызывал скрипты (так сегодня в этом репозитории: исполнитель следует `docs/executor.md` и вызывает `claim-task.sh` и `submit-task.sh`), **управляющий скрипт владеет порядком работы**, запускает готового агента (Claude Code и т.п.) на одной задаче, ограничивает его, проверяет результат и решает, что дальше. В публичных фабриках из `research/factory-kits-code-reading.md` это основной приём: «code owns the graph, agents are bounded nodes» (SSSF и его порт, minifactory, geut: контроллер на TypeScript, навыки только описывают поведение специалиста).

## Поверхности управления, проверенные в документации

- **ACP (Agent Client Protocol)** ✔ ([введение](https://agentclientprotocol.com/overview/introduction)): стандарт общения **редакторов и IDE с кодирующими агентами**; локальные агенты запускаются как подпроцессы и говорят JSON-RPC по stdio, удалённые по HTTP или WebSocket. Важная оговорка из той же страницы: ACP исходит из того, что «the user is primarily in their editor», то есть он **спроектирован как протокол редактор–агент**, а не как протокол оркестрации; скрипт в роли «клиента» это использование не по прямому назначению [синтез].
- **Цикл хода** ✔ ([prompt turn](https://agentclientprotocol.com/protocol/prompt-turn)): клиент шлёт `session/prompt`; агент присылает `session/update` (поток ответа, план, вызовы инструментов); ход заканчивается ответом на `session/prompt` со `stopReason` (например `end_turn`); клиент может отменить ход.
- **Возможности клиента** ✔ ([initialization](https://agentclientprotocol.com/protocol/initialization)): при инициализации согласуются версия и возможности; клиент может предоставлять чтение и запись файлов и терминал.
- **Запросы разрешений** ✔ ([tool calls](https://agentclientprotocol.com/protocol/tool-calls)): агент **может** запросить разрешение перед вызовом инструмента (`session/request_permission`) с вариантами вроде `allow_once` и `reject_once`; клиент **может** автоматически разрешать или отклонять по настройкам. Для фабрики это ключевое место: скрипт-клиент применяет **политику классов риска** (`risk-classes`) и маршрутизирует решения к человеку (`irreversible-actions-through-human`, `deferred-tool-call`) [синтез].
- **Claude Code в ACP** ✔ ([список агентов](https://agentclientprotocol.com/overview/agents)): среди агентов указан «Claude Agent (via Zed's SDK adapter)», то есть через адаптер; подробности адаптера не читались.
- **Другие поверхности Claude Code** ✔ ([headless](https://code.claude.com/docs/en/headless)): `claude -p` для неинтерактивного режима с `--allowedTools` и `--output-format`; Agent SDK на Python и TypeScript с «structured outputs, tool approval callbacks, and native message objects»; в режиме `-p` без `--bare` запускаются хуки из `.claude/settings.json`; на SIGTERM процесс завершает дерево процессов и вызывает хуки конца сессии. То есть для скрипта есть как минимум три способа: ACP, `claude -p`, Agent SDK, плюс хуки.

## Что скрипт может контролировать [синтез, к проверке]

Порядок и повторы задач; бюджет (время, число ходов, деньги); права по классам риска; обязательные проверки (`check.sh`, независимая проверка) до принятия результата; состояние задач вне агента; эскалацию человеку на точках решения (вопросы и запросы разрешений как события, а не как вмешательство в идущий флоу); сообщения человеку по темпу (`outbox-meaning`).

## Проверено в этой сессии (2026-11-17)

- **Файловая система и терминал в ACP** ✔ ([file system](https://agentclientprotocol.com/protocol/file-system), [terminals](https://agentclientprotocol.com/protocol/terminals)): это **необязательные возможности клиента**. Агент «MUST verify» поддержку и «MUST NOT attempt» вызывать метод, если клиент её не объявил. Назначение по тексту: дать агенту доступ к несохранённому состоянию редактора и дать клиенту отслеживать изменения файлов. Это норма для соблюдающих протокол агентов, а **не принуждение**: ничто в протоколе не мешает агенту читать и писать файлы собственными инструментами в своём процессе.
- **Адаптер Claude Code для ACP** ✔ (`agentclientprotocol/claude-agent-acp`, README и исходник `src/v2/agent.ts` на ветке main в момент чтения; черновая ветка протокола v2, путь v1 не читался): адаптер реализует ACP-агента поверх Claude Agent SDK и запускает Claude CLI; поддерживает вызовы инструментов «with permission requests», терминалы, MCP-серверы клиента, в том числе «MCP-over-ACP». В исходнике параметры сессии SDK: `canUseTool` (запрос превращается в `session/request_permission` к клиенту), `permissionMode`, `disallowedTools` (из настроек клиента), `hooks` (в том числе `PreToolUse`), `settingSources: ["user","project","local"]` (подхватываются пользовательские, проектные и локальные настройки Claude Code). Набор инструментов: `tools: client?.tools ?? (params._meta?.disableBuiltInTools === true ? [] : { type: "preset", preset: "claude_code" })`, то есть **по умолчанию включены встроенные инструменты Claude Code**; отключить их и подать собственные инструменты через хост можно флагом клиента.
- **Что это значит для вашего воспоминания «все правки и чтения идут через ACP-хост (скрипт)».** Это возможно, но **не по умолчанию**: нужно отключить встроенные инструменты и обслуживать чтение и запись инструментами хоста (MCP-over-ACP), либо ограничивать встроенные инструменты правилами. Сквозной эксперимент я не запускал.
- **Порядок проверки прав в Agent SDK** ✔ ([permissions](https://code.claude.com/docs/en/agent-sdk/permissions)): хуки; запрещающие правила (из `disallowed_tools` и файлов настроек; **действуют даже в `bypassPermissions` и когда хук разрешил**); правила «спросить»; режим разрешений; разрешающие правила; затем колбэк `canUseTool`. Ловушки для скрипта-контроллера из той же страницы: в режиме `bypassPermissions` и для записей `allowedTools`, состоящих только из имени инструмента (например `Read`), колбэк **не вызывается**; запрет `Bash(rm *)` срабатывает на команду «как написано», а `/bin/rm` проходит дальше. Вывод: списки запретов по шаблону не граница, а подсказка.
- **Требование владельца «агент не должен мочь обойти»** → граница должна быть там, куда агент не дотягивается: изоляция уровня ОС (документация песочницы Claude Code ✔: «The operating system enforces the sandbox boundary on the running process, so it holds regardless of what the model chose to run»), учётные данные вне среды агента (прокси, `always-on-agents` ✔), инструменты чтения и записи, обслуживаемые хостом. Это согласуется с историей обхода запретов ◐ (`owner-dialog-walkthrough.md`, тема про границы).

## Ответы владельца (2026-11-17)

- **Один агент или очередь:** оба варианта; в общем случае несколько агентов и задач.
- **Что контролировать:** права, бюджет, проверки и эскалации; всё остальное вторично.
- **Где запускать:** оба варианта (своя машина и облако).
- **Поверхность:** годится любая поверхность с контролем; **важно, чтобы агент не мог обойти** контроль.
- **ACP как клиент-скрипт:** «это всё ещё хорошо работает и даёт большой контроль над возможностями агента»; по его памяти все правки и чтения идут через ACP-хост, поэтому доступами легко управлять (проверено выше: возможно по настройке, не по умолчанию).
