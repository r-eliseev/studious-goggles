# How to get unambiguous and complete specs; are such specs "almost templates"?

Questions from the owner (2026-11-18), attached to the quote "(trying again) reminded her of the difficulty of writing unambiguous and complete specifications" (Böckeler): how can this be achieved? And the owner's position: he sees no big difference between spec and template; if we learn to write unambiguous and complete specs, they are almost templates, and one step remains: a spec parser plus a code generator. Labels: **primary** = read in the source; **synthesis** = my inference.

## Means, from light to strong
1. **Restricted natural-language templates.** EARS (Mavin and colleagues, Rolls-Royce, RE'09): a small set of structural rules against eight common requirement problems including ambiguity, complexity and vagueness; every requirement fits one of five templates; applied to aero-engine control requirements extracted from an airworthiness regulation, with "qualitative and quantitative improvement" reported by the authors ([Manchester record](https://research.manchester.ac.uk/en/publications/easy-approach-to-requirements-syntax-ears/), abstract read). Limits: author-reported single case study; the paper says it addresses syntax, not semantics (from a search summary of the paper, not read in full).
2. **Examples as the spec** (Given/When/Then). Böckeler saw Kiro write acceptance criteria in that form, and also saw the cost: a small bug turned into 4 user stories with 16 criteria, "I'd rather review code than all these markdown files" ([Böckeler, 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), read). So structure alone does not give quality.
3. **Find the holes by experiment.** Böckeler generated code several times from the same spec and saw different results; making the spec more specific raised repeatability (primary). Synthesis: independent runs that diverge point to under-specified places; this is the same mechanism as N-version diversity (`concepts/error-diversity.md`) used on the spec instead of on the code.
4. **Make the agent ask.** Ambig-SWE (arXiv:2502.13069, Feb 2025, revised for ICLR 2026): models "struggle to distinguish between well-specified and underspecified instructions", but when they do interact, they obtain the missing information and improve "up to 74%" over the non-interactive setting ([abstract](https://arxiv.org/abs/2502.13069), read). Consequence (synthesis): do not rely on the agent noticing a gap by itself; the harness should make "questions" a required kind of result (the `harness-as-function` thread).
5. **Formal specifications** (contracts, TLA+, Alloy and similar): not researched here; belongs to the open question `formal-proof-architecture-and-code`.
6. **Measure completeness by the outcome, not by reading the spec** (synthesis): completeness cannot be proven in general; it is measured by hidden acceptance checks and by defects that come back from use (the feedback loop). This is why independent acceptance tests matter more than a perfect spec.

## The owner's position: spec ≈ template, one step left (parser + generator)
Recorded as the owner's view (`spec-and-template-no-big-difference`). It agrees with Böckeler's note that "spec as source" repeats model-driven development: the models were the specs, and generators were built to turn them into code. Analysis (synthesis):
- **The step is not small.** A parser needs a grammar, so the spec becomes a language (a DSL): this is exactly the old factory with its costs; Böckeler's judgment is that MDD "never took off for business applications" because of overhead and constraints (her opinion from her own projects).
- **A deterministic generator needs all implementation decisions in the spec.** The more complete the spec, the closer it is to a program and the generator to a compiler. Where the spec leaves choices open, a non-deterministic agent fills them. So between the two ends there is a **scale**, not two kinds: the same document can be read by a generator (all choices fixed) or by an agent (choices left to it).
- **Where the difference remains** is what the owner's next quote says: verification and risk. With a deterministic generator, the output is checked once (the generator); with an agent, **every output** has to be checked, because it can differ each time. So the determinism moves from generation to verification (leads to `old-new-same-axis-objection`).
- **ImageGen already has the "one step" in one place**: Gherkin scenarios parsed by Reqnroll into generated test code. The spec there is a restricted language with a parser and a generator. The step for application code is the proof-of-concept of task 296 (formalize ImageGen as models).
