# Notes on source 04: Anthropic, "Building always-on agents"

Source: `docs/factory/sources/04-anthropic-always-on-agents.md`. Role: **supporting, vendor** (an architecture for agents that run unattended). Claims are the vendor's; "Maps to" is our hypothesis, to be checked in task 291.

## Claims

| # | Claim in the source | Maps to in the factory concept (hypothesis) |
|---|---|---|
| A1 | An "always-on" agent is not on: it sleeps and wakes up for **runs** (receive an event, do the task, save what happened); a run works inside a **session** (transcript of messages and tool calls). The same core agent loop; the difference is the surrounding architecture. | The "near the loop" mode of source 01 (C2) is this cycle seen from the human side: agents run around the clock and stop at decision points. |
| A2 | Five primitives: **event inbox, timers, memory, permissions, outbox**. | A checklist for what a factory needs besides agents: intake (source 02, W10 "intake channels"), scheduling, memory (W10 "data plane"), guardrails (source 03 T8/T10), delivery. |
| A3 | **Event inbox:** sources do not call the agent; they write to a durable list (usually a DB table) via a handler; a worker reads it. Track event status; deduplicate by source id; start with one inbox per user. Practices: acknowledge quickly and do deeper checks (e.g. prompt injection) inside the run; the inbox is the source of truth so a dead worker's event is retried; **one active worker per inbox**; a new event mid-run is queued, folded in or interrupts; batch pending events into one run. | This repository's task files and `scripts/claim-task.sh` are a git-based inbox with claim = single worker; compare with the Warp "control plane" (source 02, W10). Gap: no event types other than tasks, no dedupe, no batching. |
| A4 | **Timers:** two kinds, **follow-ups** (a deadline the agent sets for itself) and **schedules** (recurring); stored in their own durable store, separate from the inbox; a scheduler polls, fires due timers by adding an event to the inbox and waking the worker. | Gap: the harness has no timers (audits, "check back on this PR"). Source 02 W8 (monitoring feeding back to intake) needs them. |
| A5 | **Memory:** its own durable store (a directory of files in Claude Code's auto memory and the Messages API memory tool), outliving the worker. Rule: hold only what the agent cannot look up again; store a pointer to the issue tracker instead of copying it. Types: user instructions (loaded every run), user notes (index loaded, details on demand), past messages (so nothing is repeated), **task progress** (progress file per ongoing task). Optional **dreaming**: review past sessions to curate memories (replace outdated entries, find cross-run patterns). | Close matches here: standing instructions in `docs/status.md` (user instructions), task Report/Comments (task progress), `docs/knowledge/` (notes), `AGENTS.md`/ADRs. "Dreaming" is the missing curation loop = the skill/memory loop of source 02 (W12) and the staleness audit (`scripts/audit.sh`). The "pointer, not copy" rule matches source 03 D3/T7 (write short rules in the repo, link sources). |
| A6 | **Context window:** every run loads the system prompt, tool definitions and memory files (the "overhead"); keep it lean, use prompt caching; a new session = overhead + triggering events, an existing one restores earlier messages and tool calls; if a session gets long, compact or start a new one: both lose detail, so persist what matters to memory along the way. | Matches the dialog's context thread (source 03, T6, M20); same "write outward, do not rely on compaction". |
| A7 | **Permissions** are "where always-on agents carry the most risk": a run holds the user's access and operates unattended; each tool call is proceed, block or wait for approval. Components: **credential store as a proxy outside the agent's environment** that injects credentials into outgoing requests (the agent never holds them); **auto mode** (classifiers review higher-risk actions, block dangerous ones; user review still needed for the most important decisions); **deferred tool calls** (a hook defers a call, the run ends with the session saved mid-call, the request is shown to the user, the answer returns as an **event in the inbox** and starts a new run that resumes the saved session; the worker is free for other events meanwhile). | Strong match with the owner's constraints in source 03: enforced by the system, not the prompt (T8, T10); the credential proxy is the answer to the PocketOS and Grigorev causes (broad tokens within reach). **Deferred tool calls = the "typed pause" / decision-point mechanism** (geut's `waiting_for_user`, research 02 section 6) and the right shape for "near the loop": the human answers asynchronously, as an event. In this harness the closest thing is status `blocked` plus a question in Comments. |
| A8 | **Outbox:** a run ends in one of three ways: a message to the outbox, "nothing needs to be sent", or a deferred tool call. A simple "send" tool is enough unless you need pacing or error recovery; then an outbox table plus a **dispatcher** (analogous to the worker) that decides what to deliver. **Tune how many messages the agent sends**: too many = noisy, too few = misses what the user needs; build evals for the balance; "start quiet and then earn more of the user's attention over time". | The human-attention budget: owner note N1 (owner minutes per merged task, approval waiting time). The outbox with pacing is the mechanism that makes "stop only at decision points" (source 01, C2) real, and its eval is a metric (source 02, W11). Gap: no outbox, no pacing. |
| A9 | The cycle: every run starts with an inbox event (user message, webhook, timer); worker starts the run in a new or existing session; the agent reads memory, acts within permissions, updates memory; at the end it pushes a row to the outbox; the dispatcher delivers; a run may set a timer; the user's reply returns as an inbox event. | The factory loop of source 02 (idea, triage, spec, build, review, verify, ship, monitor, back to ideas) written as an event-driven machine. |
| A10 | Vendor claims about models: models are better at judgment and "knowing when to check in"; intelligence is cheaper ("on one long-horizon coding benchmark, Opus 5.5 cost 78% less per solved task than Opus 5, compared with 40% less on typical workloads"). | Unverified vendor figures: do not use as evidence. |

## What it adds to the concept (three sources compared)

- Source 01 (TSF) names the goal (near the loop) and the tool shape (liquid template); source 02 (Warp) the lifecycle graph and skill loops; source 03 (owner's dialog) the verification and control constraints; **source 04 supplies the runtime skeleton**: durable stores (inbox, timers, memory, outbox) separated from agents, one worker per inbox, state outside the agent, and a specific way for a human to be "near the loop" (a deferred call whose answer comes back as an event).
- Not covered by source 04 (verification of results, independent checks, who judges): that remains source 03's territory; source 04 only says "user review is still necessary for the most important decisions".

## Open questions
